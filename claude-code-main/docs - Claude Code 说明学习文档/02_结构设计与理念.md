## 一、设计哲学总纲

Claude Code 的设计哲学可以用一句话概括：

> **"让 AI 成为开发者工作流中的原生公民，而不是一个外挂工具。"**

这体现在三个核心理念上：

```
┌─────────────────────────────────────────────────────────┐
│              Claude Code 三大设计理念                     │
│                                                         │
│  ┌─────────────┐  ┌──────────────┐  ┌───────────────┐  │
│  │  Markdown   │  │  事件驱动    │  │  多智能体     │  │
│  │  即代码     │  │  架构        │  │  协作         │  │
│  │             │  │              │  │               │  │
│  │ 降低门槛    │  │ 灵活拦截     │  │ 并行增效      │  │
│  │ 人人可扩展  │  │ 非侵入式     │  │ 专业化分工    │  │
│  └─────────────┘  └──────────────┘  └───────────────┘  │
└─────────────────────────────────────────────────────────┘
```

## 二、七大设计模式详解

### 2.1 模式一：Markdown即代码（Markdown-as-Code）

**核心思想**：用 Markdown 文件代替传统的代码文件来定义行为。

**为什么这样设计？**
- 传统做法：用 Python/JS 编写插件 → 需要编程能力 → 门槛高
- Claude Code 做法：用 Markdown 编写命令/智能体 → 只需会写文档 → 门槛极低

**实际案例**：定义一个代码审查命令只需要一个 .md 文件：
```markdown
---
description: 审查当前分支的代码变更
allowed-tools: Read, Bash(git diff:*)
model: sonnet
---

请审查当前分支与主分支之间的所有代码变更。
重点关注：
1. 潜在的Bug
2. 代码风格一致性
3. 安全隐患

输出格式：按严重程度排列发现的问题。
```

**设计收益**：
| 收益 | 说明 |
|------|------|
| 零编程门槛 | 产品经理、设计师都能编写命令 |
| 版本可控 | .md 文件可以直接 Git 管理 |
| 即改即用 | 修改后无需编译，立即生效 |
| 自文档化 | 命令本身就是最好的文档 |

### 2.2 模式二：约定优于配置（Convention over Configuration）

**核心思想**：目录名和文件名本身就是配置信息，无需额外的注册文件。

```
plugin-name/
├── commands/        ← 放在这里的 .md 自动成为斜杠命令
├── agents/          ← 放在这里的 .md 自动注册为智能体
├── skills/          ← 放在这里的 SKILL.md 自动加载为技能
└── hooks/           ← hooks.json 自动注册钩子
```

**设计效果**：
- 不需要"注册代码"
- 不需要"配置映射表"
- 文件位置 = 功能声明

**与 Rails 的对比**：
这与 Ruby on Rails 的理念完全一致——Rails 通过目录结构（models/、controllers/、views/）自动发现组件，Claude Code 通过 commands/、agents/、skills/ 自动发现扩展。

### 2.3 模式三：渐进式披露（Progressive Disclosure）

**核心思想**：系统按需加载信息，不一次性读取全部内容。

```
加载阶段1：plugin.json (几十字节)
    ↓ 只有插件被激活时
加载阶段2：SKILL.md / command.md (几KB)
    ↓ 只有需要详细参考时
加载阶段3：references/ + examples/ (可能几十KB)
```

**为什么重要？**
AI 大模型的上下文窗口是有限的（即使有100K/1M token）。如果一次性把所有插件文档全部加载，会造成极大的token浪费。渐进式披露确保：
- 系统只在需要时才深入加载
- 上下文窗口利用效率最大化
- 启动速度不受插件数量影响

### 2.4 模式四：事件驱动拦截（Event-Driven Interception）

**核心思想**：像 Web 中间件一样，在生命周期的关键节点插入自定义逻辑。

```
用户输入
  │
  ↓
[UserPromptSubmit 钩子] ←── 可以修改/拦截用户输入
  │
  ↓  
Claude 思考并决定使用工具
  │
  ↓
[PreToolUse 钩子] ←── 可以阻止危险命令执行
  │
  ↓
工具执行
  │
  ↓
[PostToolUse 钩子] ←── 可以审查执行结果
  │
  ↓
Claude 准备响应
  │
  ↓
[Stop 钩子] ←── 可以阻止退出、注入后续任务
```

**实际应用场景**：

| 钩子事件 | 应用场景 | 示例 |
|---------|---------|------|
| PreToolUse | 阻止危险命令 | 拦截 `rm -rf /` |
| PostToolUse | 安全审查 | 检测代码中的硬编码密钥 |
| Stop | 迭代循环 | Ralph Wiggum 的自动继续机制 |
| SessionStart | 注入上下文 | 教育模式/学习模式的样式注入 |

### 2.5 模式五：最小权限原则（Least Privilege）

**核心思想**：每个组件只获得它需要的最少工具/权限。

```yaml
# code-explorer 智能体 → 只有读取权限
tools: ["Read", "Grep", "Glob"]

# code-reviewer 智能体 → 只能读取和搜索
tools: ["Read", "Grep", "Glob", "WebFetch"]

# commit 命令 → 只能执行特定 Git 命令
allowed-tools: Bash(git add:*), Bash(git commit:*), Read
```

**设计效果**：
- 探索型智能体无法修改代码
- 审查型智能体无法执行任意命令
- 提交命令无法执行非 Git 命令
- 即使 AI 产生幻觉，也不会造成破坏

### 2.6 模式六：策略层级覆盖（Policy Hierarchy Override）

**核心思想**：多级配置体系，高优先级策略可覆盖低优先级设置。

```
优先级（从高到低）：
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
① managed-settings.json     │ 企业强制策略（MDM下发）
                             │     ↓ 覆盖
② .claude/settings.json     │ 项目级配置（团队检入Git）
                             │     ↓ 覆盖
③ .claude/settings.local.json│ 用户本地覆盖（.gitignore）
                             │     ↓ 覆盖  
④ ~/.claude/settings.json   │ 用户全局偏好
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```

**现实场景**：
- 企业安全团队通过 MDM 下发 `deny: ["Bash(rm:*)"]` → 全公司禁止删除命令
- 项目组在 `.claude/settings.json` 设置 `allow: ["Bash(npm:*)"]` → 允许npm命令
- 开发者个人在 `settings.local.json` 调整偏好 → 不影响团队

### 2.7 模式七：并行智能体编排（Parallel Agent Orchestration）

**核心思想**：多个专业智能体同时工作，结果合并后输出。

```
命令发起
    │
    ├──→ 智能体A（CLAUDE.md合规检查）──┐
    ├──→ 智能体B（CLAUDE.md合规检查）──┤
    ├──→ 智能体C（Bug检测）          ──┤── 结果汇总 → 置信度过滤 → 最终报告
    └──→ 智能体D（历史分析）          ──┘
```

**置信度评分过滤机制**：
```
得分 0-25  → 误报，静默丢弃
得分 26-49 → 低置信度，仅记录日志
得分 50-79 → 中等置信度，列为次要发现
得分 80-100 → 高置信度，列为主要发现并报告
```

## 四、数据流架构

### 4.1 一次命令执行的完整数据流

```
用户输入: "/feature-dev 添加用户认证"
    │
    ↓
①【命令解析】
    解析斜杠命令名 → 查找 feature-dev.md
    提取 YAML 前置数据 → allowed-tools, model
    注入 $ARGUMENTS → "添加用户认证"
    │
    ↓
②【钩子拦截 - UserPromptSubmit】
    遍历注册的钩子 → 执行处理脚本
    返回：allow / block / 修改后的输入
    │
    ↓
③【AI推理】
    Claude API 调用 → 分析需求
    决定启动 code-explorer 智能体
    │
    ↓
④【智能体调度】
    并行启动 2-3 个 code-explorer
    每个智能体独立执行：
      → 读取代码文件
      → 搜索相关模式
      → 生成探索报告
    │
    ↓
⑤【工具执行（每次工具调用前后都有钩子）】
    [PreToolUse 钩子] → 检查工具合法性
    执行工具（Read/Grep/Glob/Bash）
    [PostToolUse 钩子] → 审查执行结果
    │
    ↓
⑥【结果汇总】
    收集所有智能体返回结果
    合并去重 → 置信度评分 → 筛选输出
    │
    ↓
⑦【响应输出】
    格式化结果 → 返回用户
    │
    ↓
⑧【Stop 钩子】
    检查是否需要迭代 → 允许退出 / 继续循环
```

### 4.2 钩子数据通信协议

钩子通过 **标准输入/输出** 和 **JSON 协议** 通信：

```
┌─────────────┐    stdin (JSON)     ┌──────────────┐
│ Claude Code  │ ──────────────────→ │  钩子脚本     │
│ 主进程       │                     │  (.py/.sh)   │
│              │ ←────────────────── │              │
└─────────────┘    stdout (JSON)    └──────────────┘
```

**输入数据格式**：
```json
{
  "tool_name": "Bash",
  "tool_input": {
    "command": "rm -rf ./temp"
  },
  "session_id": "abc123",
  "conversation_context": "..."
}
```

**输出数据格式**：
```json
{
  "decision": "block",
  "reason": "检测到危险的删除命令",
  "systemMessage": "已阻止危险操作: rm -rf",
  "hookSpecificOutput": {
    "hookEventName": "PreToolUse",
    "permissionDecision": "deny"
  }
}
```

## 五、扩展性设计分析

### 5.1 扩展点矩阵

| 扩展维度 | 扩展方式 | 技术要求 | 典型场景 |
|---------|---------|---------|---------|
| 新增命令 | 添加 .md 到 commands/ | 无需编程 | 自定义工作流 |
| 新增智能体 | 添加 .md 到 agents/ | 无需编程 | 专业化任务 |
| 新增技能 | 添加 SKILL.md 到 skills/ | 无需编程 | 领域知识注入 |
| 行为拦截 | 编写 hooks.json + 脚本 | Python/Bash | 安全策略/质量门禁 |
| 外部工具 | 配置 .mcp.json | 了解MCP协议 | 对接外部服务 |
| 完整插件 | 创建插件目录结构 | 综合能力 | 功能模块化分发 |

### 5.2 插件生命周期

```
1. 发现 → 扫描 .claude-plugin/plugin.json
2. 注册 → 读取 plugin.json 元数据
3. 加载 → 发现 commands/ agents/ skills/ hooks/
4. 激活 → 注册钩子、加载命令列表
5. 执行 → 用户触发或自动匹配
6. 卸载 → 移除插件目录即可
```

## 六、设计理念总结

| 理念 | 实现方式 | 业界对标 |
|------|---------|---------|
| 降低门槛 | Markdown即代码 | Notion/Obsidian 的插件理念 |
| 约定优于配置 | 目录结构即配置 | Ruby on Rails |
| 渐进式披露 | 三级信息加载 | 移动端UI设计原则 |
| 事件驱动 | 生命周期钩子 | Express中间件、Git Hooks |
| 最小权限 | 工具白名单 | 容器安全、Linux capabilities |
| 策略层级 | 多级配置覆盖 | CSS层叠样式/K8s ConfigMap |
| 并行编排 | 多智能体并行 | MapReduce/微服务编排 |

**一句话总结**：Claude Code 的架构设计，本质上是将**软件工程的最佳实践**（中间件、插件系统、最小权限、事件驱动）与**AI原生能力**（自然语言理解、多智能体协作、上下文管理）巧妙融合的产物。
