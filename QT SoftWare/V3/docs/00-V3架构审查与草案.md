## 零、核心结论（先给结论，再给证据）

V2 的**骨架方向是对的，但血肉是"为了凑指标"堆出来的**。具体表现为三件事：

1. **写了状态机却从不接线**——`DeviceController`（自动重连）在正式程序里是死代码，`mainwindow.cpp:56` 直接 `new DataService`，绕过了 `DeviceController`。文档宣称的"自动重连已接入应用"与事实不符，它只活在 `tst_devicecontroller` 一个测试里。

2. **两套领域模型并存**——`domain/models.h`（V1）与 `domain/domainmodel_v2.h`（`namespace v2`）同时存在。热路径（`acquisitionworker.cpp` → `DataService` → `MonitorPage`）走 V1 的 `domain::DataPoint`，而 `v2::DataPoint`/`AlarmRule`/`AlarmEvent` 只被 alarm/model 层消费。这不是"渐进迁移"，是"平行宇宙"。

3. **V1 审查列为 P0 的问题，V2 只是换了个位置**——报警阈值 `rangeMax × 0.85` 从 V1 的 `monitorpage.cpp` 内联 `value>max*0.85`，挪进了 V2 的 `setupAlarmRules()`，本质仍是 View 层硬编码魔法数（`monitorpage.h:184 kAlarmRatio = 0.85`）。

**结论：你的判断是对的。V2 不作为 V3 的代码基础。V3 保留 V2 的"协议层、模拟器、测试方法、失败教训"，其余重写。**

## 五、V3 总体架构

### 5.1 架构风格：分层 + 依赖倒置（Ports & Adapters / 洋葱架构）

V2 是"分层但依赖方向靠约定"（上层依赖下层，靠头文件注释约定红线）。V3 用**依赖倒置**把约定变成编译器强制：

```
┌─────────────────────────────────────────────────────────┐
│  UI 层（Qt Widgets + Model/View）—— 适配器（Adapter）      │
│   MainWindow / DevicePage / MonitorPage / ...            │
├─────────────────────────────────────────────────────────┤
│  Application 层（用例编排，纯业务，无 Qt 依赖）              │
│   ConnectDeviceUseCase / StartAcquisitionUseCase /       │
│   EvaluateAlarmUseCase / RecordSessionUseCase            │
├─────────────────────────────────────────────────────────┤
│  Domain 层（纯 C++17，零 Qt / 零框架依赖）★核心★           │
│   Device / ChannelConfig / DataPoint / AlarmRule /       │
│   AlarmEvent / AcquisitionSession / ConnectionState      │
│   + 端口接口（Port）：IDevicePort / IDataSink / IClock     │
├─────────────────────────────────────────────────────────┤
│  Infrastructure 层（Adapter 实现端口，可替换）              │
│   TcpDeviceAdapter / SerialDeviceAdapter /               │
│   FileRecordAdapter / ConfigAdapter / LogAdapter         │
└─────────────────────────────────────────────────────────┘
```

**关键变化 vs V2：**

1. **Domain 层零 Qt 依赖**——V2 的 domain 依赖 `QString/QDateTime/QVector`。V3 的 domain 用纯 C++17（`std::string`/`std::optional`/`std::vector`/`std::chrono`）。理由：真正可测（无需 Qt 事件循环）、可迁移 Linux、可被非 Qt 代码消费。Qt 类型只在 UI/Adapter 边界转换。

2. **Application 层是新增的**——V2 没有这一层，业务逻辑散落在 services 和 UI 里。V3 用 Use Case（用例）编排 domain，UI 只做"发命令 + 渲染结果"。

3. **依赖倒置**——domain 定义端口接口（Port），infrastructure 实现（Adapter），通过构造函数注入。上层（application/UI）依赖接口，不依赖具体 Adapter。这让"换 TCP→串口"、"换文件→数据库"成为加一个 Adapter 而非改业务代码。

### 5.2 为什么不用 V2 的"5 个静态库"直接搬

V2 的 6 个静态库（utils/infra/domain/protocol/services/simulator）划分是对的**方向**，但：
- `domain` 被 `ui/models` 污染（`devicelistmodel` 编进 `datascope_domain`，而它是 Qt Model，违反"domain 零 Qt"）。
- `services` 层职责过重（既有 TCP 又有状态机又有记录又有报警），边界不清。
- 没有 Application 层，UI 直接摸 services。

V3 的库划分见第六节。

## 六、V3 模块边界

| 模块（CMake target） | 内容 | 允许依赖 | 禁止依赖 |
|----------------------|------|---------|---------|
| `dscope_domain` | 领域模型 + 端口接口 + 纯逻辑服务（报警评估/状态机转移） | 无（纯 C++17） | Qt、UI、网络、文件 |
| `dscope_protocol` | 协议引擎（帧格式/CRC/编解码/流式解析） | 无（纯 C++17，或仅 `std`） | Qt、domain、UI |
| `dscope_application` | Use Case 编排 + 应用服务接口 | domain、protocol | Qt Widgets、具体 Adapter |
| `dscope_infra_tcp` | TCP 设备 Adapter（实现 IDevicePort） | domain 端口、QtNetwork | UI、application |
| `dscope_infra_serial` | 串口 Adapter（P9 预留，实现同一 IDevicePort） | domain 端口、QtSerialPort | UI |
| `dscope_infra_storage` | 记录/配置/日志 Adapter | domain 端口、QtCore | UI |
| `dscope_simulator` | 模拟设备（实现 IDevicePort 的"设备侧" + FaultInjector） | protocol、QtNetwork | domain 业务、UI |
| `dscope_ui` | Qt Widgets + Model/View | application 接口、domain（只读）、QtWidgets | 具体 Adapter、协议细节 |
| `dscope_app` | main() + 依赖组装（Composition Root） | 所有模块 | —（唯一允许"知道一切"的地方） |

**关键红线：**
- **只有 `dscope_app`（Composition Root）知道具体 Adapter**。其余模块只依赖接口。
- **domain 和 protocol 不依赖 Qt**。这是 V3 与 V2 最大的不同。
- **UI 不碰协议细节**（不直接 `#include frameparser.h`），只通过 application 层拿领域对象。

## 七、V3 依赖方向

```
dscope_app（组装）
   ↓ 依赖所有
dscope_ui ──→ dsсope_application ──→ dsсope_domain（零依赖）
                                     ↕（domain 定义端口，适配器实现端口）
                    dsсope_infra_*（实现端口）──→ dsсope_domain 端口
dscope_protocol（独立，零依赖）←── dsсope_infra_tcp/serial/simulator
```

**规则（编译器强制，非注释约定）：**
1. 依赖只能从外层指向内层，禁止反向。
2. `domain` 不 include 任何 Qt 头、任何本工程其他模块头。
3. `protocol` 不 include domain（协议是字节契约，不知道业务语义）。
4. `application` 依赖 domain 接口 + protocol 类型，不依赖具体 Adapter。
5. `ui` 只依赖 `application` 的用例接口和 domain 的只读模型，绝不 `new` 具体 Adapter。
6. 跨模块共享类型（如 `DataPoint`）只定义一次，放在 domain。

## 八、V3 数据流

**单向数据流（采集）**：

```
设备/模拟器 ──字节流──▶ [TcpDeviceAdapter] ──原始帧──▶ [FrameParser 协议层]
                                                            │
                                             [Application: 帧→DataPoint 用例]
                                                            │
                              ┌─────────────────────────────┤
                              ▼                             ▼
                     [DataBus 数据总线]              [AlarmEngine 报警评估]
                     (有界队列, 线程安全)              (纯逻辑, 同帧触发)
                              │                             │
                              ▼                             ▼
                     [DeviceListModel 等]            [AlarmEventModel]
                              │                             │
                              └──────────────┬──────────────┘
                                             ▼
                                    [MonitorPage 渲染]
```

**关键点：**
1. **只有一条数据入口**——UI 只认 `IDataBus::subscribe()`，数据源（真实设备/模拟器/回放文件）都是"实现同一个端口"，不靠 if/else 区分。
2. **报警与渲染是数据流的两条分支**，都从同一条原始数据出发，不互相阻塞。
3. **回放是独立的 IDataBus 实现**——回放时真实采集暂停，不是"两个源同时灌一个曲线"（V2 的 replayData 与 dataUpdated 混叠问题）。

## 九、V3 线程模型

V2 的线程模型（QThread + moveToThread + QueuedConnection）认知是对的，但生命周期脆弱。V3 明确以下规则：

| 线程 | 职责 | 通信方式 |
|------|------|---------|
| **UI 线程** | 事件循环、渲染、Model 更新 | 只收信号/回调，不做 I/O、不做解析 |
| **每设备一个 I/O 线程** | 收字节、喂 FrameParser、发帧 | 通过 `IDataBus`（有界队列）推数据给主线程 |
| **记录线程**（可选） | 异步落盘 CSV/文件 | 消费 IDataBus 的快照流，不阻塞采集 |
| **定时器/时钟** | 用可注入 `IClock`，测试可伪造 | — |

**铁律（写成 Coding/Threading Rules）：**
1. socket 在所属线程内创建（V2 已知，V3 固化）。
2. 跨线程只传**值对象**（可拷贝、无指针），禁止传裸指针/引用跨线程。
3. 线程关停用**显式协议**：`stop() → 清队列 → drain() → quit() → wait()`，禁止 `wait(固定毫秒)` 赌超时。
4. 共享数据不靠裸锁，靠**有界队列 + 单一写者/单一读者**（SPSC）。
5. 元类型注册集中在**一个**编译单元（`metatype_registry.cpp`），不再散落。
6. 禁用 `QMetaObject::invokeMethod` 字符串重载，用类型安全连接。

## 十、V3 对象生命周期模型

1. **业务对象 ≠ QObject**——domain 对象（Device/DataPoint/AlarmEvent）是纯值/实体，不继承 QObject，不用对象树管理，用值语义 + `std::unique_ptr`/`std::shared_ptr` 显式所有权。
2. **QObject 只用于需要信号槽的 UI/Adapter 对象**，用对象树管理（parent 链）。
3. **Composition Root 组装所有依赖**，main() 里 `new` 顶层对象，其余通过构造函数注入，不用全局单例。
4. **线程对象显式关停**——持有 QThread 的对象析构前必须 `stop → quit → wait`，且有超时兜底 + 日志告警（不能静默崩溃）。
5. **资源 RAII**——socket/文件/锁全用值成员或智能指针，禁止手动 `new QMutex` 再 `delete`。

## 十一、V3 错误处理模型

V2 的错误全 `QString`，无法分类、无法降级、无法测试断言。V3 改为：

```cpp
// 错误码枚举（domain 层定义，零 Qt 依赖）
enum class ErrorCode {
    Ok,
    Timeout,
    ConnectionRefused,
    ProtocolCrcMismatch,
    ProtocolIllegalFrame,
    PayloadTooLarge,
    DeviceBusy,
    ConfigInvalid,
    IoError,
    // ...
};

// Result 包装（带回值或错误）
template <typename T>
class Result {
    T value;            // 成功时的值
    ErrorCode code;     // 失败时的码
    std::string detail;// 人类可读上下文（非控制流用）
    bool ok() const;
    // ...
};
```

**规则：**
1. 跨模块边界（Adapter→Application）只返回 `Result<T>` 或 `ErrorCode`，**不返回裸 bool 假装成功**。
2. `QString` 错误信息只在 UI 边界生成（`ErrorCode → 用户可读文案` 映射表在 UI 层）。
3. **禁止静默丢弃**——CRC 错/解析异常必须上报（计数 + 可选日志），V2 的"静默丢帧"是错的。
4. 协议错误、通信错误、业务错误**分层归类**，UI 能按类别降级显示。

## 十二、V3 配置模型

1. **非单例**——`ConfigStore` 是普通对象，通过接口 `IConfigStore` 注入。
2. **分层配置**——默认值（编译期）→ 用户配置（文件）→ 运行时覆盖（会话），合并有明确优先级。
3. **Schema 校验**——配置项有类型 + 取值范围，非法值拒绝加载并报错（不是静默用默认值）。
4. **变更通知**——配置变更是信号/回调，UI 订阅刷新（V2 只有主题切换是这种模式，V3 全部走这种模式）。
5. **设备配置独立于应用配置**——设备连接参数是 domain 对象 `ConnectionParams`（V2 已建模，保留），持久化到设备存储，不是塞进全局 INI。

---

## 十三、V3 协议层设计

**保留 V2 的正确部分**：帧格式 `SOF(0xAA55) | FUNC | CMD | LEN(大端) | DATA | CRC16(MODBUS)`、`FrameParser` 的 feed/nextFrame 模型、`kMaxPayloadLen` 防御、`Crc16`。

**V3 改进（推翻 V2 的缺陷）：**

1. **帧增加序列号 + 时间戳**（V1 审查 P2 已指出"帧无序列号，回放与实时无法区分"）——V3 帧头加 `SEQ(4B)`，数据帧带设备时间戳。
2. **帧类型枚举化 + 白名单过滤**——V2 的 `acquisitionworker::handleFrame` 不校验 func/cmd，任何帧都按"N×4B float"解析。V3 用显式的帧类型 switch + 白名单，未知帧拒绝。
3. **Codec 与解析器分离**——`ChannelConfigCodec` 是好的（纯编解码 + 脏数据防御），V3 把它泛化为"每个 FUNC/CMD 一个 Codec"，解析器只负责拆帧，Codec 负责解码。
4. **协议层零 Qt**——`QByteArray` → `std::vector<uint8_t>` + 长度，纯 C++17。理由：可移植、可测（无需 Qt）、可被模拟器和测试直接消费。
5. **协议错误上报**——解析器产出"错误帧"而不是静默丢弃，错误计数器暴露给上层。

---

## 十四、V3 Simulator 设计

**保留 V2 的正确部分**：FaultInjector 纯逻辑注入器、SimulatorDevice 组件化、运行模式、`start(0)` 随机端口可测、命令行配置。

**V3 改进：**

1. **场景文件驱动**——不只是命令行参数，支持 JSON 场景文件（"第 0~100 帧正常 → 第 101 帧注入 CRC 错 → 第 200 帧断线 5 秒 → ..."），可复现、可入库、可 CI。
2. **模拟设备 = 真实设备的"反角色"**——实现与真实 Adapter 相同的 `IDevicePort` 的**设备侧**，保证"测试设备"和"真实设备"协议一致。
3. **多客户端隔离**——V2 已有 `m_clientParsers` 每客户端一个解析器，V3 固化这条规则（多客户端不串帧）。
4. **可编程数据生成**——正弦只是默认，支持自定义波形函数/回放真实采集数据（喂历史 CSV 让模拟器重放）。

## 十五、V3 测试架构

V2 的测试数量是虚的——163 用例里大量是"为了覆盖指标"（如 `tst_signalslotdemo` 直接测教学对象、UI 零测试、smoke/integration 目录曾经是空的）。V3 重新定义测试分层：

| 层 | 测什么 | 工具 | 边界 |
|----|--------|------|------|
| **Unit** | domain 不变量、状态机转移、协议解析、编解码 | GoogleTest 或 QtTest（纯逻辑无 Qt 时用 gtest） | 无 I/O、无线程、无 Qt 事件循环 |
| **Component** | 单个 Adapter（TcpDeviceAdapter 面对模拟 socket） | 测试替身 + 回环 | 有 I/O 但单组件 |
| **Integration** | 应用层用例 + 真实模拟器（随机端口） | SimulatorDevice 内嵌 | 跨组件组装，无真实硬件 |
| **E2E** | 双进程（DataScope + simulator）+ 发布包 | 脚本 + 协议探针 | 真实进程边界 |

**规则：**
1. **测试替身优先**——用接口注入 fake，不用真实 socket/文件/时钟。V2 的"绑定-释放法找空闲端口"（4.3s 且 flaky）要弃用，V3 用 `start(0)` 随机端口。
2. **禁止 `qWait(固定毫秒)` 和裸 sleep**——用 `QTRY_VERIFY_WITH_TIMEOUT` 事件驱动断言，或注入 fake 时钟。
3. **每个领域不变量必须有对应测试**——"有行为才有测试"，不为凑数写 getter/setter 测试。
4. **失败场景必须有测试**——断线重连、超时、CRC 错、非法帧、线程退出时序，这些是工业软件的生命线。
5. **测试独立于开发 Agent**（保留 V2 原则）。

## 十六、V3 UI 架构

1. **真 Model/View**——V2 补了 `DeviceListModel`/`AlarmEventModel`，但 UI 数据流仍有硬编码。V3 所有列表/表格走 QAbstractItemModel，数据变化走 `dataChanged`，不手动刷新控件。
2. **每页一个 Presenter/Controller（瘦 UI）**——UI 只渲染，业务逻辑在 application 层用例。V2 的 `monitorpage` 塞了报警规则、demo 源、卡片重建等一堆逻辑，V3 全部抽走。
3. **去教学代码**——`signalslotdemo`/`demopage`/`onDemoTick` 不进入生产 exe。学习内容全部在 `docs/learn/`。
4. **自绘控件保留并提升**——LineChartWidget（改环形缓冲去 O(n)）、GaugeWidget、LedIndicator 是真实资产，但颜色/字体抽主题 token，时间轴用真实时间戳（V2 曲线无时间维度）。
5. **报警可视化**——曲线阈值线、仪表危险区、时间轴刻度（V1 审查 P0，V2 未完全落实）。

## 十七、V3 日志架构

1. **结构化日志**——不是 `LogManager::info("MainWindow", "字符串拼接")`，而是带字段的结构化事件（时间/级别/category/消息/上下文），便于过滤和后续分析。
2. **非单例**——`Logger` 通过接口 `ILogger` 注入，sink（控制台/文件/滚动）可替换。
3. **分级 + 分类器（category）**——按模块分类（`net.tcp`、`proto.parse`、`alarm`、`storage`），运行时按 category 过滤。
4. **性能**——异步 sink，日志不阻塞采集线程；有界队列防日志风暴。

---

## 十八、V3 性能设计

1. **有界缓冲 + 背压**——数据总线用有界队列，消费慢时丢弃旧数据而非无限堆积（V2 无此概念）。
2. **去除 O(n) 操作**——曲线缓冲用环形缓冲（`std::deque` 或 `QVector` 头尾双指针），不用 `removeFirst()`。
3. **批量渲染**——UI 更新按帧率节流（如 30Hz），不是每个数据点都重绘。
4. **零拷贝/移动语义**——跨线程传值对象用 move，避免深拷贝。
5. **协议解析性能基准**——大量帧下解析器不退化（V2 无性能测试，V3 加 benchmark）。

---

## 十九、V3 发布设计

1. **CI 自动化**——一键构建 + 测试 + 打包，不在本机手工 windeployqt（V2 是手工/半自动）。
2. **版本一致**——主程序与 simulator 同版本号（V2 曾出现 1.0.0 vs 0.1.0 不一致）。
3. **发布包验证**——自动化校验 DLL 完整性 + 独立环境运行（V2 的 e2e probe 方向对，但要做成 CI 门禁）。
4. **编译产物与源码分离**——`build/`、`deploy/` 不进版本库。

## 二十、V3 扩展路线（Serial / 多设备 / 数据分析 / Linux）

| 扩展 | V3 预留方式 | 说明 |
|------|-----------|------|
| **串口（P9）** | `IDevicePort` 端口已抽象，加 `SerialDeviceAdapter` 即插即用 | 串口与 TCP 是同一端口的两个 Adapter，业务零改动 |
| **多设备** | `IDeviceManager` 管理 `QVector<IDevicePort>`，每设备一线程 | 设备是聚合根，天然支持集合 |
| **数据分析** | 数据总线是"流"，分析是"消费者"，`IDataSink` 可插拔 | 加 `AnalysisSink`（均值/方差/频谱）不碰采集 |
| **Linux** | domain/protocol 零 Qt，UI 用 Qt 跨平台，网络用 QtNetwork 跨平台 | 唯一平台相关的是 windeployqt（换成 linuxdeployqt） |

## 二十一、给 7 个审查角色的攻击目标

以下是我作为 Principal Architect 的**可被推翻的假设**，请各角色重点攻击：

1. **"domain 零 Qt 依赖"**是否过度？纯 `std::string` vs `QString` 的转换成本是否值得？（Senior Qt/C++ 攻击点）
2. **"每设备一个线程"**在多设备/高频场景是否撑得住？是否需要线程池或 IO 多路复用？（Concurrency 攻击点）
3. **"Application 层用例"**是否引入不必要的抽象层，导致 V2 的"services 门面"问题换个马甲重来？（Principal SW Architect 攻击点）
4. **"协议层零 Qt"**是否与"协议层被 simulator/测试复用"矛盾？`std::vector<uint8_t>` 与 `QByteArray` 的边界转换在哪？（Industrial Communication 攻击点）
5. **"Result<T> 错误模型"**是否会重蹈 V2"假装成功"覆辙？错误是否真的不可忽略？（Testing 攻击点）
6. **"每页一个 Presenter"**在 Qt Widgets 语境是否合适？会不会又变成"为了分层而分层"？（UI Architecture 攻击点）
7. **"CI 自动化发布"**在用户当前"本机开发、无远程 CI 服务器"的环境下是否可行？（Release 攻击点）
