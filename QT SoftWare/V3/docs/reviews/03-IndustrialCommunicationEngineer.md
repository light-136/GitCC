## 一、同意点（简要）

1. **保留 FrameParser 的 feed/nextFrame 模型 + kMaxPayloadLen 防御** —— 正确。这是 V2 唯一被各审查一致高分的设计，"累积缓冲 + 按需提取"天然解半包/粘包，LEN 越界防御是真实的内存攻击防御。V3 保留思路重写，方向对。
2. **保留 Crc16 / FrameBuilder 的字节契约** —— 正确。CRC 是"已验证的字节契约"，不重造轮子。
3. **保留 FaultInjector 纯逻辑注入器** —— 正确。"正常帧 → 0..N 段异常字节流"的纯函数设计是教科书级可测性。
4. **"错误分类分层上报"方向正确** —— V2 的"CRC 错静默丢弃"（frameparser.cpp:153-154）确实该改，草案第十一节"禁止静默丢弃"是对的。
5. **"协议层零 Qt"的动机正确** —— 可测、可移植、可被非 Qt 代码消费，这个目标没错。**但草案把"零 Qt"偷换成了"零 Qt 容器"，容器选择是错的**（见攻击点 3）。

## 二、攻击点（主体）

### 攻击点 1【P0】帧格式变更没有"协议版本号 / 版本协商"，是兼容性炸弹

草案第十三节第 1 点说"帧头加 SEQ(4B)，数据帧带设备时间戳"。这意味着帧头从 6 字节（`kHeaderLen=6`）膨胀到 10 字节以上，且 CRC 覆盖范围、LEN 语义、字段偏移全部变化。

**问题：草案通篇没有一个"协议版本号"字段，也没有新旧帧如何共存的协商机制。**

DataScope 已经按 V2 契约（`03-通信协议帧格式契约.md`）交付了 simulator 与固件约定，这些"已交付设备/模拟器"按 6 字节头、无 SEQ 组帧。V3 主机一旦换成新帧格式解析，旧设备的帧会怎样？
- FUNC/CMD 会错位读成 SEQ 的高位字节；
- 校验对不上 → 整帧被判非法丢弃；
- 最坏情况：错位后 LEN 读出一个合法小值，CRC 恰好撞上，**把旧帧静默误解析成新帧**——这是比"丢弃"更危险的错乱。

工业协议的真实教训：**帧格式一旦上线就不能单方面改**，改就必须有版本协商或显式兼容开关。草案加了字段，却对"新旧帧如何共存/识别"完全没提。这比"加不加 SEQ"更前置，是必须先回答的问题。

**要求**：草案必须给出 V3 完整帧布局（逐字段、字节数、字节序、CRC 新覆盖范围、时间戳编码与字节数），并明确"协议版本"的三个候选来源（帧头 version 字节 / 连接配置里声明 / 握手协商）选哪个、为什么。

### 攻击点 2【P0】超时 / 心跳 / 半开连接 —— 草案"承认了问题"但正文没有解决方案，V2 已示范过一次"建模不接线"

V1 审查已指出"无连接超时/心跳/keep-alive"。V2 做了什么？两件事，且第二件证明问题会重演：

1. `ConnectionParams` 建模了 `connectTimeoutMs = 5000`（`domainmodel_v2.h:135`）。
2. **但 `TcpClient::connectToHost()`（`tcpclient.cpp:51-55`）根本没有用到这个字段**——只是 `m_socket->connectToHost(host, port)` 异步发起，没有 `waitForConnected`、没有 QTimer 兜底、没有超时上报。

结果：连不可达 IP（如 `192.168.1.200`）时，OS 的 TCP SYN 重试默认可达 20 秒以上才返回，UI 长时间无反馈。工业现场要求 3~5 秒内明确报"连不上"。

草案对此的回应只有两个名词：`ErrorCode::Timeout`（第十一节）、"自动重连作为 Connection 状态机真实转移"（第四节）。**草案正文没有回答三个具体问题：**

1. **连接超时在哪层实现、超时值从哪来？** Adapter 里 `waitForConnected + 定时器`？还是 application 层？`connectTimeoutMs` 已建模，V3 接不接线？
2. **半开连接（网线拔断）怎么检测？** 这是最致命的空白。DataScope 是**被动收**模型——simulator 的 `onTick` 周期主动推（`simulatordevice.h`），主机只消费 `readyRead`。半开时 TCP 静默：主机既不 `write`，也不再收到 `readyRead`，**永远不会自己发现断线**。唯一可靠机制是"接收超时"——超过 X 毫秒没收到任何帧即判半开 → 断开重连。草案对"接收超时阈值"这个核心参数只字未提。
3. **keep-alive 用 TCP 层还是应用层？** 设备侧（simulator）本来就在周期发数据帧，这本身就是天然心跳——所以"接收超时"即可，无需额外心跳帧。但这条必须**显式声明**，否则会被误以为"V3 还没做心跳"。

**结论**：V2 已经示范了一次"建模 connectTimeoutMs 但不接线"（这是草案第二节"失败但假装成功"清单里的同源问题）。V3 若只是在草案里再写一遍 `ErrorCode::Timeout` 和"自动重连"，等于把 V1 的 P0 问题第三次换位置。必须给出"连接超时 + 接收超时 + 半开检测"三者各自的实现层、参数来源、与 Connection 状态机的转移关系。

### 攻击点 3【P1】协议层"零 Qt"用 `std::vector<uint8_t>` 是错误的容器选择，会引入 Adapter 边界拷贝

草案第十三节第 4 点："QByteArray → std::vector<uint8_t> + 长度"；草案第七节"protocol 不 include Qt"。

但看草案自己的数据流（第八节）：`[TcpDeviceAdapter] ──原始帧──▶ [FrameParser 协议层]`。TcpDeviceAdapter 内部是 QTcpSocket，现状 `readyRead` 里 `m_socket->readAll()` 返回 **QByteArray**（`tcpclient.cpp:104`）。simulator 侧同理：`socket->write(chunk)` 接收 QByteArray，FaultInjector 输入输出全是 QByteArray（`faultinjector.h`）。

如果 `FrameParser::feed` 改成 `std::vector<uint8_t>`，则：
- 每收一段字节，QByteArray → std::vector 要么 **memcpy 一遍**（热路径拷贝），要么 `fromRawData` 零拷贝但丢失生命周期保证。
- QByteArray 本身是引用计数 COW 的连续内存，转 std::vector 会**破坏 COW 语义**（本可零拷贝 append 的场景被强制变成拷贝）。
- 发送侧（FrameBuilder 产出 std::vector → `socket->write` 需要 `char*`/QByteArray）同样要再转一次。

**"零 Qt"和"被 Qt Adapter 复用"之间存在真实的边界转换成本，草案没有指定转换点在哪、用什么接口避免拷贝。** 这正是草案第二十一节第 4 点自己列出的待攻击假设——答案是：这个矛盾是真实的，而且草案的容器选择让它无解。

**正确做法**：该零 Qt 的是**纯逻辑**（Crc16 查表、Codec 字节运算、状态机转移、FaultInjector 变换），**不该**是"字节缓冲容器"。容器接口应该用**视图/跨度**：`std::span<const std::byte>`（C++20，草案锁定 C++17 则用 gsl::span 或自造 span）或 `const std::byte* + size`。这样 QByteArray 的 `data()/size()` 和 std::vector 的 `data()/size()` 都能零拷贝喂给同一套 Crc16/FrameParser，协议层依旧不 include Qt。草案把"零 Qt"偷换成了"零 Qt 容器"——容器恰恰是最不该自己拥有的那一层。

### 攻击点 4【P1】IDevicePort 把 transport 和 framing 两层压成一个，串口语义会被 TCP 压扁

草案第四节/第二十节：`IDevicePort` 一个端口，`TcpDeviceAdapter` 与 `SerialDeviceAdapter` 都实现它，"换 TCP→串口业务零改动"。

但 TCP 与串口的差异不在 `open/read/write`，而在**帧定界与链路状态**：
- **TCP**：字节流、可靠有序，SOF+LEN 定界即可，无需帧间隙。
- **串口**：无包边界；RS485 半双工主从轮询需要"帧间静默超时"判定一帧结束（Modbus RTU 用 3.5 字符时间）；需要**方向切换**（RTS/GPIO，发完切接收）；断线检测靠 DSR/CD 信号或超时，与 TCP 半开机制完全不同。

一个 IDevicePort 要同时表达这两者，只有两个结局：
1. **接口宽泛化**：每个方法内部 `if serial ... else if tcp ...`，最不公共面，换传输时"业务零改动"是假象——业务还是得知道面对的是哪种传输。
2. **串口语义被压扁成"像 TCP 的串口"**：帧间隙、方向切换、断线信号这些串口特有语义无处安放，最后塞进 SerialDeviceAdapter 私有实现，接口层看不到。

**更严重的是分层污染**：IDevicePort 被放在 domain 层（第四节"端口接口（Port）：IDevicePort"）。若 IDevicePort 要暴露波特率/流控/帧间隙/半双工这些**物理层概念**，domain 层就被物理层污染，违反"domain 纯业务"的初衷。而 V2 的 `ConnectionParams` 只建模了 `baudRate`（`domainmodel_v2.h:134`），**缺数据位/校验位/停止位/流控/半双工标志**——这些是接真实串口设备必须的，缺了就接不了真实串口。

**建议**：分两层抽象——`ITransport`（open/read/write/close + 能力位查询）之上加 `IFraming`（TCP=流式 SOF+LEN；串口=帧间隙定界 + 流式）。串口特有配置走 `ConnectionParams` 的 variant/tagged union，不让 domain 层为串口单独开接口。草案现在的一个 IDevicePort 是"为了抽象而抽象"，反而把最需要显式的差异藏起来了。

### 攻击点 5【P1】多设备"每设备一线程"合理性悬空——没定位"上报型 vs 轮询型"

草案第二十节：`IDeviceManager` 管理 `QVector<IDevicePort>`，每设备一线程。

工业现场两种模型，二者对线程模型的要求完全不同：
- **异步上报**（设备主动推）：每个 socket 阻塞在 read，一线程一 socket 最自然。当前 V2 simulator 就是此模型（`onTick` 周期广播，主机被动收）。
- **主从轮询**（主机主动问）：主机发请求 → 等响应 → 超时 → 下一请求，是**调度驱动**。

**草案从头到尾没有说 V3 是哪种模型。** 这个缺失让"每设备一线程"变成无锚点的拍脑袋：

- 若是上报型，一线程一设备合理，但要定设备数上限——几十上百台设备 = 上百线程，Windows 每线程默认栈 reserve 1MB，100 线程 = 100MB 虚拟内存 + 上下文切换开销。草案没给设备数上限，也没给"超过 N 台转 IO 多路复用（epoll/select）"的切换阈值。
- 若是轮询型，"每设备一线程"仍可（每设备一个轮询循环），但更优是"一个采集调度线程 + IO 多路复用"统一调度所有设备的请求-响应，否则 N 设备的请求各自为政抢占。

而且草案第九节线程模型只有"每设备 I/O 线程"和"记录线程"，**没有"采集调度器"的位置**。`IDeviceManager` 被定义成 `QVector` 容器，但轮询模型下 Manager 必须承担调度职责（谁先问、超时怎么推进），不是一个容器能概括的。

**要求**：草案必须回答"V3 是上报型还是轮询型（还是两者都支持）"，并据此给线程模型和 IDeviceManager 定职责。不能把"每设备一线程"当放之四海皆准的默认答案。

### 攻击点 6【P1】时间戳"设备时间 vs 主机时间"没有定义，时钟漂移是数据正确性问题

草案第十三节第 1 点："数据帧带设备时间戳"。但没说：
1. 这个时间戳是**采样时刻**（设备 RTC）还是**到达时刻**（主机时钟）？
2. 设备无 RTC（大量嵌入式采集设备没有实时钟，上电从 0 或随机值开始）怎么办？
3. 设备和主机时钟漂移（RTC 每月 ±几十秒很常见）怎么办——报警时间轴、记录 CSV、回放对时会错乱。

草案第九节已有 `IClock`（可注入时钟），但那是**主机侧**测试用时钟，解决不了**设备侧**时间戳不可信的问题。

**建议**：DataPoint 的时间戳采用"来源优先级"策略——设备时间戳（采样真相时刻）优先；设备无 RTC 或时间戳非法（0 / 1970 / 未来 1 天）时回退主机到达时刻。同时记录"主机到达时刻"作为**通信延迟度量**（到达时刻 − 设备采样时刻 = 链路延迟，本身是诊断信号）。草案要显式定义这两个时刻的语义和回退规则，而不是一句"带设备时间戳"。

### 攻击点 7【P2】SEQ(4B) 的定位没有定义——"重传/去重/乱序"在 TCP 上是伪需求

草案第十三节加 SEQ，V1 审查 P2 的理由是"回放与实时无法区分"。

先戳破一个概念错误：**在 TCP 上，"重传、去重、乱序"三个词都不成立**——TCP 本身保证字节有序、可靠、不重复，应用层解出的帧天然有序无重复，不需要 SEQ 做这三件事。如果未来走 UDP（高频遥测/广播）这三者才成立，但草案从没提 UDP。

所以 SEQ 的真实价值只剩：
1. **丢帧检测**（统计通信质量，如"过去 1 分钟丢了 3 帧"）；
2. **回放时间轴挂靠**（V1 P2 的真实需求）；
3. **采样间隔抖动度量**。

这些都是"观测元数据"，不是"传输控制"。草案把 SEQ 当帧格式升级核心，却没说清它解决哪个问题、4B 是否必要（20Hz 下 2B 会 54 分钟回绕，4B 够 6.8 年——4B 其实合理，但理由要写出来，不是拍 4B）。

**结论**：SEQ 可以加，但必须明确定位为"观测元数据（丢帧率/时间轴）"，并声明"TCP 下不做重传/去重/乱序，最新值胜出"。草案若不声明，实现者会误以为要基于 SEQ 做重传机制，凭空造出 TCP 上不存在的复杂度。

### 攻击点 8【P2】错误处理只有"计数器"，没有"策略/阈值"，"错误帧"产出措辞危险

草案第十一节规则 3："禁止静默丢弃——CRC 错/解析异常必须上报（计数 + 可选日志）"；第十三节第 5 点："解析器产出错误帧"。

方向对，但两个问题：

**1. "错误帧"不能当帧产出。** CRC 错的帧，其 payload 是**不可信字节**，把它的内容交给上层（哪怕标了 isValid=false）都是危险的——上层任何"顺手用一下 payload"都是安全漏洞。V2 的 `ProtocolFrame.isValid` 字段（`protocoltypes.h:75`）本身就是"为语义完整而留"的半吊子设计，V3 不要再保留"带内容的坏帧"。正确做法：解析器产出的是**错误事件**（错误类型 + 计数字段 + 位置），不是"错误帧内容"。

**2. 缺降级阈值策略。** 工业现场的健壮性标准动作是：
- **CRC 错**：丢弃 + 计数，**不重发**——采集是周期连续流，丢一帧下一秒又来，最新值胜出，重发无意义。这条 V2 的 FrameParser 已经做对（`frameparser.cpp:153-154` 丢弃继续重同步）。
- **非法帧**（LEN>1024 / 未知 FUNC/CMD）：丢弃 + 计数 + 告警，**不立即断开**——单次脏数据/噪声断开重连只会放大问题（重连风暴）。
- **断开时机**：**连续 N 个错误 或 持续 T 秒无有效帧 → 才断开重连**。单次错误不断开。

草案只有"错误计数器 + 上报"，没有"计数器达到什么阈值触发什么动作"。计数器是死的，没有策略。而且要区分错误**是否致命**（CRC 错=瞬态可丢弃；非法帧风暴=链路/协议坏=致命），ErrorCode 枚举只有一维（第十一节），缺"致命性/可重试性"维度。

## 四、verdict

**方向正确，但"协议层"这半边的规格严重不足，不能直接进入编码。**

草案把最难、最该在架构阶段敲定的三件事留成了空白：
1. **帧格式升级的兼容性契约**（版本号 / 完整新帧布局 / CRC 新覆盖范围）——P0；
2. **半开连接与接收超时的具体落点**（V2 已示范"建模不接线"，V3 不许第三次）——P0；
3. **传输模型定位**（上报型 vs 轮询型）——P1。

这三件不定，IDevicePort、线程模型、SEQ、错误策略全是空中楼阁。
