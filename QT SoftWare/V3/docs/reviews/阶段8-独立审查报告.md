## 3. 发现的缺陷清单（按严重程度排序）

### 缺陷 #1【中】连接退避函数存在有符号左移未定义行为（UB）

- **位置**：`src/domain/connectionstate.cpp:62`
  ```cpp
  qint64 delay = static_cast<qint64>(1000) << attempt;   // attempt 无上界
  ```
- **失败场景**：`attempt >= 54` 时 `1000 << attempt` 溢出 `qint64` 符号位（UB）；`attempt >= 64` 时移位位数越界（UB）。采集端在设备长期故障下 `m_retryCount` 无限递增（每次退避 30s），约 27 分钟即可逼近 54 次重试。
- **为什么单测没抓住**：`tst_v3_unit.cpp:226` 的 `nextRetryDelayMs(100)` 断言 30000 之所以"绿"，是因为 x86 `shl` 指令把移位位数**按 6 位掩码**（`100 & 63 = 36`），UB 被硬件行为掩盖——这是"测试绿但测的是 UB"的典型例子。
- **建议**：移位前钳制：`if (attempt >= 31) return kMaxDelayMs;`（或改用 `1LL << min(attempt, 31)` 再乘），并把 `attempt >= 54/64` 纳入单测边界。

### 缺陷 #2【中】`infra/config` 缺失 + host/port 硬编码（违反 v1 规格）

- **位置**：v1 §1 目录结构列 `infra/config.h/.cpp`（QSettings 读 host/port）；v1 §3/§13 要求"连接入口参数读 infra::config"；`src/ui/mainwindow.cpp:93,102` 硬编码 `"127.0.0.1"` 与 `45678`。
- **失败场景**：实际 `src/infra/` 只有 `logger.h/.cpp`，无 config。host/port 是硬编码魔法数，且默认端口 45678 在 MainWindow 与 simulator `kDefaultPort` 两处重复（无单一来源）；用户无法持久化连接配置。
- **建议**：补 `infra/config.h/.cpp`（`QSettings` 读 host/port，构造注入非单例），或至少把默认 host/port 收敛为单一具名常量。

### 缺陷 #3【中】`onReceiveTimeout` 依赖 `abort()` 隐式触发 `disconnected` 才走重连

- **位置**：`src/acquisition/acquisitionworker.cpp:318-325`
- **失败场景**：`onReceiveTimeout` 发完 `ReceiveTimeout` 后只调 `m_socket->abort()`，**未显式调用 `handleDisconnection()`**；它依赖"Connected 状态下 abort 同步触发 disconnected → handleDisconnection"。若 socket 在定时器触发与 abort 之间已异常变为 UnconnectedState（对端刚关闭的竞态窗口），abort 不再发 disconnected，则 worker 会**卡在 Connected 状态、无定时器、永不重连**。
- **对比**：同文件 `onConnectTimeout`（:308-316）在 abort 后**显式调用了 `handleDisconnection()`**，二者不对称。
- **建议**：`onReceiveTimeout` 在 `abort()` 后补 `handleDisconnection();`（`m_reconnectScheduled` 守卫已保证幂等，不会双重重连）。

### 缺陷 #4【低】关停五件套第 5 件（wait 超时兜底）未实现

- **位置**：`src/app/main.cpp:151` `workerThread.wait();`（无超时参数）；集成测试 `tst_v3_integration.cpp:101,146` 同样裸 `wait()`。
- **失败场景**：v1 §7 关停协议明确"`wait()` 超时不析构共享资源"。当前若采集线程因未知原因不退出，主线程在退出时**无限阻塞**。
- **建议**：改 `workerThread.wait(3000)`，超时后 `m_socket->abort()` + 再 `wait()`，仍失败则记录日志告警后放弃（泄漏线程但不崩）。

### 缺陷 #5【低】`ErrorCode::InvalidFrame / Ok` 为死枚举 + 错误码映射不精确

- **位置**：`src/domain/errorcode.h:31,37`（`Ok`、`InvalidFrame` 定义后从未被 emit）；`src/acquisition/acquisitionworker.cpp:482-485`（`FrameError::InvalidHeader` 映射为 `ErrorCode::ParseError` 而非语义更准的 `ErrorCode::InvalidFrame`）。
- **失败场景**：错误码分类表里有两个值永远不产出，`InvalidFrame` 语义（非法帧头）被 `ParseError` 混用，削弱了上层"按错误类别降级"的语义清晰度（第一阶段虽未做致命性维度，但分类正确性仍是后续演进的地基）。
- **建议**：`handleFrameError` 的 `InvalidHeader` 分支改 emit `ErrorCode::InvalidFrame`；或从枚举中删除 `InvalidFrame`/`Ok`（保留 `Ok` 亦可，但需明确其为占位语义）。

### 缺陷 #6【低】`dscope_ui` 传递链接 `Qt5::Network`，且 ui→acquisition 链接未被实际使用

- **位置**：`CMakeLists.txt:116`（acquisition 以 `PUBLIC` 链接 `Qt5::Network`）→ `:131`（ui PUBLIC 链 acquisition）。
- **失败场景**：`docs/03 §2` 白名单禁 `dscope_ui` 带 Network；但因 acquisition 把 Network 设为 PUBLIC，ui 传递获得了 Qt5::Network。同时 MainWindow 对 worker 用前向声明 + 字符串 `invokeMethod/SIGNAL-SLOT`（mainwindow.h:35, mainwindow.cpp:58-79），**从未 include acquisition 头**，ui→acquisition 链接实质未消费。
- **建议**：把 `dscope_acquisition` 的 `Qt5::Network` 改为 `PRIVATE`，并在 main.cpp/tst_v3_integration 显式补 `Qt5::Network`；或把 ui→acquisition 的链接改为 `PRIVATE`（避免传递）。这是依赖方向卫生问题，非运行 bug。

### 缺陷 #7【低】教学注释（"WPF 对照"）遍布生产源码，违反编码规则 §2

- **位置**：34 处"WPF 对照/↔ C#"注释分布 23 个生产文件（如 `src/domain/datapoint.h:22`、`src/acquisition/acquisitionworker.h:30`、`src/protocol/frametypes.h:19`、`src/ui/theme.h:18` 等）。
- **失败场景**：`docs/05 §2`、`docs/09 §5` 明确"禁止教学式注释进生产源码，迁移对照注释一律进 docs/learn/"；但 `docs/learn/` 目录**不存在**，教学注释却直接写在生产源码里。这与用户 CLAUDE.md/MEMORY 的"WPF 背景学 Qt、讲解用 WPF 锚点"学习目标**存在真实张力**。
- **建议**：二选一并落文档——(a) 保留教学注释、同步修改 docs/05 §2/docs/09 §5 声明"本学习项目允许生产源码含 WPF 对照注释"；(b) 把对照注释迁到 `docs/learn/`。当前状态是"规则与实现矛盾"。

### 缺陷 #8【发布风险】整个 V3 源码树尚未纳入 git 版本控制
