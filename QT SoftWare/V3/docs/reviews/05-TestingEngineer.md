## 零、审查结论先行

草案对 V2 测试失败的**病理诊断是对的**（凑数测试、分层虚设、固定等待 flaky），但**开出的药方大部分是"换标签 + 换类型"，而不是"换强制手段"**。V2 测试失败的根本原因不是"没画四层表"，也不是"没用 gtest / Result<T> / fake"，而是：**没有任何机械手段强制"测试必须证明行为"**。草案第十五节给了一张更漂亮的四层表，却依然没给出任何可机械验证的边界判据和门禁。**只要门禁缺失，V3 的四层表会以"名字不同、内容相同"的方式，精确复刻 V2 的 163 用例悲剧。**

## 一、同意点（简要，不展开）

1. **保留 FaultInjector / SimulatorDevice / `start(0)` 随机端口作为测试基础设施**——这是 V2 唯一被实践验证的"测试即基础设施"资产，`tst_integration.cpp` 已经用得很好。
2. **禁止 `qWait(固定毫秒)` 与裸 `sleep` 的方向正确**——V2 实测残留 `QTest::qWait(300)`（`tst_dataservice.cpp:195`）、`qWait(1200)`（`tst_simulatordevice.cpp:192`）、`sleep 1.5`（`smoke.sh:24`），这些确实是 flaky 与慢测试的来源。
3. **"失败场景必须有测试"（断线重连/超时/CRC/非法帧/线程退出时序）是工业软件的生命线**——V2 恰恰缺"线程退出时序"和"超时"的确定性测试，这是真实缺口。
4. **"每个领域不变量必须有对应测试，不为凑数写 getter/setter 测试"**——直接命中 V2 的 `tst_signalslotdemo.cpp`（整个文件在测要删除的教学对象 `SignalSlotDemo`）。
5. **错误分类（`ErrorCode` 替代裸 `QString`）提升断言能力**——`connectionError(QString)` 让测试只能断言"非空字符串"，分类后才能按类别断言，方向正确。
6. **"测试独立于开发 Agent"原则保留正确**。

## 二、攻击点（主体）

### 攻击点 1（P0）：「四层分层」没有机械边界判据，必然重演"名字不同、内容相同"

**草案主张**：第十五节给出 Unit/Component/Integration/E2E 四层表，每层有"测什么/工具/边界"三栏。

**证据——V2 为什么失败**：
- V2 同样宣称"四层测试体系"（见草案第一节第 8 条、第十五节自述），但 smoke/integration 目录**曾经是空的**，21 个套件里混进 `tst_signalslotdemo.cpp` 这种"测教学对象"的凑数测试。
- 关键观察：V2 的每个测试文件**文件头注释都在宣称自己的分层归属**（"这是 Integration 层"、"这是 Unit 层"），分层靠**注释自证**，没有任何工具能验证"这个测试真的在测它声称的那一层"。`tst_dataservice.cpp` 声明自己是"单元测试"，但它 `#include <QTcpServer>` 起真 socket——按草案新定义它其实是 Component 层。**V2 的分层不是没人画，是画了没人执行。**

**反驳**：
- 草案第六节对**生产代码**的模块边界给了编译期强制（CMake target 依赖白名单，"domain 不 include Qt"可以被链接关系机械验证），但对**测试代码**的四层边界，第十五节只给了断言式表格，没有给出对应强制手段：
  - **Unit 层禁止链接 `QtNetwork`/`QtWidgets`**——没有对应的 CMake target 白名单或 lint 规则，测试照样能 `#include <QTcpServer>` 混进 I/O；
  - **Component/Integration/E2E 的差异**只差一个"SimulatorDevice 是内嵌还是独立进程"，边界是模糊的——草案的 Integration 层定义（"应用层用例 + 真实模拟器，随机端口"）与 V2 的 `tst_integration.cpp` **几乎逐字相同**。也就是说，草案把 V2 已经做对的那一个测试，重新贴了个标签，然后声称是 V3 的"重新定义分层"。这不是重新定义，是**把 V2 唯一做对的部分抄了一遍**。
- 四层表里"工具"栏写"GoogleTest 或 QtTest"、"脚本 + 协议探针"，这种"或"字表述等于**没有选型**——Unit 层允许 gtest 也允许 QtTest，意味着一个团队可以同时产出两套断言风格，`QFETCH`/`_data`（`tst_protocol.cpp` 已在用）与 gtest 的 `TEST_P` 并存，这正是"名字不同、内容相同"的温床。

**修正建议（必须写进 V3 正式规格）**：
1. 给每一层一个**可机械验证的判据**，而非描述性文字：
   - Unit：CMake target 只链接 `dscope_domain` + `dscope_protocol`，**白名单禁止 QtNetwork/QtWidgets/QtSql**，用 `cmake` 的 `LINK_LIBRARIES` 或一个 lint 脚本在构建期检查；
   - Component：允许链接单个 Adapter target，但被测对象只能有一个 `dscope_infra_*`；
   - Integration：必须链接 `dscope_simulator`（真实 socket 内嵌），禁止链接任何 fake/替身；
   - E2E：测试体必须是**独立进程启动**（`Start-Process`/`fork+exec`），进程边界由脚本断言。
2. 统一断言框架选型：**纯逻辑（domain/protocol）用 gtest，含 Qt 信号/事件循环的用 QtTest，二选一，不许"或"**。

### 攻击点 2（P0）：「DoD / 门禁 / 失败即阻塞」在本机无 CI 的现实下是空话

**草案主张**：第十五节列了测试规则，第二十节第 1 条"CI 自动化——一键构建 + 测试 + 打包"；攻击目标第 7 条自认"本机开发、无远程 CI 服务器"。

**反驳**：
- **"失败即阻塞"阻塞的是谁？** 没有 CI 服务器，就没有"提交 → 自动跑 → 红了拦下来"这个阻塞点。V2 已经证明：163 用例"真实运行全绿"（草案第一节第 8 条承认），但仍然混进凑数测试、smoke 曾为空。原因不是"测试没跑"，是**跑绿这件事靠人手工执行一次，不构成任何强制**。V3 若还是"本机手工 ctest 一下"，那么"失败即阻塞"没有任何载体。
- **草案的 DoD 没有"怎样算通过"的可执行判据**。清单是定性愿望（"失败场景必须有测试"、"不为凑数写测试"），但一个测试怎样才算"通过"、怎样才算"证明行为"、怎样才算"不是凑数"，没有一条量化。可执行的 DoD 应该是：
  - `ctest --output-on-failure` 退出码 0；
  - 每个失败场景（CRC/超时/重连/非法帧/线程退出）至少有一条**断言了 ErrorCode 或状态转移**的用例，而非"不崩"；
  - **变异冒烟**：删掉被测代码的一行关键逻辑，对应测试必须转红——这是防"测了等于没测"（`tst_signalslotdemo` 即使删掉 `SignalSlotDemo` 生产代码，只要测试文件一起删，照样"全绿"）的唯一硬判据；
  - Unit+Component 全绿时间预算 ≤ 2 分钟，Integration ≤ 1 分钟，超时即视为"测试写重了，返工"。
- **无 CI 的最务实等价物**：本地**不可跳过的单命令门禁**（如 `build_and_verify.ps1`，串起 configure + build + ctest + smoke + e2e，任一非零即整体非零），并把它写进 DoD 的"完成"定义——完成 = 这条命令返回 0，而不是"开发者记得跑了"。草案把 CI 写成"发布设计"（第二十节）而非"开发门禁"，等于把可测性的强制寄托在一个**不存在的服务器**上。

**结论**：如果 V3 不能交付一条"本地单命令、失败即非零、DoD 引用它"的门禁，那么第五节的四层表、第十一节的 Result<T>、第十五节的 fake 优先，全部是纸面设计。

### 攻击点 3（P1）：「fake 优先」缺 fake 预算，会让 Integration 退化成"单元测试马甲"

**草案主张**：第十五节规则 1"测试替身优先——用接口注入 fake，不用真实 socket/文件/时钟"，并弃用"绑定-释放法找端口"。

**证据**：
- V2 的 `tst_integration.cpp` 已经用**真实** SimulatorDevice + 真实 TcpClient + 真实随机端口，测出了真实 socket 边界（粘包重组、CRC 丢弃、配置查询往返）。它的问题**不是**"用了真实组件"，而是里面残留 `QTest::qWait(200)` 固定等待（`:118/:149/:177`）——这属于攻击点 5 的"固定等待"问题，不该归罪于"用了真实组件"。
- `tst_tcpclient.cpp:112-128` 的"绑定-释放法找空闲端口"确实是坏味道（Windows 回环 2s 才回 RST，等待放 5s），但它的正确替代品 `start(0)` 随机端口，V2 的 `tst_integration`/`tst_simulatordevice` **已经在用**了。

**反驳**：
- 草案把两件**不同的事**捆在一起说："fake 优先"（针对不该用真实 I/O 的场景：文件系统、真实时钟、数据库）和"弃用绑定-释放法"（针对端口发现）。**端口发现应该用 `start(0)`，这是 V2 已解决的问题；而 fake 优先针对的是"真实时钟/真实文件"这类慢且非确定的依赖，不是 socket 本身。**
- 更危险的：如果 Integration 层把 socket 也换成 fake，那么"集成测试"就退化成"单元测试马甲"——fake socket 不会暴露真实 TCP 的粘包/半包/断连时序，而这些**恰恰是 Integration 层存在的唯一理由**。草案的 Component 层（"单个 Adapter 面对模拟 socket"）已经覆盖了"半真实"边界，Integration 层若再 fake，两层重复且都测不到真边界。
- 草案缺一条**fake 预算（每层 fake 到哪）**的梯度规则。没有它，"fake 优先"会被执行成"所有层都 fake"，精确复刻 V2 的"名字不同内容相同"。

**修正建议**：写死每层的 fake 预算——
- Unit：全 fake（含 IClock，见攻击点 5）；
- Component：I/O 用真实 QtNetwork 回环 + 设备侧用真实 `SimulatorDevice` 或最小 fake，**但时钟必须 fake**；
- Integration：socket 全真实，SimulatorDevice 真实内嵌，**禁止 mock socket**；
- E2E：双进程全真实。
把"Integration 禁止 mock socket"写成一条**负面清单红线**，与"domain 不 include Qt"同等地位。

### 攻击点 4（P1）：`Result<T>` 不能根治"假装成功"，且引入"错误态取垃圾值"新陷阱

**草案主张**：第十一节规则 1"跨模块边界只返回 `Result<T>` 或 `ErrorCode`，不返回裸 bool 假装成功"，声称"错误不可忽略、可断言"。

**证据——草案自己承认**：第二节第 8 条、攻击目标第 5 条都承认 V2 的"假装成功"（`loadReplay` 返回 true 但 0 帧）根源是**设计惰性**，不是缺 `Result<T>`。

**反驳**：
1. **C++ 没有强制解包**。`Result<T>::ok()` 调用与否是**可选的**，`Result<T> r = loadReplay(...); if (r.ok()) {...}` 里的 `if` 可以省略。草案的 `Result` 设计没有 `[[nodiscard]]`、没有"未消费错误即编译告警/错误"的约束，那么"失败但假装成功"完全可以变成"失败但没人调用 `ok()`"。**`Result<T>` 把错误从 bool 换成 ErrorCode，换的是表达，不是纪律。**
2. **`value` 在错误态的可访问性契约缺失**。草案的 `Result` 里 `T value` 是普通成员，若 `ok()==false` 时 value 是默认构造的，偷懒调用方可以 `auto x = r.value()` 根本不看 `ok()`，拿到一个**垃圾默认值**继续跑。这比 V2 的 bool 更隐蔽——bool 至少暗示"你需要判断"，而 `value` 看起来"直接能用"。草案没说"错误态禁止取 value"（应通过 `assert`/异常/`std::optional` 强制），这是 `Result<T>` 引入的**新陷阱**。
3. 真正根治"假装成功"的是**测试纪律**，不是类型：第十五节规则 4"失败场景必须有测试"才是关键，但它是纪律，需要攻击点 2 的门禁去强制。草案把希望寄托在 `Result<T>` 上，会把读者误导成"换了类型就安全了"，从而放松对"失败路径必须有断言 ErrorCode 的测试"的要求。

**修正建议**：`Result<T>` 必须附带三条硬约束写进规格——(a) `[[nodiscard]]` 标注；(b) `ok()==false` 时取 `value` 是未定义行为/触发断言，错误态用 `std::optional<T>` 或异常表达；(c) DoD 增加一条"每个失败路径至少一条断言 `ErrorCode != Ok` 的测试 + 每个 `Result` 调用点必须显式处理错误（代码审查项）"。否则 V3 只是把"返回 true 假装成功"换成"返回 `Result{Ok, 0帧}` 假装成功"。

### 攻击点 5（P1）：「domain 零 Qt 便于测试」因果倒置，可测性主要靠依赖注入而非去 Qt

**草案主张**：第五.1 节"domain 零 Qt 依赖……真正可测（无需 Qt 事件循环）"；第十五节"纯逻辑无 Qt 时用 gtest"。

**证据——V2 的 domain 不变量测试已经能干净地测**：
- `tst_alarmengine.cpp` 全程**无 I/O、无线程、无事件循环**，`engine.evaluate(makePoint(...))` 是纯同步调用 + `QCOMPARE`，干净地测了报警状态机的触发去重/恢复/通道过滤/坏数据跳过/重触发。这个测试用 QtTest 已经够好，**"domain 依赖 QString/QDateTime"没有构成任何测试障碍**。
- 真正杀测试的是**单例**（草案第二节第 6 条自己承认 LogManager/ConfigManager 单例"不可注入、不可替换、不可并行测试"）。它们的不可测源于单例，**不是**源于用了 QString。`tst_alarmengine` 能测是因为 AlarmEngine 是独立类、数据点通过参数传入，**不是因为数据点不用 QString**。

**反驳**：
1. **可测性的因果倒置**。草案把"去 Qt"当作可测性的首要理由（"真正可测"），但证据显示可测性 = **依赖注入 + 测试替身**，去 Qt 只是手段之一。把可测性系在"去 Qt"上，会让人误以为"去了 Qt 就自动可测"，从而放松对 DI 的要求——而 DI 才是根治单例问题的药。
2. **"可用 gtest"的边际收益被高估**。QtTest 的 `QFETCH`/`_data`（`tst_protocol.cpp:71-114` 的 `roundTrip_data`）已经覆盖数据驱动，`QTRY_*` 覆盖异步。换 gtest 的收益主要是断言风格与生态，不是"可测性"本身，而成本是：domain↔Adapter 边界要新增 `std::string↔QString`、`std::chrono↔QDateTime` 的转换胶水，每个转换点都是新的 bug 源和测试负担（草案攻击目标第 1 条自己列为"转换成本是否值得"）。
3. domain 零 Qt 的**真实**收益是别的：依赖方向编译期强制、Linux 可移植、协议层可被模拟器/测试直接消费（草案第七节规则 2、第十三条）。**这些是架构理由，不是可测性理由**。草案把可测性列为第一理由，是理由错配。

**结论**：接受 domain 零 Qt（架构上合理），但请把可测性归因于"依赖注入 + 测试替身"，并在规格里**单独写一条 DI 纪律**（单例禁止、构造函数注入、端口接口），而不是把可测性寄托在"去 Qt"上。

### 攻击点 6（P1）：线程/生命周期测试的"确定性"承诺过头，QTRY_VERIFY + fake 时钟不够

**草案主张**：第十五节规则 2"禁止 qWait/裸 sleep，用 `QTRY_VERIFY_WITH_TIMEOUT` 或注入 fake 时钟"；规则 4"失败场景必须有测试（断线重连、超时、线程退出时序）"；第九节"定时器/时钟用可注入 `IClock`，测试可伪造"。

**反驳**：
1. **fake 时钟注入不到 QTimer**。重连退避（`tst_devicecontroller.cpp` 的 1s 退避）、连接超时、`SimulatorDevice` 的 frameGenerated 周期，实际都由 **QTimer + 真实系统时钟**驱动。`IClock` 只能注入 domain 的纯逻辑（如"计算 nextRetryDelay"这个纯函数），但 **QTimer 本身无法被 fake clock 驱动**——它走 Qt 事件循环 + 真实时钟。草案没说 `IClock` 如何与 QTimer 桥接，这是个**真空白**。结果：涉及 QTimer 的重连/超时测试仍只能等真实时间，`QTRY_VERIFY_WITH_TIMEOUT` 本质还是"等真实毫秒"，重连测试要等退避时间（V2 的 `autoReconnectAfterFailure` 已放 6s，`:164/:213`），测试时间线性增长。
2. **`QTRY_VERIFY` 不是确定性方案，只是 flaky 的缓释**。它消除"固定等待不够长"的 flaky，但保留"超时阈值设错"的 flaky：太短→慢机器误报，太长→测试慢且掩盖真 bug（永不满足的条件被拖满超时才失败）。更致命的是**负向时序断言**：`tst_dataservice.cpp:195-197` 的 `stopAcquisition` 后"计数不变"、`tst_integration.cpp:180` 的 CRC 坏帧"收到 0 帧"，本质是"等一个窗口然后赌它没发生"。**任何事件驱动宏都无法断言"永不再发生"**——QTRY_VERIFY 只能等"真"，不能等"永不发生"。草案规则 2 禁止 qWait，却没说这类负向时序断言该怎么写。
3. **线程退出时序的确定性靠设计，不靠测试**。第九节铁律 3"stop→清队列→drain→quit→wait，禁止 wait(固定毫秒)"，但 `QThread::wait()` 仍需要超时参数，`wait(3000)` 正是 V2 崩溃风险的根源（草案第三节 `dataservice.cpp` 析构）。"超时兜底 + 日志告警"仍要面对"wait 超时后线程还在跑怎么办"——此时强制析构仍崩。这个确定性不是测试技术能解决的，需要**可 join 的退出协议 + 关停状态机**这类设计保证；测试只能验证"给定设计下不崩"，不能把"不确定设计"测成"确定"。

**修正建议（分层降级，诚实划分"可确定性测"与"只能探针测"）**：
- 状态机转移、退避计算、超时判定全部抽成**纯函数/纯状态机**（`IClock` 注入），在 Unit 层用 fake clock **确定性**测（这是 gtest 该干的活）；
- QTimer 只做"每个 tick 调一次纯函数"的薄壳，**Qt 世界不做时序决策**；
- 真正的 socket 断连/线程退出留在 Integration/E2E，**明确接受**"QTRY_VERIFY + 宽松超时 + 失败重试一次"的非完全确定性，并如实标注这些是"探针"而非"证明"。
草案缺这一步"哪些能确定性测、哪些只能探针测"的诚实划分，把所有时序问题都塞进"QTRY_VERIFY + fake 时钟"一句带过，是过度承诺。

## 三、按严重度排序的攻击点汇总

| 严重度 | 编号 | 一句话 |
|--------|------|--------|
| **P0** | 攻击点 1 | 四层测试分层是断言式表格，无 CMake 链接白名单/头文件白名单/时间预算等机械边界判据，必然重演"名字不同、内容相同"。 |
| **P0** | 攻击点 2 | DoD 无"怎样算通过"的可执行判据；本机无 CI 时"失败即阻塞"没有阻塞点，缺一条"本地单命令、失败即非零"的门禁。 |
| **P1** | 攻击点 3 | "fake 优先"缺 fake 预算梯度，Integration 若也 fake socket 就退化成单元测试马甲，测不到真 TCP 边界。 |
| **P1** | 攻击点 4 | `Result<T>` 不根治"假装成功"（C++ 无强制解包、`ok()` 可忽略），且 `value` 错误态可取垃圾值是新陷阱。 |
| **P1** | 攻击点 5 | "domain 零 Qt 便于测试"因果倒置——`tst_alarmengine` 证明可测性靠依赖注入而非去 Qt，去 Qt 的真实收益是架构而非可测性。 |
| **P1** | 攻击点 6 | 线程/生命周期测试确定性承诺过头：fake 时钟注入不到 QTimer，QTRY_VERIFY 是 flaky 缓释，负向时序断言本质是赌窗口。 |

## 四、Verdict

**草案对 V2 的病根诊断正确，但药方是"换标签 + 换类型"，不是"换强制手段"。** 测试分层的四层表、`Result<T>`、fake 优先、gtest 选型，这些单独看都不错，但它们**没有一个能防止"为凑指标写测试"重演**——因为 V2 失败的根因是"没有任何机械手段强制测试必须证明行为、失败必须阻塞"，而草案恰恰在这一点上依然只给定性愿望，没给可机械验证的判据和门禁。

**有条件通过（条件 = 补三样东西）**：
1. **每层一个机械边界判据 + 统一断言框架选型**（攻击点 1）；
2. **一条本地单命令门禁（失败即非零）+ 可执行 DoD（含变异冒烟、时间预算、失败路径断言 ErrorCode）**（攻击点 2/4）；
3. **fake 预算梯度 + 线程时序测试的"确定性/探针"诚实划分**（攻击点 3/6）。

补齐这三样，V3 测试架构才是真正"重新定义"；不补，第十五节就是 V2 的四层表换了一行"工具"栏的文字，163 用例的悲剧会以 200 用例的方式再来一次。
