## 二、攻击点（主体）

### 攻击 1：每设备一个 I/O 线程，是在错误的地方用线程

草案第九节表格与第二十节都写死"每设备一个 I/O 线程"，第二十节甚至把"多设备 = `QVector<IDevicePort>`，每设备一线程"当作扩展路线的**结论**。这是本次审查最该被推翻的假设。

**事实 1：Qt 的 socket 是事件驱动、非阻塞的。**
`tcpclient.cpp:101-112` 的 `onReadyRead` 就是证据：`readAll()` 立即返回，从不阻塞；真正驱动它的是 `QTcpSocket::readyRead` 信号，底层是内核 `select/epoll/WSAPoll` 多路复用。也就是说，**一个事件循环线程天然能服务几十上百个 socket**——`QAbstractSocket` 的 notifier 只在"有数据/可写/出错"时才被唤醒，空闲 socket 不消耗任何 CPU 时间片。

**事实 2：这个场景的数据量根本不需要并发。**
草案自己的量级是"20Hz × 4 通道"。即每设备 80 DataPoint/s。100 台设备 = 8000 DataPoint/s。一个 `float` 解析 + 一次队列入队，每个点不到 1 微秒，8000 点/s 约 8ms CPU/秒，**单线程绰绰有余，甚至到 1000 台都够**。草案用"每设备一线程"去解决一个不存在的 CPU 瓶颈。

**事实 3：每设备一线程的真实成本不是 CPU，而是资源与管理。**
- **栈内存**：每线程预留栈空间（Linux pthread 默认 8MB 虚拟内存，Windows 默认 1MB）。100 设备在 Linux 上 = 800MB 虚拟地址预留。虽然物理内存按需提交，但虚拟地址空间、线程 TCB、内核栈、每个线程的 `QEventDispatcher` + 定时器 + notifier 对象，都是 ×N 的常驻开销。
- **生命周期复杂度**：V2 的关停已经是"最脆弱的代码"（`dataservice.cpp` 析构），草案把"每设备一线程"写死后，等于把 V2 最脆弱的这段代码**复制 N 份**。每台设备的连接/断线/重连/关停/异常，都要各自管理一个线程的生死。
- **跨设备聚合**：第二十节未来要做"数据分析（AnalysisSink）"，多设备数据要聚合计算。数据散在 N 个线程里，聚合点就成了 N 个生产者汇入一个消费者的复杂拓扑，比"一个 I/O 线程内所有 socket 的数据天然有序"难得多。

**唯一的辩护点是"故障隔离"**：一个设备的解析卡死不会拖累别的设备。但——解析是纯 CPU 的非阻塞操作（`acquisitionworker.cpp:97` 的 `handleFrame`），**如果它卡死，那本身就是 bug，应该修 bug 而不是靠线程隔离来兜底**。用线程隔离去掩盖阻塞，是治标。

**结论与修正方向**：
- 把"每设备一个 I/O 线程"改为 **"一个（或固定 N 个分片）I/O 事件循环线程，承载所有设备的 socket"**。N 不随设备数增长，取 1（小规模）或固定小常数 2~4（按 CPU 核数分片）。
- 设备与线程的归属由**连接分片器**决定（如按 deviceId 哈希分配到固定线程），而不是"一设备一线程"。
- 若未来出现真正的 CPU 密集解析（如 1kHz 振动 × 100 设备的 FFT 类分析），再加**解析工作线程池（N:M 模型）**，与 I/O 线程解耦。但那是"分析阶段"的事，不该现在写死进 I/O 层。

> **攻击靶心**：草案把"线程"当作"隔离单元"而不是"并发单元"，在一个数据量极小、且 Qt 原生支持多路复用的场景里，选择了最贵的方案，并把错误的方案写进了扩展路线（第二十节），后续要推翻代价极高。

### 攻击 2：有界队列 + 背压的具体机制全部缺失，且与报警引擎自相矛盾

草案第十八节只有一句"消费慢时丢弃旧数据而非无限堆积"。这句话留了五个未定义的空洞，每一个都会在实现时变成 bug：

**空洞 1：队列容量多大？**
没有数量级。需要给出公式，否则实现者随意填。建议基准：`capacity = dataRate × maxAllowedLatency`。以 20Hz×4 通道=80 point/s 为例，允许 2 秒延迟则容量 = 160 点（或按"批"计，40 批 × 4 点）。容量不是拍脑袋，是"允许的最大陈旧度"的产品决策，草案必须把它变成一个显式参数。

**空洞 2：满了丢旧还是丢新？**
草案说"丢旧"（drop-oldest）。这对**监控渲染**是合理的——曲线/仪表只关心最新值，丢旧等价于压缩历史。但 drop-oldest 需要 `std::deque` 或环形缓冲的头部删除，草案没确认实现结构。而且"丢旧"与"丢新"是两种截然不同的语义：丢新（drop-newest）保留历史连续性但最新值缺失；丢旧保留最新值但挖历史洞。草案只拍板"丢旧"，没论证为什么。

**空洞 3：丢了要不要通知 UI 有数据缺口？**
没提。这是**必须**的。丢帧后曲线会出现跳变/空洞，用户无法区分"设备没发"还是"我丢了"。需要一个 `droppedFrames` 计数器 + `dataGapDetected` 信号，UI 在曲线上标缺口或显示"数据降级"徽标。否则丢帧是静默的，用户会误判设备故障。这与草案第十一节第 3 条"禁止静默丢弃"（CRC 错必须上报）是同一原则，但草案自己没把这条原则应用到"背压丢帧"上。

**空洞 4：丢帧对报警引擎的影响（最严重）。**
报警引擎需要**连续数据**判断趋势——"连续 N 点超阈"、"斜率上升"、"突变检测"都依赖相邻点的连续性。drop-oldest 会在数据序列里挖洞，趋势判断会被打断或误判。而草案第八节的数据流图里，`AlarmEngine` 是 `Application` 层之后、与 `DataBus` **并列**的分支，暗示报警消费"完整流"；但第九节又说所有数据走 `IDataBus` 有界队列（会丢帧）。**两处自相矛盾**。
**正确的做法**：报警引擎必须挂在**丢帧之前**的完整流上——即在采集线程内、数据入有界队列**之前**就同步完成报警评估（草案第八节图也写了"同帧触发"，方向对但位置错）。渲染可以容忍丢帧，报警不能。这条必须写进架构，否则报警系统从设计第一天起就是漏报/误报的。

**空洞 5：背压会不会反过来阻塞采集线程？**
没说。如果队列满了采集线程 `push` 时**阻塞等待**，后果是：`readyRead` 不再被处理 → TCP 接收缓冲区积压 → 对端窗口停止 → 数据积压在对端工业设备（设备内存有限，可能溢出/死机）。这是比丢帧更糟的故障。
**必须明确**：这里的背压是**丢弃式降级（drop）**，不是**阻塞式反压（block）**。采集线程的 `push` 永远非阻塞：满了就丢弃并计数，绝不等待。草案用"背压（backpressure）"这个词有误导性，应该改名"降级丢弃（shed load / drop-oldest）"。

> **攻击靶心**：草案把"丢旧数据"当成一个无需论证的简单决策，实际它牵动容量、语义、UI 诚实性、报警正确性、对端设备安全性五件事，且其中"报警 vs 丢帧"是 P0 级矛盾。

### 攻击 3："跨线程只传值对象（move 避免拷贝）"与"SPSC 队列"是两套互斥机制，草案没选型

草案铁律 2 说"跨线程只传值对象（move 避免拷贝）"，铁律 4 说"共享数据靠有界队列 + SPSC"，性能设计第 4 条说"跨线程传值对象用 move"。但 Qt 的跨线程机制和 move 语义是**互相打架**的：

**事实：`QueuedConnection` 是拷贝语义，不是 move。**
V2 的 `acquisitionworker.cpp:153` `emit pointsReady(points)` 跨线程投递时，Qt 通过 `QMetaCallEvent` 把参数**拷贝**进接收线程的事件队列。注意是拷贝，不是 move。唯一值得庆幸的是 `QVector<DataPoint>` 是隐式共享（implicitly shared），拷贝构造只做引用计数 +1（原子操作），**不会深拷贝每个 `DataPoint`**——`acquisitionworker.cpp:151-152` 的注释"QVector 隐式共享，拷贝便宜"是对的。所以 V2 的真实开销是：`QVector` 引用计数原子操作 + 一次 `QMetaCallEvent` 的堆分配（malloc/free）。

**矛盾：如果要用 move，就不能走 Qt 信号槽。**
`std::move` 把 `QVector` 移进队列，只适用于**自研队列**。而自研 SPSC 队列不走 `QMetaCallEvent`，也就不享受元类型系统的类型检查、`qRegisterMetaType`、`Q_DECLARE_METATYPE` 那套（草案铁律 5 还想把元类型注册集中化）。所以草案同时要求"move"+"元类型注册"+"SPSC 队列"，这三者没法同时成立，必须二选一或明确边界：

- **方案 A：继续 Qt 信号槽（QueuedConnection）**。接受 `QVector` 隐式共享浅拷贝，真实成本 = 引用计数 + `QMetaCallEvent` 分配。简单、类型安全、可被元类型系统检查。缺点：每次入队一次 malloc，高频下分配器有压力。
- **方案 B：自研 SPSC 环形队列 + move-only 槽 + 对象池**。数据包用预分配结构，采集线程填满一个槽（slot）就原子提交，消费者 `std::move` 走、处理完归还槽。稳态**零分配**。缺点：失去 Qt 信号槽的类型安全与调试便利，且要自己处理"槽归还"的生命周期。

**高频是否需要对象池/预分配？**
草案场景 20Hz×4=80 point/s，每秒 20 次 `emit`，方案 A 的分配开销完全可以忽略。但如果"更高"（草案自己写"20Hz×4通道→更高"），比如振动通道 1kHz×4=4000 point/s、且按"每帧一批"投递就是 1000 批/s，此时 1000 次/秒的 `QMetaCallEvent` malloc 会变成分配器热点。**草案性能设计第 4 条只说"move 避免深拷贝"，但没说机制、没说选型、没说是否池化，等于没设计。**

> **攻击靶心**：草案把"值对象"、"move"、"SPSC"三个概念并列写，但它们分属 Qt 信号槽（拷贝语义）与自研队列（move 语义）两套互斥传输机制。必须选型：小规模用 A，高频用 B + 对象池；不能两套都写又都不落地。

### 攻击 4：线程关停协议在"阻塞槽/优雅关闭卡死"下仍然会崩

草案铁律 3 写"`stop() → 清队列 → drain() → quit() → wait()`，禁止 `wait(固定毫秒)`"。方向比 V2 好，但有一个**根本漏洞**没被识别：

**漏洞 1：`stop()` 是 QueuedConnection 投递的，阻塞时收不到。**
`stop()` 是通过队列投递到采集线程的信号/槽（V2 的 `dataservice.cpp:144` 用 `invokeMethod(stop, QueuedConnection)`）。如果采集线程当前正在执行的槽**阻塞了**，`stop` 就永远排队，`quit()`、`wait()` 都等不到线程退出——显式协议瞬间退化成 V2 的赌超时。

有人会说"Qt 的 socket 是非阻塞的，readAll 不会卡"。对，`tcpclient.cpp:104` 的 `readAll()` 确实不阻塞。但以下场景真实存在且草案没防：
- 槽里误用 `waitForReadyRead()` / `waitForBytesWritten()` / `waitForConnected()`（这些在非 GUI 线程合法可用，但会阻塞事件循环）；
- 串口 `QSerialPort` 若走同步 wait 模式（P9 预留的 `dscope_infra_serial`）；
- 第三方同步调用（DNS 解析、文件、数据库——`dscope_infra_storage` 落盘）；
- 解析逻辑 bug 导致的死循环。

**漏洞 2：`disconnectFromHost()` 是优雅关闭，可能长时间不返回。**
V2 的 `acquisitionworker.cpp:91` `disconnectFromHost()` 在 TCP 半关闭（对端不 ACK FIN）时，`disconnected` 信号迟迟不来，`deleteLater()` 排队的对象迟迟不释放。关停时应该用 **`abort()`**（立即关闭，丢弃缓冲区，不发优雅 FIN），而不是 `disconnectFromHost()`。草案的关停协议完全没提 socket 这一层怎么配合。

**漏洞 3：`drain()` 语义未定义。**
"清队列 → drain"如果 drain 意味着"等队列里所有数据被消费完"，而消费者（主线程）恰好也忙/也阻塞，drain 就会无限等。drain 必须有 deadline（如"最多等 100ms，超时丢弃剩余"），否则关停协议自己就能死锁。

**漏洞 4：关停期间的信号风暴（V2 实锤，草案没纳入协议）。**
V2 的 `stopAcquisition()`（`dataservice.cpp:134-147`）在 `invokeMethod(stop)` 之后**同步 `emit disconnected()`**，随后 Worker 里销毁 socket 又触发一次 `disconnected` → `connectedChanged(false)` → 再 `emit disconnected()`。这就是 `dataservice.cpp` 注释里写的"disconnected 双发"。结果是：**用户主动断开 → 被 `DeviceController::onServiceDisconnected` 误判为意外断线 → 触发自动重连**（`devicecontroller.cpp:113-117`）。草案第九节的关停协议里，**完全没有"关停期间抑制 connected/disconnected/error 信号"这一条**。不加上，V3 的重连状态机会在每次主动断开时乱转一次。

**需要的配套机制（草案缺的）**：
1. `stop` 后等 Worker **主动回一个 `stopped()` 确认信号**（请求→确认握手），主线程收到确认才 `quit()+wait()`，而不是 fire-and-forget。
2. socket 关停用 `abort()`，不用 `disconnectFromHost()`。
3. 连接超时 QTimer（`connectToHost` 在 Qt 里是无限等待的，必须挂定时器）。
4. 协议层"帧超时"（多久没收到帧判定对端死亡），与 socket 超时互补。
5. `wait()` 超时兜底时，**不得继续析构共享资源**（V2 的 `delete m_mutex` 就是超时后继续析构才崩的）。超时后应 `abort() + 再 wait()`，仍失败则**泄漏该线程但记录日志告警**，符合草案第十节第 4 条"超时兜底 + 日志告警，不能静默崩溃"——但草案没把第十节第 4 条和第九节铁律 3 连成一条可执行协议。

> **攻击靶心**：草案的显式协议解决了"赌固定毫秒"，但没解决"stop 信号送达不了"（阻塞槽）和"优雅关闭卡死"（disconnectFromHost）这两个更根本的卡死源，也没把"关停期抑制信号"纳入协议。关停协议必须由"握手 + abort + 超时 + 抑制信号 + 兜底泄漏告警"五件套组成，缺一不可。

### 攻击 5：UI 30Hz 节流的三层解耦没定义，自绘控件的真正瓶颈是文字栅格化

草案第十八节第 3 条"UI 更新按帧率节流（30Hz），不是每个数据点都重绘"，把"帧率"和"数据点率"混为一谈。

**三层速率必须解耦**：
1. **采集帧率**：设备发送帧的频率（20Hz，即 50ms/帧；振动通道可能 1kHz）。
2. **数据点率**：每帧通道数 × 帧率（20Hz×4 = 80 point/s；1kHz×4 = 4000 point/s）。
3. **UI 渲染率**：30Hz（33ms/帧）。

**关键：20Hz 主场景下，数据点率（80/s）远低于 30Hz，节流根本不该触发。**
4 个通道各占一个 `LineChartWidget`，每个控件每秒才 20 个点，UI 完全可以"每点重绘"且毫无压力。只有当某通道采样率 > 30Hz（高速振动诊断）时，节流才有意义。所以"30Hz 节流"应该是**渲染层的通用护栏（渲染率上限）**，而不是针对 20Hz 主场景的优化。草案没说明触发条件，实现者可能对 20Hz 场景也套一层 30Hz 定时器，反而引入不必要的延迟和复杂度。

**自绘控件 QPainter 在 30Hz 的真实瓶颈排序**（对照 `linechartwidget.cpp`）：
1. **文字栅格化（最贵，草案完全没提）**：`paintEvent` 每次调用 `drawText` 绘制标题、5 个刻度标签、最新值。QPainter 每次重绘都重新栅格化字形，这是纯 CPU 消耗的大头。应该用 `QStaticText` 缓存，或把文字预渲染进缓存的背景 pixmap。
2. **全量路径重建**：`paintEvent` 每次都遍历 `m_data`（最多 500 点）重建 `QPainterPath` 并逐点做 `valueToY` 映射。30Hz × 500 点 × 4 控件 = 每秒 6 万次坐标映射 + 路径重建。
3. **抗锯齿滥用**：`setRenderHint(Antialiasing, true)` 对网格线、背景等所有图元生效，网格线根本不需要 AA。
4. **`removeFirst()` O(n) 抖动**：`appendPoint` 里 `while + removeFirst` 是整体移位（草案已识别，确认）。
5. **无 dirty-rect**：每次 `update()` 全量重绘，没有只重绘变化区域。

**优化分层**（草案缺具体方案）：
- 背景/网格/刻度 → 缓存为 `QPixmap` 或独立背景层，只在 resize/量程变化时重画；
- 曲线 → 只画折线层；
- 文字 → `QStaticText` 缓存；
- 节流 → 数据进环形缓冲，`QTimer` 30Hz 固定节拍驱动 `update()`，`paintEvent` 只读缓冲，而不是"每个数据点 `update()` 靠 Qt 合并重绘事件"（高频下事件循环会被重绘事件淹没）。
- 更高速（>100Hz 渲染）才考虑 `QOpenGLWidget`。

> **攻击靶心**：草案把"节流 30Hz"当成万能药，但没厘清"采集帧率/数据点率/渲染率"三层关系（20Hz 主场景根本不需要节流），也没识别自绘控件的真正瓶颈是**文字栅格化**而非"每点重绘"。性能设计第 3 条需要替换成"三层解耦 + 分层缓存 + 文字 QStaticText"。

---

### 攻击 6：SPSC 的前提被草案自己的架构图打破，且 V2 的锁本来就多余

草案铁律 4 说"共享数据不靠裸锁，靠有界队列 + SPSC"。这句话有两个问题：

**问题 1：V2 的 `lastData()` 锁其实是多余的，草案没点破，导致边界没定义。**
`dataservice.cpp:155-159` 的 `lastData()` 用 `QMutex` 保护 `m_lastData`，但**写者（`onPointsReady`，`dataservice.cpp:161`）和读者（`lastData`）都在主线程**。跨线程边界其实在 `worker → 主线程` 的 `pointsReady` 信号，已经由 `QueuedConnection` 的拷贝保证了。所以 `m_mutex` 保护的 `m_lastData` 是"同线程内的防御性锁"，根本没保护任何跨线程访问。同样 `m_connected`/`m_acquiring` 的写读也基本都在主线程。V2 的锁是**假锁**。草案说"不靠裸锁靠 SPSC 队列"直觉对，但它没点破"V2 的锁本来就多余"这个事实，于是"哪些数据真需要同步、哪些可以无锁"的边界始终没被说清。

**问题 2：SPSC 的"单读者"前提，在草案自己的数据流图里就被打破了。**
"SPSC = 单一写者 / 单一读者"。但草案第八节数据流图有**三个消费者**：
- `DeviceListModel` / `MonitorPage`（渲染）
- `AlarmEngine`（报警评估）
- 记录线程（第九节："消费 IDataBus 的快照流"）

这是**单写多读（SPMC）**，不是 SPSC。草案一边在铁律里写"SPSC"，一边在自己画的架构图里放了三个读者，自相矛盾。真实的同步需求是：

| 共享数据 | 写者线程 | 读者线程（数量） | 正确机制 |
|---|---|---|---|
| 采集数据流 | I/O 线程 | 渲染(1) + 报警(1) + 记录(1) | **SPMC**：扇出到每消费者独立有界队列；或共享环形缓冲 + 各自游标，写者以"最慢消费者"水位做背压 |
| 连接/错误状态标志 | I/O 线程 | UI + Controller（多线程读） | `std::atomic<bool>` / 状态机串行化 |
| 设备集合（多设备增删） | 主线程 | I/O 线程遍历 | 锁 或 QObject 事件串行化 |
| 配置 | 主线程 | I/O 线程读 | `shared_ptr<const T>` 不可变快照（无锁） |

草案必须产出**这样一张表**（数据名 / 写者 / 读者数量 / 同步机制 / 生命周期）。没有这张表，"SPSC 无锁"就是口号。

**SPMC 的落地建议**：不要用"三个消费者抢一个队列"（那才需要锁）。用**扇出**——采集线程把同一批数据 push 进 N 个独立的有界队列（渲染队列、报警队列、记录队列各一）。代价是 N 份浅拷贝（`QVector` 隐式共享下便宜），换来每个队列仍是严格 SPSC、全程无锁。报警队列可以设成"从不丢帧 + 更大容量"（呼应攻击 2：报警要完整流），渲染队列"允许丢旧"。

> **攻击靶心**：草案没定义"谁是写者、谁是读者、有几个读者"就断言 SPSC，而它自己的架构图里有三个消费者（SPMC）。必须补一张"共享数据清单"表，并把数据流改成"扇出到每消费者独立 SPSC 队列"，报警队列保持不丢帧。

## 三、按严重度排序

| 严重度 | 问题 | 一句话定性 |
|---|---|---|
| **P0** | 报警引擎消费"丢帧后的队列"，丢帧破坏趋势判断 | 报警正确性从设计第一天就是漏报/误报，必须把报警挂到"丢帧之前"的完整流 |
| **P1** | "每设备一线程"锁死扩展路线 | 上百设备撑不住（栈内存/调度/管理复杂度），Qt 非阻塞 socket 单线程就能多路复用，应改"固定 N 个 I/O 线程 + 所有 socket" |
| **P1** | 线程关停协议在"阻塞槽/优雅关闭卡死"下仍会崩 | `stop` 是 QueuedConnection、`disconnectFromHost` 可能卡死，需握手 + `abort()` + 超时 + 抑制关停信号 + 兜底泄漏告警五件套 |
| **P1** | SPSC 前提被架构图自破 + V2 的锁本就多余 | 三消费者是 SPMC；`lastData` 锁是假锁。需"共享数据清单"表 + 扇出每消费者独立队列 |
| **P2** | 有界队列参数全缺失 | 容量/丢旧丢新/丢帧缺口通知/背压方向（丢弃式非阻塞式）五个空洞全没定 |
| **P2** | move 与 QueuedConnection 拷贝语义互斥、无对象池方案 | 两套传输机制未选型；高频（>1000 批/s）无预分配/池化会成分配器热点 |
| **P2** | UI 30Hz 三层解耦未定义、真正瓶颈是文字栅格化 | 20Hz 主场景本不需节流；自绘控件最贵的是 `drawText` 而非"每点重绘" |

## 四、Verdict

**不否决 V3 线程模型的大方向**——事件驱动、有界队列、显式关停、去裸锁，这些都比 V2 对，方向正确。

**但三个假设必须推翻后才能作为实现依据**：

1. **"每设备一线程"推翻** → 改为"固定 N 个 I/O 事件循环线程 + 所有设备 socket 多路复用"，设备与线程由分片器归属，N 不随设备数增长；CPU 密集解析将来再加工作线程池。第二十节"多设备 = 每设备一线程"这句话必须删掉，否则扩展路线一出生就错。

2. **"SPSC 无锁"推翻** → 架构图里有三个消费者（渲染/报警/记录），是 SPMC。必须先补一张"共享数据清单"表，把数据流改成"扇出到每消费者独立 SPSC 队列"；报警队列不丢帧、渲染队列允许丢旧。同时点破"V2 的 lastData 锁是假锁"，明确哪些数据用原子、哪些用锁、哪些无锁。

3. **"丢旧数据背压"推翻** → 报警必须挂在丢帧之前的完整流上（采集线程内同步评估）。背压明确定义为"丢弃式降级、push 永不阻塞"，并补齐容量公式、丢帧计数 + 缺口通知。线程关停协议补充"握手 + socket abort() + 连接/帧超时 + 关停期抑制信号 + wait 超时后不析构共享资源"五件套。

在完成上述三条修正之前，草案第九节（线程模型）、第十八节（性能设计）**不能冻结为最终规格**，否则实现阶段会把这些 P0/P1 问题原样搬进代码——正如 V2 把"自动重连死代码"和"wait(3000) 崩溃"原样搬进了交付物。
