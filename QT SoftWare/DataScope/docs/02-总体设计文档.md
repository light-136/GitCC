# DataScope Studio 总体设计文档

- 文档编号：DS-DESIGN-02
- 适用范围：工业多通道数据采集与实时监控系统（DataScope Studio）
- 技术栈：C++17 / Qt 5.12.2（MinGW 7.3.0）/ CMake 3.25 / Ninja
- 版本：0.1.0

## 1. 架构分层总览

DataScope Studio 采用**分层架构**，自上而下依次为 UI（界面层）→ app（应用层）→ services（服务层）→ domain / protocol（领域模型 / 协议引擎）→ infrastructure（基础设施层）→ utils（工具层）。每一层只依赖其下方各层，层与层之间通过**信号槽**或**直接调用**协作。

```
┌─────────────────────────────────────────────────────────────────────────┐
│                                UI 层（界面）                              │
│  MainWindow（主窗口：菜单/工具栏/页签/状态栏）                             │
│  ├─ MonitorPage（监控总览：4 通道卡片）    ┌─ LineChartWidget（实时曲线）  │
│  ├─ DevicePage（设备管理，占位）          ├─ GaugeWidget（仪表盘）         │
│  ├─ RecordPage（记录/回放）               └─ LedIndicator（LED 指示灯）    │
│  ├─ SettingsPage（设置，占位）                                             │
│  └─ DemoPage（信号槽演示）                                                │
├─────────────────────────────────────────────────────────────────────────┤
│                             app 层（应用）                                │
│  main.cpp（程序入口：QApplication、基础设施初始化）                        │
│  signalslotdemo（信号槽五种连接教学演示对象）                              │
├─────────────────────────────────────────────────────────────────────────┤
│                           services 层（服务）                             │
│  DeviceController（设备状态机 + 退避重连）  ← UI 的门面                    │
│  DataService（数据总线：连接/采集/快照分发）                                │
│  AcquisitionWorker（采集线程工作对象）                                     │
│  TcpClient（TCP 客户端封装）                                              │
│  RecordManager（CSV 记录 / 回放）                                         │
├───────────────────────┬─────────────────────────────────────────────────┤
│   domain 层（领域模型） │  protocol 层（协议引擎）                          │
│   Device / Channel    │  Crc16（MODBUS CRC16 查表）                       │
│   DataPoint           │  FrameBuilder（组帧器）                           │
│   DeviceStatus 枚举    │  FrameParser（流式解析器：半包/粘包/重同步）        │
│                       │  ProtocolFrame / 帧常量                           │
├───────────────────────┴─────────────────────────────────────────────────┤
│                        infrastructure 层（基础设施）                       │
│  LogManager（全局单例日志，线程安全，按天滚动）                            │
│  ConfigManager（INI 键值配置，线程安全，单例）                             │
├─────────────────────────────────────────────────────────────────────────┤
│                            utils 层（工具）                               │
│  ByteUtils（hex 互转、大小端读写）   TimeUtils（时间格式化/解析/间隔）      │
└─────────────────────────────────────────────────────────────────────────┘
```

**依赖方向约定：**

- UI 层 → app 层 → services 层：UI 只通过 services 层的语义化接口（连接、采集、记录、状态）消费能力，不感知网络/字节细节。
- services 层 → domain 层 + protocol 层：服务层组合协议引擎与领域模型完成业务动作（组帧、解析、帧→DataPoint 转换）。
- domain 层只依赖 QtCore（纯数据模型，零业务）；protocol 层只依赖 QtCore（纯字节处理）。
- infrastructure / utils 为全工程地基，任何模块可依赖，但自身不依赖上层。

## 2. 模块划分与职责

CMake 以**静态库**方式组织各层，对应源码目录：

| 静态库 / 目标 | 对应源码 | 依赖 | 职责 |
| --- | --- | --- | --- |
| `datascope_utils` | `src/utils/`（byteutils、timeutils） | Qt5::Core | 字节/hex/大小端读写、时间格式化与解析。纯函数，无状态。 |
| `datascope_infra` | `src/infrastructure/`（logmanager、configmanager） | Qt5::Core | 全局日志（线程安全、按天滚动）、INI 键值配置（线程安全、类型安全）。 |
| `datascope_domain` | `src/domain/models.h/cpp` | Qt5::Core | 纯数据模型：`Device`、`Channel`、`DataPoint`、`DeviceStatus`。 |
| `datascope_protocol` | `src/protocol/`（protocoltypes、crc16、framebuilder、frameparser） | Qt5::Core | 通信帧定义、CRC16 校验、组帧、流式解析（半包/粘包/错位重同步）。 |
| `datascope_services` | `src/services/`（tcpclient、acquisitionworker、dataservice、devicecontroller、recordmanager） | Qt5::Core、Qt5::Network、protocol、domain | 业务动作封装：TCP 通信、采集线程、数据总线、设备状态机、记录/回放。 |
| `DataScope`（可执行） | `src/app/`、`src/ui/`、`resources/` | 全部静态库 + Qt5::Gui、Qt5::Widgets | 程序入口、主窗口、5 个业务页面、3 个自绘控件、QSS 深色主题。 |
| `simulator`（可执行） | `src/simulator/main.cpp` | Qt5::Network、protocol | 无硬件联调时模拟采集设备：TCP 服务端，50ms 周期发 4 通道正弦波数据帧。 |
| `tst_*`（测试） | `tests/unittests/` | Qt5::Test + 对应库 | 各模块单元测试（ByteUtils/TimeUtils/LogManager/ConfigManager/Domain/Protocol/Widgets/TcpClient/DataService/DeviceController/RecordManager）。 |

**模块边界原则：**

1. **domain 不依赖 UI / 网络 / 串口**：任何界面或协议改动不波及纯数据模型。
2. **protocol 不依赖业务**：组帧/解析器只处理字节，服务层负责业务语义（帧→DataPoint）。
3. **services 是"业务动作"封装者**：向上提供语义化接口，向下依赖协议与领域模型。
4. **UI 不直接触碰网络**：数据流必须经过 DataService 数据总线。

## 3. 数据流设计

### 3.1 实时采集链路（Simulator → UI 曲线）

```
Simulator（模拟设备）
  │  QTcpServer 监听 0.0.0.0:40001
  │  每 50ms 组帧 FUNC=0x01 CMD=0x01，载荷 = 4 通道 × 4 字节 float（大端）
  ▼
QTcpSocket（TCP 字节流，可能半包/粘包）
  │  readyRead 信号
  ▼
TcpClient::onReadyRead()
  │  readAll() → m_parser.feed(chunk) → 循环 nextFrame()
  │  emit frameReceived(ProtocolFrame)        [采集线程]
  ▼
AcquisitionWorker::handleFrame(ProtocolFrame)
  │  大端 4 字节 → float，每帧 4 个 DataPoint（channelIndex 0..3）
  │  emit pointsReady(QVector<DataPoint>)      [采集线程]
  ▼
DataService::onPointsReady()                    [主线程，QueuedConnection]
  │  锁内更新 m_lastData 快照
  │  emit dataUpdated(QVector<DataPoint>)      [主线程]
  ├────────────────────────────┬─────────────────────────────┐
  ▼                            ▼                             ▼
MonitorPage::onDataUpdated()  RecordManager::appendData()   DeviceController::onDataUpdated()
  │  逐点驱动 4 通道控件：      │  记录开关开启时逐行写 CSV      │  信号透传转发
  │  chart.appendPoint()       ▼                             ▼
  │  gauge.setValue()        record_*.csv                （UI 状态显示）
  │  valueLabel 文本
  │  Led 报警变色（超限红/正常绿）
```

**关键点：**

- `FrameParser` 在采集线程内运行，一次性消化半包/粘包；`pointsReady` 通过队列连接把 `QVector<DataPoint>` **拷贝**投递回主线程。
- `DataService` 是主线程与采集线程之间的**唯一数据通道**，UI 只认 `dataUpdated` 信号。
- `m_lastData` 快照受 `QMutex` 保护，供回放/CSV 导出等只读访问。

### 3.2 记录链路（实时采集 → CSV 落盘）

```
DataService::dataUpdated(QVector<DataPoint>)
  → RecordManager::appendData(points)
      → if (m_recording && m_recordFile.isOpen())
           逐点写行：timestampMs,channelIndex,value
```

- `RecordManager` 由 `MainWindow` 创建，并连接 `DataService::dataUpdated`；`appendData` 内部用记录开关 `m_recording` 过滤，未记录时静默忽略。

### 3.3 回放链路（CSV → UI 曲线）

```
RecordPage（选择 CSV）
  → RecordManager::loadReplay(path)
      → 读文件，跳过表头，逐行解析成 DataPoint
      → 按时间戳分组为"帧"（同时间戳的全部通道），按时间戳升序排成 m_replayFrames
  → RecordManager::startReplay(intervalMs=100)
      → QTimer 每 tick 调 onReplayTick()
          → emit replayData(m_replayFrames.at(m_replayIndex))  [主线程]
          → emit progressChanged(m_replayIndex)
  ▼
MonitorPage::onDataUpdated()   ←  与实时采集共用同一入口，UI 零改动
```

**回放与实时共用数据入口**，正是"数据源可替换"设计（见 §6.3）的体现。

## 4. 线程模型

### 4.1 线程总览

| 线程 | 承载对象 | 职责 | 禁止事项 |
| --- | --- | --- | --- |
| **主线程（UI 线程）** | `QApplication` 事件循环、`MainWindow`、5 个页面、自绘控件、`DataService`、`DeviceController`、`RecordManager`、`LogManager`、`ConfigManager` | UI 渲染、用户交互、数据分发、记录/回放 | 不阻塞式收发网络；不做耗时轮询 |
| **采集线程** | `QThread`（objectName = "AcquisitionThread"）、`AcquisitionWorker`（moveToThread）、`TcpClient`、`QTcpSocket`、`FrameParser` | 连接设备、收发字节、组帧解析、帧→DataPoint 转换 | 不触碰任何 UI 对象 |

### 4.2 采集线程生命周期管理

`DataService` 构造时创建采集线程与 Worker：

1. `m_thread = new QThread(this)`，命名 "AcquisitionThread"；
2. `m_worker = new AcquisitionWorker`（parent = nullptr），`m_worker->moveToThread(m_thread)`；
3. 连接 Worker 信号 → DataService 槽（跨线程自动 `QueuedConnection`）；
4. `m_thread->start()` 启动采集线程事件循环。

析构顺序（`DataService::~DataService`）：`stopAcquisition()`（队列投递 `Worker::stop`）→ `m_thread->quit()` → `m_thread->wait(3000)`，保证"先停 Worker 再退线程"，杜绝线程在清理中途销毁。

### 4.3 跨线程通信（信号槽队列投递）

- `connectTo()` / `stopAcquisition()` 通过 `QMetaObject::invokeMethod(..., Qt::QueuedConnection)` 把请求投递到采集线程执行。
- Worker 产出数据经 `pointsReady` / `connectedChanged` / `errorOccurred` 三个信号返回主线程。
- 跨线程信号参数 `QVector<datascope::domain::DataPoint>` 必须经 `Q_DECLARE_METATYPE` + `qRegisterMetaType` 注册，否则队列投递时参数丢失（运行时警告 "Don't know how to handle..."）。注册名用**全限定名**，与 moc 规范化名保持一致。

### 4.4 线程安全铁律（Qt 强制）

1. **socket 必须在所属线程内创建**：`TcpClient` 在 `AcquisitionWorker::start()` 槽内 new（parent=this），绝不在主线程 new 后 moveToThread。
2. 共享状态（`DataService::m_lastData` / `m_connected` / `m_acquiring`）一律用 `QMutex` 保护。
3. `LogManager` / `ConfigManager` 为跨线程共享单例，内部用 `QMutex` 串行化读写；`log()` 在**锁外**广播 `messageLogged`，避免信号槽反向调用导致死锁。

## 5. 协议设计

### 5.1 帧格式

DataScope Studio 与采集设备之间采用定制的二进制通信帧（详见《通信协议帧格式契约》）：

```
| SOF(2B) | FUNC(1B) | CMD(1B) | LEN(2B 大端) | DATA(LEN) | CRC16(2B 低字节在前) |
```

| 字段 | 长度 | 说明 |
| --- | --- | --- |
| SOF | 2 字节 | 固定 `0xAA 0x55`（`kSof = 0xAA55`），用于接收端重同步 |
| FUNC | 1 字节 | 功能码：`0x01` 采集 / `0x02` 配置 / `0x03` 查询；`0x80` 表示响应帧（收到 FUNC 即回 FUNC\|0x80） |
| CMD | 1 字节 | 子命令（各功能码内部自行定义含义） |
| LEN | 2 字节 | 载荷长度，**大端序**（高字节在前） |
| DATA | LEN 字节 | 载荷，例如模拟设备采集帧为 4 通道 × 4 字节 float（大端） |
| CRC16 | 2 字节 | MODBUS CRC16，覆盖 FUNC 起到 DATA 末尾；**低字节在前**追加 |

### 5.2 关键常量与防御设计

| 常量 | 值 | 含义 |
| --- | --- | --- |
| `kSof` | `0xAA55` | 帧头 |
| `kHeaderLen` | 6 | SOF(2) + FUNC(1) + CMD(1) + LEN(2) |
| `kCrcLen` | 2 | CRC16 字段长度 |
| `kMaxPayloadLen` | 1024 | 载荷上限。解析时 LEN 声称值超过此限，**直接判定非法帧头**丢弃，防止恶意 `LEN=0xFFFF` 撑爆缓冲 |

### 5.3 组帧（FrameBuilder::build）

```
1. 写 SOF：0xAA 0x55
2. 写 FUNC / CMD 各 1 字节
3. 写 LEN：载荷长度，大端序
4. 追加 DATA
5. CRC16 覆盖 frame.mid(2)（即 FUNC+CMD+LEN+DATA），低字节在前追加
```
载荷超过 `kMaxPayloadLen` 返回空数组表示组帧失败（唯一失败信号）。

### 5.4 流式解析（FrameParser 三态状态机）

`feed()` 只追加字节；`nextFrame()` 每次尝试从缓冲头取一帧。三态循环：

```
状态 A：扫描帧头（重同步）—— 找 0xAA 0x55，找到前丢弃垃圾；
        特例：末尾残留单个 0xAA（下一帧 SOF 前半字节）予以保留。
状态 B：读帧头字段 —— 缓冲至少 6 字节；读出 LEN 后立即做越界防御：
        LEN > kMaxPayloadLen → 丢弃 6 字节头，回状态 A。
状态 C：收 DATA + 校验 CRC —— 缓冲够 6+LEN+2 字节后：
        计算 actualCrc 与帧尾 frameCrc 比对；
        一致 → 产出 isValid=true 的帧；不一致 → 整帧丢弃，回状态 A 重同步。
```

**半包/粘包处理**：由"feed 只追加 + nextFrame 只消费"自然解决。半包时返回 false 且缓冲原样保留；粘包时一次 feed 多帧，循环调用 nextFrame 逐帧取出。

### 5.5 CRC16（MODBUS，反射表驱动）

- 初始值 `0xFFFF`，多项式 `0xA001`（`0x8005` 反转）。
- 256 项查表由 `Crc16Table` 构造器一次性算好，函数局部 static 保证只初始化一次且线程安全（C++11 magic static）。
- 逐字节核心：`crc = (crc >> 8) ^ table.values[(crc ^ byte) & 0xFF]`。

## 6. 关键设计决策与理由

### 6.1 事件驱动 vs 同步等待

- **决策**：全工程采用 Qt 信号槽 + 事件循环驱动（`readyRead` 有数据才读、`QTimer` 节拍驱动、异步 `connectToHost`），**不使用**阻塞式同步收发或死循环轮询。
- **理由**：① 数据到达是"突发、不可预期"的，事件驱动天然适配采集链路，避免阻塞 UI 线程；② 多线程协作下，信号槽队列投递是 Qt 官方推荐的线程通信方式；③ 定时器驱动（模拟器 50ms 发帧、回放 100ms/帧）替代 while 死循环，不占 CPU。

### 6.2 数据源可替换（演示源 → 真实源）

- **决策**：`MonitorPage::onDataUpdated(QVector<DataPoint>)` 是监控页**唯一数据入口**；P14 阶段由内部 `QTimer` 演示正弦波驱动，P12 之后切换为 `DataService::dataUpdated` 信号驱动，`MainWindow` 中显式 `m_monitorPage->setDemoRunning(false)` 停用演示源。
- **理由**：把"数据从哪来"与"数据怎么展示"解耦。演示源与真实源都产出同一种 `QVector<DataPoint>`，监控页零改动即完成切换。该思想对应 WPF 中 View 只依赖 ViewModel 接口。

### 6.3 DeviceController 状态机 + 退避自动重连

- **决策**：`DeviceController` 持有 `DataService`，把数据总线"无状态"的信号翻译成"有状态"的设备状态机；意外断线/连接失败自动退避重连（1s→2s→4s…封顶 30s），用户主动断开则退出状态机。
- **理由**：工业上位机必须"设备离线自动恢复"。用 `m_userDisconnected` 标志区分"用户主动断开"与"意外断线"（二者都会触发 `disconnected` 信号）；重连每次都是**新建全新连接**（Worker 出错时销毁残留 `TcpClient`），避免在坏 socket 上重试。

### 6.4 协议解析下沉到 protocol 层

- **决策**：`FrameParser`/`FrameBuilder`/`Crc16` 独立成 `datascope_protocol` 静态库，`TcpClient` 只负责"读到字节就喂给解析器、取出帧就 emit"，不关心字节细节。
- **理由**：半包/粘包/重同步是链路层通病，下沉后可被主程序、模拟器、串口（P9 预留）、TCP（P11）、单测共同复用；services 层保持"业务动作"定位。

### 6.5 单例 + 线程安全的基础设施

- **决策**：`LogManager`、`ConfigManager` 均采用 Meyer's Singleton（C++11 magic static，线程安全初始化），内部用 `QMutex` 串行化读写；日志文件按天滚动、UTF-8 编码，配置用 INI（`QSettings::IniFormat`）而非注册表。
- **理由**：① 全工程共享一个日志/配置实例，避免多模块各自为政；② INI 纯文本可读、可分发、可纳入版本管理（注册表不透明、难备份）；③ QFile/QTextStream/QSettings 非线程安全，加锁是必须的。

### 6.6 跨线程数据拷贝 vs 共享

- **决策**：采集线程产出的 `QVector<DataPoint>` 通过 `QueuedConnection` **按值拷贝**投递到主线程；主线程内 `m_lastData` 快照再以 `QMutex` 保护。
- **理由**：`QVector` 是隐式共享（Copy-on-Write）容器，拷贝便宜；按值投递天然避免跨线程共享内存的数据竞争，符合 Qt 线程模型的推荐用法。

### 6.7 状态变化不重复广播

- **决策**：`DeviceController::setStatus()` 在状态未变化时直接 return，不重复 emit `statusChanged`；`LedIndicator::setState()`、`setColor()` 同样做相等性短路。
- **理由**：避免 UI 无意义刷新，减少信号风暴，提升高频率采集场景下的渲染稳定性。
