# DataScope Studio 项目概述与需求文档

> 版本：v0.1.0 ｜ 更新日期：2026-08-14 ｜ 编写人：文档 Agent（多 Agent 协作体系之 Documentation Agent）

---

## 1. 项目背景

### 1.1 项目缘起

DataScope Studio 源自用户的真实工程学习诉求：**以一款工业多通道数据采集与实时监控系统为教学载体，系统学习 C++/Qt 桌面开发**。

本项目不是玩具示例，而是一个具备完整链路（采集 → 协议解析 → 数据总线 → 实时监控 → 记录回放）的**真实工程**，覆盖 Qt 桌面开发的主要技术面：信号槽、事件循环、线程模型、网络通信、自绘控件、QSS 主题、单测、CMake 构建与部署。

### 1.2 学习者画像（WPF/C# 经验迁移）

用户具备成熟的 **WPF/C#** 桌面开发经验，对本工程的全部学习材料提出了明确要求——**每个知识点都以 WPF 概念作为锚点对照**，降低认知迁移成本：

| WPF/C# 概念 | Qt/C++ 对应 |
|---|---|
| `App.xaml` + `Main()` / `Application.Run()` | `QApplication` + `app.exec()` |
| `BackgroundWorker` / `Task.Run` | `QThread + Worker（moveToThread）` |
| event（`+=`） | signal/slot（`connect`） |
| `INotifyPropertyChanged` | Qt 信号驱动 UI 更新 |
| `TabControl` | `QTabWidget` |
| `ResourceDictionary` / 全局 Style | `.qss` 深色主题（AUTORCC 编译进资源） |
| `Properties.Settings` / app.config | `ConfigManager`（INI） |
| NLog / `TraceSource` | `LogManager`（单例日志） |
| `TcpClient` 帮助类 | `TcpClient` 封装（QTcpSocket） |
| `BitConverter` / static class | `ByteUtils` / `TimeUtils` |
| DTO / POCO / `IReadOnlyList<T>` | `Channel` / `DataPoint`（struct）+ `Device::channels()` 只读引用 |
| 测试项目（NUnit/xUnit） | Qt Test 独立测试 target + CTest |

### 1.3 教学与技术双重目标

1. **技术目标**：交付一个可运行的工业多通道数据采集与实时监控系统。
2. **教学目标**：P1~P15 增量里程碑覆盖 C++17 现代特性与 Qt 核心机制，边做工程边学语言。
3. **工程化协作目标**：全过程采用"主 Agent + 专项 Agent 并行"的 AI 工程化协作方式，让学习者同时观摩一个中型软件项目如何组织多智能体协同开发（详见《00-项目规程报告》）。

## 2. 系统目标

### 2.1 总体目标

构建一套可连接采集设备（或模拟设备）、多通道实时采集、可视化监控、数据记录与历史回放的桌面上位机软件。软件运行于 Windows，通过 TCP 与采集端通信，采用自绘控件呈现实时波形与仪表。

### 2.2 核心业务场景

1. **连接设备**：用户输入设备主机与端口，发起连接，建立采集链路。
2. **实时采集**：设备持续上报 4 通道采样数据，上位机经协议引擎解析后分发到监控页。
3. **实时监控**：监控页以"每通道一张卡片"形式展示实时曲线、仪表盘、数值与超限 LED。
4. **数据记录**：把实时采样流落盘为 CSV，供 Excel/WPS 离线分析。
5. **历史回放**：读取 CSV 记录，按时间戳逐帧重放波形。
6. **异常恢复**：设备意外断线后自动按退避策略重连，恢复数据流。

### 2.3 目标范围（含非目标）

**范围内**：
- 基于 TCP 的采集通信（TcpClient + Simulator 模拟设备）。
- 多线程采集数据总线（DataService + AcquisitionWorker）。
- 4 通道实时曲线 / 仪表盘 / LED 自绘控件。
- CSV 记录与定时回放。
- 日志与 INI 配置基础设施。
- 深色工业主题（QSS）。

**范围外（当前阶段不作为验收目标）**：
- 串口（QSerialPort）采集链路（P9 规划，工程以 TCP 落地，串口模块预留）。
- 通道/设备的动态编辑 UI 与持久化配置界面（`SettingsPage`/`DevicePage` 当前以框架与演示为主）。
- 报表生成、数据库存储、Web 前端。
- 多设备并发采集（当前为单设备 4 通道模型）。
- 跨平台打包发布（当前以 Windows + windeployqt 为验收环境）。

> 以上非目标均基于工程当前快照（v0.1.0）的实际情况描述，不虚构已实现功能。

| 编号 | 需求 | 实现位置 |

```text
| SOF(2B) | FUNC(1B) | CMD(1B) | LEN(2B 大端) | DATA(LEN) | CRC16(2B 低字节在前) |
  0xAA55     功能码     子命令      载荷长度      载荷数据      CRC16 校验
```

## 4. 非功能需求

### 4.1 稳定性

- **线程安全**：所有跨线程共享数据（日志文件、配置存储、最新快照）一律 `QMutex` 保护；跨线程通信一律信号槽（QueuedConnection）。
- **生命周期托管**：QObject 对象树托管 socket/timer；采集线程析构 `quit + wait` 安全退出。
- **异常恢复**：设备离线走退避自动重连（封顶 30s，避免重连风暴）。
- **防御性协议解析**：载荷长度上限 `kMaxPayloadLen = 1024`，LEN 字段超限直接判非法帧，防止缓冲区被撑爆。
- **错误统一字符串化**：底层 SocketError 枚举统一转业务字符串，UI 不感知底层细节。

### 4.2 模块化

- **静态库分层**：utils / infra / domain / protocol / services 五个静态库，依赖方向严格单向。
- **库级复用**：主程序与单测共享库，一个库多个消费者。
- **纯模型隔离**：domain 层只依赖 QtCore，"任何界面或协议改动都不应波及这里"。
- **服务层门面**：UI 只消费服务层语义化接口，不感知协议字节细节。

### 4.3 可测试性

- **单测 target 独立**：每个被测模块一个独立测试 target，仅链接被测库（对应 WPF 测试项目）。
- **CTest 注册**：12 个单测 target 全部注册进 CTest，`ctest` 一键全量回归。
- **独立测试视角**：Test Agent 独立于开发 Agent，覆盖边界/异常/线程/粘包/断线/生命周期。
- **数据驱动测试**：Qt Test `_data` + `QFETCH/QCOMPARE`（对应 NUnit 的 TestCase）。
- **元类型注册**：自定义枚举经 `Q_DECLARE_METATYPE` 注册，可被 `QSignalSpy` 记录断言。

### 4.4 可部署性

- **自动部署 Qt 运行库**：`ds_deploy_qt()` 在 POST_BUILD 调用 `windeployqt`，每个可执行 target（主程序 + 模拟设备 + 全部测试）都部署 DLL，避免运行期"找不到 Qt DLL"。
- **独立运行验证**：集成冻结阶段在无 Qt 环境机器上验证主程序与模拟设备。
- **资源内嵌**：QSS 经 AUTORCC 编译进可执行文件，无外部资源依赖。

### 4.5 可维护性与可学习性

- **全中文注释** + **WPF/C# 锚点**：降低维护与学习门槛。
- **契约先行**：协议帧格式、状态机以契约文档固化，代码注释直接引用编号。
- **教学链路**：每个知识点落在真实文件/类/函数，文档跟随源码。

## 5. 技术选型与理由

### 5.1 UI 呈现：Qt Widgets 自绘 vs 第三方图表库

**选型：Qt Widgets 自绘控件（LineChartWidget / GaugeWidget / LedIndicator）。**

| 对比 | Qt Charts / QCustomPlot | 自绘（本工程） |
|---|---|---|
| 开发成本 | 低（现成控件） | 高（手写 paintEvent） |
| 教学价值 | 低（黑盒） | **高**（练习 Qt 绘制体系、事件、坐标换算） |
| 依赖 | 额外第三方库 | 仅 Qt 本体 |
| 定制自由度 | 受库约束 | 完全可控 |

**理由**：本工程兼具教学目标，自绘控件让学习者深入 `QWidget::paintEvent`、画笔/画刷、坐标系缩放、抗锯齿与定时重绘等核心机制；同时避免第三方库依赖，保持部署简单。监控页对数据源做了"可替换"设计（演示 QTimer 与真实 DataService 汇聚到同一 `onDataUpdated` 槽），控件本身不关心数据来源。

### 5.2 配置存储：INI 文件 vs 注册表

**选型：INI 文件（QSettings `IniFormat`），而非 Windows 注册表（NativeFormat）。**

理由（`configmanager.h` 注释明确约定）：
- 注册表不透明、难备份、卸载残留、无法随程序分发、不能跨平台；
- INI 是纯文本：用户可读可改、可复制分发、可纳入版本管理；
- 与用户 WPF 经验的 `Properties.Settings`（用户级配置）对应，但更利于工程化交付。

### 5.3 线程模型：QThread + Worker vs 继承 QThread

**选型：`QThread` + `Worker（moveToThread）`，不继承 QThread 重写 `run()`。**

理由：
- `moveToThread` 让 Worker 对象在采集线程中通过事件循环接收跨线程信号，与 UI 线程的通信天然走 QueuedConnection，线程边界清晰；
- 对应 WPF 的 `BackgroundWorker`，便于学习者对照；
- 工程规程明令：专项 Agent 不得擅自把该架构改成"继承 QThread"；如有更优方案须提交架构变更建议由主 Agent 决策。

### 5.4 通信：QTcpSocket 封装 vs 裸 Socket / QSerialPort

**选型：封装 `QTcpSocket` 为 `TcpClient` 服务类；串口（P9）作为预留模块。**

理由：
- 封装后对外只暴露"连接 / 断开 / 发帧 / 收帧"四个业务动作，UI 不操作裸 socket；
- 字节流解析交给协议引擎（FrameParser），自动处理半包/粘包，业务层只拿完整协议帧；
- 对应 WPF 里封装的 `TcpClient` 帮助类；
- 模拟设备（Simulator）提供 TCP 服务端，无硬件时即可联调整条采集链路，降低对真实硬件的依赖。

### 5.5 构建：CMake + Ninja vs qmake

**选型：CMake + Ninja，配合 AUTOMOC/AUTORCC/AUTOUIC 三开关。**

理由：
- CMake 是 Qt 官方推荐的新一代构建体系，跨平台能力强，与 CTest 无缝集成（`enable_testing()` + `add_test`）；
- 自动化元对象编译，减少手工 moc 维护；
- 统一管理静态库依赖传播（`PUBLIC`/`PRIVATE`）、Qt 运行库部署（windeployqt 自定义命令）与测试注册。

### 5.6 测试：Qt Test + CTest

**选型：Qt Test 编写用例，CTest 统一注册与回归。**

理由：
- Qt Test 深度集成 Qt 元对象系统，`QSignalSpy` 可直接断言信号与自定义类型参数；
- CTest 提供一键全量回归（`ctest`），是"每阶段测试全绿"验收标准的执行载体；
- 每个测试 target 独立可执行、独立部署 Qt DLL，与主程序完全隔离。
