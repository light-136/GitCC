# DataScope Studio —— 测试文档

> 适用版本：DataScope 0.1.0（11/11 测试全绿基线）
> 测试框架：Qt Test（Qt 5.12.2）+ CTest 集成
> 文档编号：06；上一文档：《05-构建与部署说明》

本文档说明 DataScope 的完整测试体系：策略、12 个测试套件逐项说明、关键技术、
已知难点与解决、以及端到端冒烟测试方法。所有用例名均提取自 `tests/unittests/`

## 1. 测试策略总览

### 1.1 阶段化测试先行（契约先行 TDD）

本工程按阶段（P1→P15）推进，每个阶段遵循同一节奏：

1. 先编写**接口契约文档**（约定输入/输出/边界/状态机）；
2. 依据契约**先写测试**（`tests/unittests/tst_*.cpp`）；
3. 再实现被测模块，直到测试全绿。

因此每个测试套件与一个开发阶段一一对应，测试即契约的可执行表述。
版本历史中的提交可以佐证这一演进：

### 1.2 CTest 集成

`CMakeLists.txt` 通过 `enable_testing()` + 12 个 `add_test(NAME tst_xxx COMMAND tst_xxx)`
将全部套件接入 CTest。每个套件是**独立可执行程序**（`QTEST_MAIN` 生成 main），
仅链接被测库与 `Qt5::Test`，与主程序解耦（对应 WPF/C# 的“测试项目”）。

- 全量运行：`ctest --output-on-failure`（详见《05-构建与部署说明》第 3 节）；
- 每个测试 target 构建后自动执行 `ds_deploy_qt`，把 `Qt5Test.dll` 等运行库
  部署到 exe 同目录，保证 ctest 可运行。

### 1.3 测试金字塔

```
        ▲  端到端冒烟（simulator + DataScope 双进程）      —— 真实链路
      ▲  集成测试（回环伪服务器 + 多线程数据总线）         —— 协议/网络/状态机
    ▲    单元测试（纯函数 / 数据模型 / 控件逻辑）          —— 最多、最快
```

- **单元层**：ByteUtils、TimeUtils、Domain、Widgets 等纯逻辑，毫秒级跑完；
- **集成层**：Protocol、TcpClient、DataService、DeviceController、RecordManager，
  通过本机回环伪服务器验证协议解析、网络收发、跨线程数据投递、状态机；
- **冒烟层**：simulator（模拟设备）与 DataScope（主程序）双进程联动，验证真实链路。

## 3. 关键测试技术

### 3.1 QSignalSpy —— 信号探针

`QSignalSpy` 是 Qt Test 提供的信号监听器，类似 WPF 中“订阅事件并计数断言”，
用于验证“某信号是否发出、发出几次、参数是什么”：

```cpp
QSignalSpy frameSpy(&client, &TcpClient::frameReceived);
// ... 触发异步操作 ...
QVERIFY(frameSpy.wait(1000));          // 事件循环等待，最多 1s
QCOMPARE(frameSpy.count(), 1);          // 恰好发出 1 次
const ProtocolFrame f = frameSpy.at(0).at(0).value<ProtocolFrame>(); // 第 1 次、第 1 个参数
```

典型用法：信号计数（`count()`）、取回参数（`at(i).at(j)`）、验证状态机是否
经过中间态（遍历 `statusChanged` 的历史）。注意：**自定义类型参数**必须先在
全局作用域 `Q_DECLARE_METATYPE` + `qRegisterMetaType`，否则 QSignalSpy 取不出
参数值（见 3.4 / 4.3）。

### 3.2 QTRY_* 事件驱动等待 —— 绝不裸 sleep

异步网络/定时器事件必须让事件循环跑起来才有结果。`QTRY_VERIFY_WITH_TIMEOUT`
与 `QTRY_COMPARE_WITH_TIMEOUT` 会**反复处理事件循环**直到条件满足或超时：

```cpp
QTRY_COMPARE_WITH_TIMEOUT(connSpy.count(), 1, 2000);   // 2s 内主线程收到 connected
QTRY_VERIFY_WITH_TIMEOUT(peer, 2000);                  // 2s 内伪设备收到连接
```

对比 `QTest::qWait`（固定等待）与 `QSignalSpy::wait`（等单个信号），
`QTRY_*` 把“轮询 + 事件循环 + 超时”封装成一个宏，是异步测试的推荐姿势。
绝不用裸 `sleep`/`QThread::msleep` 等异步结果。

### 3.3 回环伪服务器

网络类测试不依赖真实硬件，在测试进程内建一个“伪设备”：

```cpp
QTcpServer server;
QVERIFY(server.listen(QHostAddress::LocalHost, 0));  // 127.0.0.1:0 随机端口
QObject::connect(&server, &QTcpServer::newConnection, [&]() {
    peer = server.nextPendingConnection();            // 记录对端 socket
});
```

- **关键**：必须用**信号连接 + QTRY 等待**接收连接，而**不用同步的
  `waitForNewConnection()`**（原因见 4.1 竞态说明）；
- 伪设备用 `FrameBuilder` 组帧、`peer->write()` 发送，可精确控制半包/粘包/篡改/
  先拒后收等场景；
- `tst_dataservice`/`tst_devicecontroller` 把建伪设备封装成辅助函数
  `startFakeServer()`（监听失败返回 0，避免在返回 quint16 的函数里用 QVERIFY）。

### 3.4 enum class 元类型注册

`QSignalSpy` 需要按类型名查到元类型才能拷贝参数。对**命名空间内的 `enum class`**
（如 `DeviceStatus`）和自定义结构（`ProtocolFrame`、`DataPoint`），需两件事：

```cpp
// ① 全局作用域声明元类型
Q_DECLARE_METATYPE(datascope::domain::DeviceStatus)
Q_DECLARE_METATYPE(QVector<datascope::domain::DataPoint>)

// ② initTestCase 中注册（moc 对命名空间类型的规范化名可能不同，三个别名都注册）
qRegisterMetaType<DeviceStatus>("DeviceStatus");
qRegisterMetaType<DeviceStatus>("domain::DeviceStatus");
qRegisterMetaType<DeviceStatus>("datascope::domain::DeviceStatus");
```

同一个类型注册多个名字是无害的（别名都指向同一元类型 id），
目的是让 QSignalSpy 无论按“裸名/相对名/全限定名”哪种方式查找都能命中。

## 4. 已知难点与解决

### 4.1 waitForNewConnection 竞态

- **问题**：初版 `tst_tcpclient` 曾用 `pseudoServer.waitForNewConnection(…)` 同步
  等待连接。该方法等待 `newConnection` 信号，而该**信号是一次性的**——如果
  `connectedSpy.wait()` 的事件循环恰好先消费了这个信号（发出时无接收者即丢弃），
  `waitForNewConnection` 就会超时，造成**随机竞态失败**。
- **解决**：改为**事件驱动**——预先连接 `newConnection` 信号记录 `nextPendingConnection()`
  的对端，再用 `QTRY_VERIFY_WITH_TIMEOUT(pseudo != nullptr, 2000)` 等待。这是
  `tst_tcpclient` 全绿与 `tst_dataservice` 的 `startFakeServer` 统一的可靠模式。

### 4.2 Windows 端口拒绝延迟

- **问题**：测试“连接不存在的端口”时，若用“相邻端口法”（存活端口 + 1），
  系统动态端口可能恰好被别的服务占用，连接会“成功”，`error` 永不触发 → flaky。
- **解决**：改用“绑定-释放法”——先 `listen(随机端口)` 验证该端口此刻空闲，作用域
  结束释放后**立即连接**。但 Windows 对“刚释放的 LISTEN 端口”约 **2 秒后才回 RST**
  （TCP 栈 SYN 重传机制），因此：
  - `tst_tcpclient::connectFailureEmitsError` 等待给足 **5s**；
  - `tst_devicecontroller::connectFailure_goesError` 等待给足 **6s**
    （叠加线程投递开销，实测最快约 3.3s 到达 Error；3s 曾超时）。
  - 注释中保留了完整调研结论，供后续维护参考。

### 4.3 跨线程信号参数注册

- **问题**：`DataService` 的 Worker 运行在采集线程，`dataUpdated(QVector<DataPoint>)`
  通过队列连接跨线程投递到主线程。QSignalSpy 若拿不到元类型，参数会空。
- **解决**：`Q_DECLARE_METATYPE` 声明 `DataPoint` 与 `QVector<DataPoint>`，
  在 `initTestCase` 用 `qRegisterMetaType` 注册（测试内声明与 `dataservice.cpp`
  生产代码中的声明保持一致）。这是“队列连接 + 元类型注册缺一不可”的教学验证点。

### 4.4 单例状态污染与临时目录隔离

- **问题**：`LogManager`/`ConfigManager` 是进程级单例，用例之间共享状态；
  且不能写用户真实配置/日志目录。
- **解决**：每个用例 `init()` 到独立的 `QTemporaryDir`（RAII，析构自动删除），
  既隔离状态又隔离磁盘文件。配置持久化用例再通过“重新 init 同一目录”模拟程序重启。

### 4.5 Windows 下临时目录残留

- **问题**：`LogManager` 会一直持有日志文件句柄，用例结束时 `QTemporaryDir`
  自动删除在 Windows 下可能因文件被占用而**静默失败**，残留在 `%TEMP%`。
- **解决**：不影响任何断言结果；残留目录可由系统或手动清理，Linux/macOS 下则
  能正常删除。测试源码注释中已说明此平台限制。

## 5. 端到端冒烟测试方法

单元/集成测试验证了模块正确性，但真实交付前还要用**双进程**验证完整链路：
模拟设备（simulator）↔ 主程序（DataScope）。

### 5.1 前置条件

1. 已按《05-构建与部署说明》构建出 Debug 或 Release 版本；
2. 构建目录内含 `DataScope.exe`、`simulator.exe` 及全部 Qt DLL/插件；
3. 目标端口（默认 `40001`）未被占用。

### 5.2 操作步骤

```bat
:: ① 启动模拟设备：TCP 服务端监听 0.0.0.0:40001，持续发送 4 通道正弦波采集帧
D:/Gemi/QT\ SoftWare/DataScope/build_release/simulator.exe
::   （端口被占时改用 --port 50001）

:: ② 另开终端启动主程序
D:/Gemi/QT\ SoftWare/DataScope/build_release/DataScope.exe
```

### 5.3 验证点

| 编号 | 操作 | 预期结果 |
|------|------|----------|
| S1 | simulator 启动 | 输出 `模拟设备已启动，监听 0.0.0.0:40001`，进程不退出 |
| S2 | 主程序“设备”页连接 `127.0.0.1:40001` | 连接成功，设备状态变为已连接 |
| S3 | 切换“监控”页并开始采集 | 4 通道实时曲线持续滚动刷新（温度/压力/流量/振动），仪表盘数值跳变 |
| S4 | 强行杀掉 simulator 进程 | 主程序进入错误/重连状态，状态指示灯变红；重启 simulator 后主程序**自动重连**恢复曲线 |
| S5 | 开始记录一段时间后停止 | 记录文件生成（CSV），可在“记录”页回放，曲线按记录重放 |

### 5.4 冒烟判定

S1–S3 全部通过即视为“链路打通”；S4 验证自动重连（对应
`tst_devicecontroller::autoReconnectAfterFailure` 的真实链路版）；
S5 验证记录/回放（对应 `tst_recordmanager`）。冒烟失败时，依据失败点回查
对应套件（详见第 2 节）定位模块。
