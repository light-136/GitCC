# 03-通信协议帧格式契约

> 适用范围：DataScope Studio 与采集设备（真实硬件 / Simulator）之间的字节级通信帧。
> 本契约是协议模块地基，组帧器 `FrameBuilder`、解析器 `FrameParser`、校验 `Crc16` 均严格按本契约实现。

## 1. 帧总布局

| 字段 | 字节数 | 说明 |
| --- | --- | --- |
| SOF | 2 | 帧头，固定 0xAA 0x55 |
| FUNC | 1 | 功能码 |
| CMD | 1 | 子命令 |
| LEN | 2 | 载荷长度（大端） |
| DATA | N=LEN | 载荷数据 |
| CRC16 | 2 | 校验值（低字节在前） |

常量：`kSof=0xAA55`、`kHeaderLen=6`（SOF+FUNC+CMD+LEN）、`kCrcLen=2`。

## 2. 字段定义与取值

| 字段 | 含义 | 取值 |
| --- | --- | --- |
| SOF | 帧头（接收端重同步锚点） | 0xAA 0x55，发送时高字节 0xAA 在前 |
| FUNC | 功能码 | 0x01 采集、0x02 配置、0x03 查询；最高位 0x80 为响应标志 |
| CMD | 子命令 | 各功能码内部自行定义；采集数据帧 CMD=0x01 |
| LEN | 载荷字节数 | 大端；上限 `kMaxPayloadLen=1024` |
| DATA | 载荷 | 可为空（LEN=0） |
| CRC16 | MODBUS CRC16 | 覆盖 FUNC 至 DATA 末尾 |

最大载荷长度 `kMaxPayloadLen = 1024`（防御值，小于协议可表达的 65535，防止恶意 LEN 撑爆缓冲）。

## 3. 字节序约定

- **LEN**：大端序（高字节在前）。
- **float**：载荷内浮点为大端序 4 字节（PC 为小端，收发双方手动重排）。
- **CRC16**：低字节在前追加（先 CRC_L 再 CRC_H）。
- **SOF**：发送 0xAA 再 0x55。

## 4. CRC16 校验

- 算法：MODBUS CRC16，初始值 `0xFFFF`，多项式 `0xA001`（反射表驱动，256 项表）。
- 覆盖范围：**FUNC 起到 DATA 末尾**，即 FUNC(1)+CMD(1)+LEN(2)+DATA(len)，LEN 字段也参与校验；SOF 不参与。
- 追加顺序：低字节在前。

## 5. 响应标志 0x80

约定：收到 FUNC 为 f 的请求帧，响应帧 FUNC = `f | 0x80`。例如采集请求 0x01 → 响应 0x81。Simulator 回发即按此构造。

## 6. 组帧 / 解析规则

- 组帧 `FrameBuilder::build(func, cmd, payload)`：SOF → FUNC → CMD → LEN 大端 → DATA → CRC；载荷超过 kMaxPayloadLen 时返回空数组表示失败（空载荷成功组帧得到 6+0+2=8 字节）。
- 解析 `FrameParser` 三态状态机：
  1. **状态 A 扫描帧头**：缓冲内逐字节找 0xAA 0x55；找到前将垃圾丢弃，仅保留末尾可能残存的 0xAA（等下一次 feed 补 0x55）。
  2. **状态 B 读帧头**：缓冲 ≥6 字节后读 FUNC/CMD/LEN（大端）；若 LEN>1024 判定非法帧头，丢弃 6 字节头回状态 A，绝不等待整帧。
  3. **状态 C 收数据校验**：缓冲 ≥6+LEN+2 后取 DATA，对 FUNC..DATA 计算 CRC 并与帧尾比对；一致则产出 `isValid=true` 帧，不一致则整帧丢弃，继续重同步。

## 7. 半包 / 粘包语义

- 采用"累积缓冲 + 按需提取"：`feed()` 只追加字节，`nextFrame()` 只从头部消费一帧。
- **半包**：`nextFrame()` 返回 false 且缓冲原样保留，下次 feed 补齐后再取。
- **粘包**：一次 feed 多帧时，连续调用 `nextFrame()` 逐帧取出。
- 只有 CRC 校验通过的帧才会产出；坏帧不产出、直接丢弃。
