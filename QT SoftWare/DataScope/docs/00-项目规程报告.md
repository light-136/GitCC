## 3. 多 Agent 协作规程

### 3.1 组织模型

采用 **主 Agent（Project Lead / Architect）+ 专项 Agent 并行 + 主 Agent 集成验收** 的模式，而非单一 Agent 串行或简单"开 N 个 Agent"。

**主 Agent 职责**（其他 Agent 不得擅自改变总体架构）：
总体架构、任务拆分、技术决策、Git/分支管理、子任务协调、代码集成、冲突解决、编译、集成测试、最终验收、文档汇总。

**专项 Agent 分工**（按任务性质动态创建）：

| 专项 Agent | 职责范围 |
|---|---|
| Core Agent（C++/Qt Core） | QObject、Meta Object、Signal/Slot、Event Loop、RAII |
| UI Agent（Widgets） | QMainWindow、QWidget、Layout、QSS、页签、自绘控件 |
| Model/View Agent | QAbstractTableModel、TableView、dataChanged |
| Communication Agent | QTcpSocket、QTcpServer、连接/断线/心跳/重连 |
| Protocol Agent | FrameParser、CRC16、粘包/分包、协议状态机、边界测试 |
| Thread Agent | QThread、moveToThread、Worker、QueuedConnection、线程生命周期 |
| Storage/Config/Log Agent | QSettings、INI、QFile、CSV、LogManager、日志轮转 |
| Test/QA Agent | Qt Test、CTest、单元/集成/冒烟测试、异常测试 |
| Documentation Agent | Qt 学习地图、WPF→Qt 对照、阶段教学文档、代码解释 |
| Build/Deploy Agent | CMake、Build、Release、windeployqt、独立运行验证 |

### 3.2 并行 / 串行判定规则

不机械创建 Agent，按依赖关系判定：

| 判定依据 | 结论 |
|---|---|
| 有依赖 | **串行**（如 P8 领域模型未定义，P12 数据总线无法并行开工） |
| 无依赖 | **并行**（如 P8~P14 各模块相对独立时，可显著增加并行度） |
| 代码冲突风险高 | **不并行**（禁止多个 Agent 无规则修改同一核心文件） |
| 接口已确定（契约先行） | **可以并行**（接口冻结后，UI / Test / Doc 可并行消费同一契约） |
| 架构尚未确定 | **不并行** |

示例（P8 契约先行的并行展开）：

```text
P8 Model/View
   ↓
先定义 Device / Channel 数据模型
   ↓
确定接口（契约冻结）
   ↓
   ├── UI Agent  ←──┐
   ├── Test Agent ←──┤ 并行
   └── Doc Agent  ←──┘
   ↓
主 Agent Review → Merge
```

### 3.3 接口先行与契约文档

- **接口先行**：先冻结模块对外接口（头文件签名 / 协议帧格式 / 状态机），再并行实现。
- **契约文档**：重要接口以编号契约文档固化，代码注释中直接引用，例如：
  - 《03-通信协议帧格式契约.md》——帧格式：`| SOF(2B) | FUNC(1B) | CMD(1B) | LEN(2B 大端) | DATA(LEN) | CRC16(2B 低字节在前) |`（`protocoltypes.h` 引用）。
  - 《07-设备状态机契约.md》——状态机：`Disconnected → Connecting → Connected / Error`（`devicecontroller.h` 引用）。
- **架构变更建议**：专项 Agent 发现更优方案时，不得擅自改动架构，必须提交"架构变更建议"（原设计 / 新设计 / 原因 / 优点 / 缺点 / 对其他模块影响），由主 Agent 决策。

### 3.4 测试独立原则

- **开发 Agent 写功能，测试 Agent 找问题**；禁止同一个 Agent"自己写代码 → 自己说测试通过"。
- 测试 Agent 从独立角度覆盖：边界条件、异常输入、线程问题、断线、粘包/分包、生命周期、程序退出。
- 单测 target 独立于主程序，仅链接被测库（对应 WPF 的"测试项目"），保证测试隔离与快速执行。

### 3.5 代码 Review 与集成冻结

**Review 检查清单**（主 Agent 对专项 Agent 产出逐项核查）：
能否编译 → 架构是否符合规划 → Qt API 是否正确 → 线程是否安全 → 生命周期是否正确 → 错误处理是否完整 → 测试是否存在 → 文档是否对应。

**集成冻结**（P15 完成前执行）：
停止新增功能 → 所有 Agent 提交 → 主 Agent 合并 → 完整 Build → 完整 Test → 修复问题 → 再次 Build → 再次 Test → Release → windeployqt → 独立环境验证，形成最终稳定版本。

**最终报告附加"Agent 协作报告"**：主 Agent 与各专项 Agent 的职责、并行/串行任务清单、各 Agent 发现的问题、经 Review 的代码、冲突情况、最终合并代码、最终测试负责人。

## 4. 代码质量规范

### 4.1 命名规范

| 类别 | 规则 | 实例 |
|---|---|---|
| 命名空间 | `datascope::` 命名空间 + 层名 | `datascope::utils`、`datascope::domain`、`datascope::services` |
| 类名 | PascalCase | `ByteUtils`、`LogManager`、`DeviceController`、`LineChartWidget` |
| 函数/方法 | camelCase | `connectToHost`、`startRecording`、`appendUInt16BE` |
| 成员变量 | `m_` 前缀 | `m_socket`、`m_status`、`m_replayFrames` |
| 常量 | `k` 前缀 | `kSof`、`kMaxPayloadLen`、`kChannelCount` |
| 头文件守卫 | `#pragma once` | 全部头文件 |
| 枚举 | `enum class` 强类型 | `enum class DeviceStatus`、`enum class LogLevel` |
| 入参风格 | const 引用入参 / 非 const 引用出参 | `const QByteArray &data`、`quint16 &out` |
| 成败报告 | TryParse 风格（返回 bool + 出参） | `ByteUtils::readUInt16BE`、`TimeUtils::parseTime` |

### 4.2 注释与教学锚点

- **全中文注释**：所有头文件、实现、单测均以简体中文书写注释。
- **WPF/C# 锚点对照**：每个教学载体类都标注对应的 WPF/C# 概念，例如：
  - `ByteUtils` ≈ `BitConverter` / static class；
  - `LogManager` ≈ NLog / `TraceSource`；
  - `ConfigManager` ≈ `Properties.Settings` / app.config；
  - `DataService` ≈ BackgroundWorker + Prism EventAggregator；
  - `TcpClient` ≈ WPF 里封装的 TcpClient 帮助类。
- **教学点**：头文件顶部以"教学点（阅读时注意）"小节说明该文件承载的 C++/Qt 知识点（const 引用、RAII、隐式共享、信号槽、moc 规范名等）。

### 4.3 分层边界与依赖方向

依赖方向严格单向（上层依赖下层，下层不感知上层）：

```text
UI / app
   ↓
services（组合 protocol + domain + network）
   ↓
domain  /  protocol（纯模型 / 纯字节协议）
   ↓
infrastructure（日志、配置）
   ↓
utils（字节、时间工具）
```

各层边界红线（已在头文件注释中固化）：

| 层 | 允许依赖 | 禁止依赖 |
|---|---|---|
| `utils` | QtCore | UI、Network、SerialPort |
| `domain` | QtCore（QString/QDateTime/QVector） | UI、QtNetwork、SerialPort（"任何界面或协议改动都不应波及这里"） |
| `protocol` | QtCore | UI、业务逻辑 |
| `services` | protocol + domain + Network | UI |
| `ui` | domain（只读模型） | 不写业务逻辑（主窗口只负责"组装"页面） |

### 4.4 静态库划分原则

- **一个库多个消费者**：主程序与单测都依赖的模块独立成库（如 `datascope_utils`）。
- **基础设施先稳定**：日志/配置是全工程地基，先于业务模块稳定（`datascope_infra`）。
- **被多方消费的模块独立成库**：协议层被串口/TCP/模拟设备共同消费（`datascope_protocol`）。
- **服务层是门面**：`datascope_services` 组合协议引擎 + 领域模型 + 网络通信，向上对 UI 提供语义化接口。
- **库用 PUBLIC 传播依赖**：`target_include_directories(... PUBLIC ${DS_SRC_DIR})`，库的使用者自动获得头文件路径。

### 4.5 线程安全规范

- **共享数据一律加锁**：LogManager 用 `QMutex` 保护 `QFile`/`QTextStream`（非线程安全）；ConfigManager 用 `QMutex` 串行化 QSettings；DataService 用 `QMutex` 保护最新快照。
- **跨线程通信一律信号槽（QueuedConnection）**：`QThread + Worker（moveToThread）`，不使用裸锁同步 UI。
- **线程生命周期托管**：析构时 `quit + wait` 安全退出；`QObject` 对象树托管 socket / timer。
- **自定义类型注册元类型**：`Q_DECLARE_METATYPE` 注册自定义枚举/结构，保证跨线程队列参数不丢失。
- **moc 规范名陷阱**：跨线程信号参数使用**全限定名**（如 `QVector<datascope::domain::DataPoint>`），使 moc 规范化名 == 注册名 == `Q_DECLARE_METATYPE` 名。
- **单例采用 Meyer's Singleton**：函数内静态局部变量，C++11 起编译器保证初始化线程安全。

## 5. 验收流程

### 5.1 每阶段验收五步

每个里程碑完成后按固定顺序验收，全部通过方可进入下一阶段：

```text
编译（完整 Build 零错误）
   ↓
测试（CTest 全绿，新增单测 target 注册）
   ↓
文档（教学文档 + 契约文档跟随源码）
   ↓
验收（主 Agent Review 检查清单逐项核对）
   ↓
进入下一阶段
```

### 5.2 集成冻结流程（P15 收尾）

```text
停止新增功能 → 所有 Agent 提交 → 主 Agent 合并
   → 完整 Build → 完整 Test → 修复问题
   → 再次 Build → 再次 Test → Release
   → windeployqt → 独立环境验证（无 Qt 环境机器运行确认）
```

### 5.3 测试注册与全绿标准

- 每个阶段新增的单测必须作为独立 target 注册进 `CMakeLists.txt` 的 `add_test`，并调用 `ds_deploy_qt()` 部署 Qt 运行库（否则 `ctest` 运行时报 DLL 缺失）。
- 合并前以 `ctest` 全绿为硬性门槛；当前 21 个单测 target 全部注册（V2 后）。

`docs/` 为本工程文档体系中心，以编号前缀区分优先级与阅读顺序：

| 文件 | 职责 | 状态 |
|---|---|---|
| `00-项目规程报告.md` | 项目基本信息、里程碑、多 Agent 协作规程、代码质量规范、验收流程、文档体系规范（本文件） | ✅ 已建 |
| `01-项目概述与需求文档.md` | 项目背景、系统目标、功能/非功能需求、技术选型与理由 | ✅ 已建 |
| `02-系统架构与设计文档.md` | 分层架构、模块接口、线程模型、数据流设计（规划） | ⏳ 规划 |
| `03-通信协议帧格式契约.md` | 帧格式契约：SOF/FUNC/CMD/LEN/DATA/CRC16（代码注释已引用） | 契约约定 |
| `04-构建与部署文档.md` | CMake 构建、Ninja、windeployqt 部署、发布包制作（规划） | ⏳ 规划 |
| `05-用户使用手册.md` | 软件操作说明：连接设备、采集、记录回放、配置（规划） | ⏳ 规划 |
| `06-单测与验收报告.md` | 单测覆盖矩阵、各阶段验收记录、Agent 协作报告（规划） | ⏳ 规划 |
| `07-设备状态机契约.md` | 状态机契约：状态转移 + 退避重连策略（代码注释已引用） | 契约约定 |

> 说明：`03`、`07` 两个契约文档编号已在源码注释中被引用，属已约定的契约层；`00/01` 为本工程新建文档；其余为规划占位，后续阶段按需补齐。

### 6.2 契约文档约定

- 契约文档必须先于实现冻结，作为并行开发的公共依据（接口先行）。
- 契约修改必须走"架构变更建议"流程，由主 Agent 决策并同步更新相关代码注释。
- 代码注释与契约文档必须一一对应，禁止出现"文档与代码脱节"。

### 6.3 教学文档要求

- 教学 Agent 必须跟踪真实代码，不得凭空编写教科书式内容。
- 写作链路：`源码 → 知识点 → 文件 → 类 → 函数 → 教学文档`。
- 每个知识点必须落在真实文件/类/函数上（如 Signal/Slot 落在 `DeviceWorker` 的某 signal 与某 connect 上，并解释实际执行过程）。
