# P10 阶段学习文档 —— 协议引擎（Crc16 / FrameBuilder / FrameParser）

> 提交：`5b68130`（P8/P10/P14 合并提交）｜ 里程碑：`datascope_protocol` 库 + `tst_protocol` 全绿（8/8 套件）

## 1. 阶段目标

实现协议引擎静态库：CRC16-MODBUS 校验、帧组帧器、流式帧解析器（状态机），作为串口（P9 预留）/TCP（P11）/模拟设备三方共用的"咽喉"。契约先行（《03-通信协议帧格式契约.md》）。

## 2. 关键技术点（WPF 迁移锚点）

- **帧格式契约**：`SOF(0xAA55,2B)+FUNC(1B)+CMD(1B)+LEN(2B 大端)+DATA(LEN)+CRC16(2B 低字节在前)`。字节序是协议灵魂，收发两端必须完全一致。
- **流式状态机（扫描帧头→读头→收数据校验）**：天然支持**粘包**（一次 feed 多帧）与**半包**（分多次到达正确拼接）——TCP 字节流通信的必修课，C# 里同样要写但 Qt 无现成工具。
- **FrameBuilder ≈ BinaryWriter / FrameParser ≈ BinaryReader**：组帧器"结构→字节"，解析器"字节流→结构"，对称独立各自可测。
- **TryParse 风格**：校验失败返回 false / 不产出帧，**绝不抛异常**——工业现场宁可丢一帧不让程序崩。

## 3. 实现内容

- `src/protocol/protocoltypes.h`：帧常量（`constexpr kSof/kHeaderLen/kMaxPayloadLen=1024`）+ `ProtocolFrame` 结构。
- `src/protocol/crc16.h/.cpp`：MODBUS CRC16 反射查表法（256 项表懒初始化），初值 0xFFFF、异或出参 0xFFFF、反射输入输出。
- `src/protocol/framebuilder.h/.cpp`：`build(func,cmd,payload)` 按字节序拼帧，载荷超限返回空。
- `src/protocol/frameparser.h/.cpp`：三态状态机 + 内部缓冲，`feed(chunk)` 攒字节、`nextFrame()` 消费产出；垃圾重同步、坏帧丢弃、缓冲裁剪。
- `tests/unittests/tst_protocol.cpp`：12 函数 / 数据驱动 6 行 → 17 用例 / 约 130 断言。
- `CMakeLists.txt`：新增 `datascope_protocol` 静态库。

## 4. 测试与验证

`tst_protocol` 全绿，CTest 升到 8/8 套件。覆盖契约 8 个强制项：往返 / 半包 / 粘包 / CRC 篡改 / SOF 错位 / LEN 越界 / 空载荷 / 单字节喂入。**CRC 标准向量 `"123456789" → 0x4B37` 验证**，不靠"自己算自己查"循环验证。

## 5. 遇到的难点与解决

- **CRC 覆盖范围两端不一致**：组帧与解析对"CRC 覆盖哪几字节"理解不一致（一个含 LEN 一个不含），数据总解析失败。解法：以契约为准统一为 `FUNC+CMD+LEN+DATA` 共 `4+LEN` 字节，两端用对称表达式 `mid(2)` vs `mid(2, ...)`。
- **半包/粘包处理不当**：只按"读一次解析一次"帧被拆就失败。解法：状态机 + 内部缓冲，`feed` 只管攒、`nextFrame` 够一帧才消费。
- **`QByteArray(int, char)` 构造陷阱**：`append(int,char)` 在 5.12 存在性不确定，统一用确定存在的构造规避。

## 6. 阶段成果小结

协议引擎成为全系统咽喉，先于模拟设备/TCP 客户端稳定。核心领悟：**C# 把字节↔结构交给 BinaryReader/Writer 顺手做完，Qt 没有帧解析基础设施——通信可靠性（防攻击上限、坏帧丢弃、粘包半包）必须由你自己设计**，这是"从框架替你干活到理解引擎如何干活"的关键一步。
