## 1. 阶段目标

完成串口通信（QSerialPort）的技术调研与接口预留。规划中 P9 实现"采集设备串口链路"，但考虑到时间优先级与本机无真实串口硬件，工程最终**以 TCP + 模拟设备（P11）落地采集链路**，串口模块作为预留规划（见《08-项目总结》扣分项说明与《00-项目规程报告》P9 状态）。

## 2. 关键技术点（WPF 迁移锚点）

- **QSerialPort ≈ .NET `SerialPort`**：两者同为 QIODevice/Stream 模型，提供打开/波特率/数据位/停止位/校验位等参数。
- **QSerialPortInfo ≈ `SerialPort.GetPortNames()`**：枚举可用串口。
- **QSerialPort 与 QTcpSocket 同源**：都继承 QIODevice、都是事件驱动（readyRead 信号）+ 字节流——**粘包/分包/协议解析完全复用 P10 的 FrameParser 状态机**。
- **同步阻塞 API（waitForReadyRead/waitForBytesWritten）**：与 P11 的 `waitForNewConnection` 同类，只宜在测试/脚本用，生产必须事件驱动（这是 P11 竞态踩坑后确立的纪律）。

## 3. 实现内容

本阶段无独立源码产物，落地为四处"预留"：

- **协议引擎共用预留**：`datascope_protocol` 库注释明确"串口(P9)、TCP客户端(P11)、模拟设备(Simulator)都消费它"——一个帧引擎，三种通道复用。

## 4. 测试与验证

无单测（未列入构建，`CMakeLists.txt` 未注册任何串口模块）。验证方式为"接口预留审查"：确认协议引擎可被串口复用、UI 占位页标注了串口接入点。

## 5. 遇到的难点与解决

- **无硬件联调**：本机无真实串口设备，无法做端到端验证。解决思路：与 P11 一致，用模拟设备/回环方式联调；帧引擎（P10）先行稳定，串口只做字节通道替换。
- **同步阻塞 vs 事件驱动**：QSerialPort 的 `waitForReadyRead` 与 QTcpSocket 的 `waitForNewConnection` 同类，P11 已实证其存在信号竞态——串口落地时必须同样采用信号槽事件驱动。
- **时间优先级取舍**：串口与 TCP 同属"采集通道"，选择先走通 TCP + 模拟设备验证全链路，串口列入"未来方向"（最终报告第十节）。

## 6. 阶段成果小结

P9 以"技术调研 + 接口预留"完成，是"完整而非完美"的唯一缺口。最大收获：**通道无关的协议引擎设计**让串口/TCP/模拟设备共享同一套组帧/解析/校验，未来接入串口只需实现一个"字节通道"，无需重写协议逻辑。
