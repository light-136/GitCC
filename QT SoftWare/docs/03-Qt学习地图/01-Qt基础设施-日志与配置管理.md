## 1. 本节为什么重要：工业软件的地基先于业务

> 一句话类比：日志是工业软件的"黑匣子（flight recorder）"，配置是"设备的仪表盘（dashboard）"——**没有它们，多通道采集程序一旦跑起来，出问题就是黑盒。**

在 C# 生态里，这两件事你已经习以为常：

- **日志**：`NLog` / `Serilog` / `log4net`，一行 `logger.Info("...")` 就把时间、级别、调用栈、线程 ID 写进文件或控制台。`Trace.WriteLine` 配合 `Trace.Listeners` 是 .NET 原生的轻量方案。
- **配置**：`Properties.Settings.Default.Xxx` 读的是编译进程序的强类型配置；`app.config` / `web.config` 是 XML 配置文件；`ConfigurationManager` 读连接串、开关项。

为什么一个正经的工业数据采集软件**必须一上来就建好这两块**？

1. **现场排障靠日志**。多通道采集跑在客户现场，程序崩了、帧丢了、网络断了，你不可能到现场去 `debugger`。日志必须把"时间 / 线程 / 级别 / 模块 / 消息"五要素写下来，崩溃之后翻日志就能定位是采集线程、协议解析还是 UI。
2. **设备参数靠配置**。通道数、采样率、串口/网口参数、报警阈值——这些**不能写死在代码里**。写死意味着每次改参数都要重新编译发布；工业现场改个通道数就要求"重新出一次软件"，这是灾难。
3. **WPF 里有框架替你兜底，Qt 里没有**。.NET 自带 `Trace` 和 `Settings` 两套基础设施；Qt 只给了低级的 `qDebug()/qWarning()`（打控制台）和 `QSettings`（通用配置），**没有官方日志库**。所以"自建 `LogManager`"和"封装 `ConfigManager`"是本工程 **P6 / P7 两个阶段的任务**——它们不是业务功能，是**所有后续模块（UI/采集/协议/线程）都依赖的地基**。

这正是开发规范 §9 早就立下的规矩：**统一走 `LogManager`（P6 起），禁止裸 `qDebug()` 到控制台**；§8 要求"每类错误必须写日志"。本文档就是把这套规范翻译成"怎么实现、为什么这么实现"。

## 2. WPF → Qt 对照总表

| WPF / C# | Qt / C++ |
|----------|----------|
| NLog / log4net / Serilog / `System.Diagnostics.Trace` | Qt 没有官方日志库，工程自建 `LogManager`（本实践） |
| `Trace.WriteLine(msg)` / `logger.Info(msg)` | `LogManager::instance().info(module, msg)` |
| 日志级别 `Trace/Debug/Info/Warn/Error/Fatal` | 自定义 `enum class LogLevel { Debug, Info, Warn, Error, Fatal }` |
| `Properties.Settings.Default.Xxx` | `QSettings`（Qt 官方）或自建 `ConfigManager`（本实践） |
| `app.config` / `web.config`（XML） | `datascope-config.ini`（INI 文本） |
| 单例 `static Lazy<Log> Instance` | **Meyer's Singleton**：函数内 `static` 局部变量 |
| `lock(lockObj)`（Monitor） | `QMutex` + `QMutexLocker`（RAII 加锁） |
| `event EventHandler<LogMsg> OnLog` | `signal messageLogged(LogLevel, QString, QString)` |
| `Trace.Listeners` / `logger.Configure()` | 全局唯一 `LogManager::instance()` + 一次性 `init(path)` |

**逐行讲解**（挑容易误解的几行）：

- **日志库**：.NET 有官方+第三方日志生态，Qt **没有**。`qDebug()` 只打控制台，且`日志规范`禁止裸用；工程自建一个 `LogManager` 单例，全项目一行 `LogManager::instance().info(...)` 统一出口。
- **级别**：C# 习惯 `Trace/Debug/Info/Warn/Error/Fatal`；Qt 没有内置枚举，我们用 `enum class LogLevel` 自定义，**`enum class` 是强类型枚举**——不会像 C# `enum` 那样能隐式转 `int`（C++ 里 `if (level < LogLevel::Info)` 需要显式转换）。
- **配置**：`Properties.Settings.Default` 是编译期强类型访问；Qt 的 `QSettings` 是**运行时按字符串 key 读 `QVariant`**，是弱类型。我们包一层 `ConfigManager` 把"字符串 key → 强类型"的转换收口。
- **单例**：C# 用 `Lazy<T>` 保证线程安全的懒初始化；C++ 更简单——函数内 `static` 局部变量，C++11 起**编译器保证初始化线程安全**（详见 3.3）。
- **锁**：C# 的 `lock` 用的是 `Monitor`（**可重入**）；Qt 的 `QMutex` 默认**不可重入**（同线程重复 lock 会死锁），这是 C# 转 Qt 最容易撞的坑（详见 3.4）。
- **信号推送**：WPF 里你想把日志实时刷到 UI 就 `event OnLog += ...`；Qt 里让 `LogManager` 继承 `QObject` 后声明一个 `signal messageLogged(...)`，UI 用 `connect` 订阅（详见 4.3）。注意 Qt 的**信号槽天然跨线程**（AutoConnection），后台线程 `emit`、UI 线程自动排队收到——这正是日志面板想要的效果。

## 3. Qt 原理深入

### 3.1 QSettings 的三种存储与 Windows 上的"配置文件找不到"之谜

> 一句话类比：C# 的 `Settings` 只有"配置文件"这一种形态；Qt 的 `QSettings` 是"一个接口，N 种后端"——在 Windows 上默认后端是**注册表**，不是文件！

**机制讲解**

`QSettings` 的完整签名是 `QSettings(format, scope, organization, application)`，它有 **Format（格式）** 和 **Scope（作用域）** 两个维度：

| 维度 | 取值 | 含义 |
|------|------|------|
| Format | `QSettings::NativeFormat` | **平台原生**：Windows 上就是注册表 `HKEY_CURRENT_USER\Software\<组织>\<应用>`；Unix/Linux 上是 INI 文件 |
| Format | `QSettings::IniFormat` | 强制用 **INI 纯文本文件**（不依赖注册表） |
| Scope | `QSettings::UserScope` | 当前用户级（可写，对应 `%APPDATA%` / 注册表 HKCU） |
| Scope | `QSettings::SystemScope` | 系统级（全机器共享，通常需要管理员权限） |

关键点：**在 Windows 上，`NativeFormat` 就是注册表**。如果你不指定格式，`QSettings("MyOrg", "DataScope")` 就会把配置写进注册表。

**为什么工程要显式 `QSettings::IniFormat` + 文件路径？**

1. **可读、可审计**：注册表用 `regedit` 才能看，INI 用记事本/`git diff` 就能看。工业软件的配置应该**人类可读、可进版本库**，方便评审和回滚。
2. **可迁移**：把 `datascope-config.ini` 拷到另一台机器 = 配置迁移完成。注册表做不到"拷一个文件过去"。
3. **避免"配置文件找不到"**：注册表是隐形的，客户/同事找不到"配置文件在哪"，也说不清"配置到底存没存上"。显式指定一个 `config/datascope-config.ini` 路径，**文件就在那里**，谁也骗不了谁。
4. **工程管理**：路径写死、行为确定，单测也好隔离（见错误案例 4 的 `QTemporaryDir`）。

推荐的构造方式（设计意图）：

```cpp
// 显式指定：绝对路径 + IniFormat，绝不落到注册表
const QString iniPath = QCoreApplication::applicationDirPath()
                        + QStringLiteral("/config/datascope-config.ini");
QSettings settings(iniPath, QSettings::IniFormat);
```

> 注意：`applicationDirPath()` 是"可执行文件所在目录"。开发阶段把配置放在 exe 旁方便调试；**正式安装部署**（如装到 `C:\Program Files\`，普通用户无权写）则应改用 `QStandardPaths::writableLocation(QStandardPaths::AppConfigLocation)`——它返回 `%APPDATA%\<组织>\<应用>`，永远可写。开发 vs 部署的取舍，第 4.2 节 `ConfigManager` 会再讲。

**为什么不能简单照搬 C# 思维**

- C# 里 `app.config` 永远是文件、永远在 exe 旁；Qt 里"不指定就是注册表"，照搬"我存了配置"的习惯，**配置实际进了注册表**，你在文件系统里永远找不到它。
- C# `Settings` 是**强类型**（`Settings.Default.Channels` 编译期类型确定）；Qt `QSettings` 读回来是 `QVariant`，类型转换是你的责任（见 3.2）。

**在 DataScope 里的落地**：`ConfigManager::init()` 用上面推荐写法，把 `iniPath` 显式传给 `QSettings(iniPath, QSettings::IniFormat)`，并在文档/头文件注释里写明"为什么不用 NativeFormat"。

### 3.2 QSettings 的类型转换与 QVariant 原理

> 一句话类比：`QVariant` 是 C++ 版的"万能盒子"——接近 C# 的 `object` 装箱，但**盒子里能放什么类型是预先登记的**，取出来时必须用对应的 `toXxx()` 拆箱。

**机制讲解**

`QSettings::value(key)` 永远返回 `QVariant`。`QVariant` 是一个**类型擦除（type-erased）容器**：它能在运行时持有 `int` / `double` / `QString` / `bool` / `QByteArray` / 容器等一大批已知类型中的任意一种。这解决的是 C++ "一个变量只能有一种编译期类型"的限制。

```cpp
// 写入：setValue 接受任意"能变成 QVariant"的值
settings.setValue("channels", 8);            // int → QVariant(int)
settings.setValue("sampleRate", 1000.0);     // double
settings.setValue("serialPort", "COM3");     // QString
settings.setValue("enabled", true);          // bool

// 读取：value() 返回 QVariant，必须用 toXxx() 转换
int ch = settings.value("channels", 0).toInt();          // 取不到时用默认值 0
double rate = settings.value("sampleRate", 0.0).toDouble();
QString port = settings.value("serialPort").toString();  // 空 QVariant → 空串
bool en = settings.value("enabled", false).toBool();
```

几个关键行为：

1. **默认值**：`value(key, defaultValue)` 的第二个参数就是"key 不存在时返回的默认值"。**空 `QVariant` 的 `toInt()` 是 0、`toString()` 是空串**——如果你不传默认值，读一个不存在的 key 会"静默拿到类型默认值"，而不是报错。C# 的 `Settings` 永远有 app.config 兜底值，Qt 没有——**每次读取都要给默认值**，这是配置代码的第一个好习惯。
2. **类型不匹配时**：存 `int` 读 `toDouble()` 也能成（C++ 数值提升）；存字符串 "abc" 读 `toInt()` 会得到 0。`QVariant` 提供 `canConvert<T>()` 可以事先探测，但工程里我们约定"**配置里是什么类型就用什么类型读**"，靠 `ConfigManager` 收口。
3. **INI 存储规则**：`QSettings` 把 `QVariant` 序列化成 INI 文本。布尔值存成 `true/false`，数值存成数字文本，字符串直接存。中文字符串存 INI 时按 UTF-8 处理（`QSettings` 内部对 INI 有编码处理）。
4. **键的组织**：INI 用 `/` 表达分组，等价于注册表的分层 key。`settings.setValue("ui/theme", "dark")` 在 INI 里就是 `[ui]` 节下的 `theme=dark`。C# 里没有"节"概念，这里要适应 INI 的**节（section）**结构。

**为什么不能简单照搬 C# 思维**

- C# `Settings.Default.X` 是**编译期强类型**，写错类型编译器就报错；Qt 是**运行时字符串 key + `QVariant`**，写错 key 名、读错类型**都不报错**，只是静默给默认值/0。所以必须靠 `ConfigManager` 封装一层"命名 + 默认值 + 类型转换"的收口，把运行时错误变成**一处定义、处处安全**。
- `QVariant` 的转换是"尽力而为"（C++ 语义），不是 C# 的 `Convert.ToXxx` 那么严格。别指望它替你校验非法输入——非法输入的处理仍要遵循规范 §8：**校验 + 日志 + 默认值**。

**在 DataScope 里的落地**：`ConfigManager` 暴露 `intValue(key, def)` / `doubleValue(...)` / `boolValue(...)` / `stringValue(...)` 四个强类型方法，内部统一调 `settings.value(key, def).toXxx()`，把 `QVariant` 的弱类型关在门内。

### 3.3 Meyer's Singleton：C++11 线程安全的"懒汉"单例

> 一句话类比：C# 用 `Lazy<T>` 的 `ExecutionAndPublication` 模式保证"多线程下只造一个 + 线程安全"；C++ 用**函数内 `static` 局部变量**，编译器替你完成同样的事——更短、更快、零额外对象。

**代码对比**

```csharp
// C#：Lazy<T> 显式声明线程安全模式
private static readonly Lazy<Log> _inst =
    new Lazy<Log>(() => new Log(), LazyThreadSafetyMode.ExecutionAndPublication);
public static Log Instance => _inst.Value;
```

```cpp
// C++：Meyer's Singleton —— 函数内 static 局部变量
static LogManager &instance() {
    static LogManager inst;   // C++11 保证：首次并发初始化时，其他线程在此等待
    return inst;
}
```

**机制讲解**

1. **函数内 `static` 局部变量（function-local static）**：它的生命周期从"首次执行到这一行"开始，到程序退出时结束。首次进入这一行时构造对象，之后每次调用都直接返回同一个实例。
2. **C++11 标准保证**（`[stmt.dcl]`）：如果多个线程**同时**首次进入这个声明，且变量正在初始化，那么**其他线程必须阻塞等待初始化完成**，之后看到的都是已初始化完的对象。换句话说，编译器（和标准库）内部已经给你插好了**一次性初始化锁（guard）**，**不需要你自己写 double-checked locking**。
3. 对比 C# `Lazy<T>`：两者思想一致——"懒加载 + 线程安全"。C++ 版连 `Lazy` 包装对象都省了，`static` 局部变量本身就是那个"懒 + 锁 + 实例"的三合一。注意：**C++11 之前的编译器不保证这个**，但本项目用 Qt 5.12 自带的 MinGW 7.3（C++17），完全放心。
4. **为什么不用类内 `static` 成员变量**（`static LogManager m_instance;`）？因为类内静态成员的初始化顺序**跨编译单元不确定**（即著名的 *static initialization order fiasco*），且它**没有线程安全保证**。函数内 static 是"首次调用时初始化"，顺带解决了这两个问题。

**为什么不能简单照搬 C# 思维**

- C# 的"单例"和 C++ 的"单例"看着像，但 C# 里 `static Lazy<Log>` 是**类字段**，天然安全；C++ 里如果照着 C# 写**类内 static 成员**，反而踩初始化顺序的坑。**C++ 正确写法就是函数内 static**。
- **析构时机**：程序退出时，`static` 局部变量按构造的**逆序**析构。如果别的 static 对象的析构函数在退出阶段调用 `LogManager::instance()`，而它已经被析构了 → 崩溃。工业软件里一个常见妥协是**故意泄漏**（不析构）——`static auto *p = new LogManager; return *p;`——换来"永远活着，随时可用"。教学项目用标准版即可，但要知道这个变体存在。

**在 DataScope 里的落地**：`LogManager::instance()` / `ConfigManager::instance()` 都用 Meyer's Singleton。私有构造函数 + `Q_DISABLE_COPY`（禁止拷贝），杜绝"再 new 一个"和"复制一份"。

### 3.4 QMutex / QMutexLocker：RAII 加锁与 C# lock 的异同

> 一句话类比：`lock(lockObj)` 和 `QMutexLocker` 都是"进了作用域上锁、出了作用域自动解锁"，但 C# 的 Monitor **可重入**，Qt 的 `QMutex` **默认不可重入**——C# 里随手的嵌套 `lock`，搬到 Qt 就是同线程死锁。

**代码对比**

```csharp
// C#：lock 语句，Monitor 可重入，出了作用域自动释放
private readonly object _lock = new object();
public void Append(string line) {
    lock (_lock) {                       // 再嵌套一层 lock 也合法
        _file.Append(line);
    }
}
```

```cpp
// C++：QMutex + QMutexLocker，RAII 自动解锁
static QMutex s_mutex;                   // 跨线程共享的锁
void appendLine(const QString &line) {
    QMutexLocker locker(&s_mutex);       // 构造 = lock；析构 = unlock
    file.append(line);
}                                        // 这里 locker 析构，自动解锁
```

**机制讲解**

1. **QMutex 是什么**：一个互斥量（mutual exclusion），保证"同一时刻只有一个线程持有它"。`QMutexLocker locker(&mutex);` 构造时 `lock()`，作用域结束（函数返回、`{}` 结束、提前 `return`、抛异常）时**析构自动 `unlock()`**——这就是 RAII 加锁，对应 C# `lock` 的"离开作用域自动释放"。
2. **RAII 锁的好处**：C# 的 `lock` 依赖编译器生成的 `try/finally`；C++ 依赖对象析构。**提前 `return` 时，`locker` 析构照样执行**，不会像裸 `mutex.lock(); ...; return;`（忘写 `unlock()`）那样把锁锁死。规范 §6"RAII 优先"在这里具象成"**用 `QMutexLocker`，永远不裸调 `lock()/unlock()`**"。
3. **与 C# 的关键差异——可重入性**：
   - C# `Monitor` 是**可重入（reentrant）**：同一线程可以重复 `lock` 同一对象，内部有计数器。
   - Qt `QMutex` **默认不可重入**：同一线程对同一把锁连续 `lock()` 两次 → **死锁**（Qt 调试模式下会打印警告）。
   - 对应：Qt 5.12 里构造 `QMutex(QMutex::Recursive)` 才是可重入模式；Qt 5.14+ 有更清晰的 `QRecursiveMutex`。**能不用递归锁就别用**——递归锁通常说明代码结构有问题（持锁时间过长）。
4. **等待/唤醒（condition）**：C# 的 `Monitor.Wait/Pulse` 对应 Qt 的 `QWaitCondition` + `QMutex` 配合使用。`lock` 本身在 C# 里带条件等待能力，Qt 拆成了两个类。本文只讲互斥，条件等待到线程章节再展开。

**为什么不能简单照搬 C# 思维**

1. **可重入假设要丢掉**：C# 里"锁里再调一个也 lock 同一对象的方法"很正常；Qt 里这是死锁。**持锁区间要短、要单层**。
2. **锁的顺序**：多把锁同时持有要**全工程统一加锁顺序**，否则两个线程各持一把锁等另一把 → 死锁。规范 §7 要求跨线程共享容器用 `QMutex` 保护，正是这个道理。
3. **别在 UI 线程持锁等 I/O**：日志写文件会慢，如果 UI 线程在持锁状态下等待文件 I/O，界面会卡。所以日志的锁**只保护内存缓冲到文件这一小段**，不要锁着整个日志对象的对外接口（见 4.1 的设计：`init` 和 `writeLine` 各锁各的、不嵌套）。

**在 DataScope 里的落地**：`LogManager` 用 `QMutex` 保护 `m_file` 的写入；`ConfigManager` 主要在 UI/采集线程初始化阶段读一次配置，写入集中在启动/设置页，锁粒度小。**采集线程（工作线程）写日志、UI 线程写日志，都进 `LogManager::writeLine` 的同一把锁**，保证日志行不交错。

### 4.1 LogManager —— 全局日志管理器

**头文件 `src/utils/logmanager.h`**

```cpp
/**
 * @file logmanager.h
 * @brief 全局日志管理器（P6 设计意图稿）
 *
 * 对应 C# 的 NLog/Serilog 的静态 Logger 用法：
 *   C#:  logger.Info(msg)
 *   Qt:  LogManager::instance().info(module, msg)
 *
 * 设计要点：
 *   1. Meyer's Singleton —— 全进程唯一出口（见本文 3.3）；
 *   2. 私有构造函数 + Q_DISABLE_COPY —— 禁止再创建、禁止复制；
 *   3. 消息模板对齐开发规范 §9：
 *      [时间] [线程ID] [级别] [模块] 消息
 *   4. QMutex + QMutexLocker —— 多线程（采集线程/UI 线程）写文件互斥（见本文 3.4）。
 */

#pragma once

#include <QString>
#include <QFile>
#include <QMutex>

namespace datascope {
namespace utils {

// 日志级别：对应 C# 的 Trace/Debug/Info/Warn/Error/Fatal
enum class LogLevel {
    Debug = 0,   // 调试：只在本机开发时关注
    Info  = 1,   // 普通信息：启动、连接、参数
    Warn  = 2,   // 警告：不致命但可疑（如重试、校验失败）
    Error = 3,   // 错误：本模块失败但可恢复（如一条帧解析失败）
    Fatal = 4    // 致命：程序即将退出（如初始化失败）
};

class LogManager
{
public:
    static LogManager &instance();      // Meyer's Singleton，见 logmanager.cpp

    // 初始化日志目录。幂等：重复调用只生效第一次。
    void init(const QString &logDir);

    // 运行时调节最低级别：低于它的日志被丢弃（如发布时切到 Warn）
    void setMinLevel(LogLevel level);

    // 统一出口：level + 模块名 + 消息
    void log(LogLevel level, const QString &module, const QString &msg);

    // 便捷包装：LogManager::instance().info("UI", "主窗口已创建")
    void debug(const QString &module, const QString &msg);
    void info (const QString &module, const QString &msg);
    void warn (const QString &module, const QString &msg);
    void error(const QString &module, const QString &msg);
    void fatal(const QString &module, const QString &msg);

private:
    LogManager() = default;             // 私有构造：只有 instance() 能创建
    ~LogManager() = default;
    Q_DISABLE_COPY(LogManager)          // 禁止拷贝（QFile/QMutex 本来就不可拷贝）

    void writeLine(LogLevel level, const QString &module, const QString &msg);
    static QString levelToString(LogLevel level);   // 枚举 → 字符串标签
    void ensureFile();                              // 确保日志文件已打开

    QFile    m_file;      // RAII 文件句柄：析构自动关闭
    QMutex   m_mutex;     // 写文件互斥锁（见 3.4）
    LogLevel m_minLevel = LogLevel::Debug;   // 当前最低级别
    bool     m_ready = false;                // init 是否成功
};

} // namespace utils
} // namespace datascope
```

**实现 `src/utils/logmanager.cpp`**

```cpp
/**
 * @file logmanager.cpp
 * @brief LogManager 实现（P6 设计意图稿）
 */

#include "logmanager.h"

#include <QDir>          // 目录操作
#include <QDateTime>     // 时间戳
#include <QThread>       // 线程 ID
#include <QCoreApplication>

namespace datascope {
namespace utils {

// ---------- Meyer's Singleton ----------
LogManager &LogManager::instance()
{
    static LogManager inst;   // C++11：首次并发调用也线程安全（见 3.3）
    return inst;
}

// ---------- 初始化：建目录、开文件（幂等） ----------
void LogManager::init(const QString &logDir)
{
    QMutexLocker locker(&m_mutex);   // RAII：作用域结束自动解锁
    if (m_ready) {
        return;                      // 已初始化过，直接返回（幂等）
    }

    // mkpath 会递归创建多级目录：logs/ 不存在就逐级建出来
    QDir dir(logDir);
    if (!dir.exists() && !dir.mkpath(logDir)) {
        return;                      // 目录都建不起来，放弃（此时没有地方可写日志）
    }

    const QString filePath = logDir + QStringLiteral("/datascope.log");
    m_file.setFileName(filePath);

    // Append 追加写、Text 用文本模式（避免 Windows 下换行被吃/被转换的怪问题）
    m_ready = m_file.open(QIODevice::WriteOnly | QIODevice::Append | QIODevice::Text);
}

// ---------- 级别过滤后写入 ----------
void LogManager::log(LogLevel level, const QString &module, const QString &msg)
{
    if (level < m_minLevel) {
        return;                      // 低于当前最低级别，直接丢弃
    }
    writeLine(level, module, msg);
}

// ---------- 核心：格式化 + 加锁写文件 ----------
void LogManager::writeLine(LogLevel level, const QString &module, const QString &msg)
{
    QMutexLocker locker(&m_mutex);   // 采集线程/UI 线程并发写时互斥（见 3.4）

    if (!m_ready) {
        return;                      // init 失败或未 init，静默丢弃
    }

    // 消息模板（规范 §9）：[时间] [线程ID] [级别] [模块] 消息
    const QString line = QStringLiteral("[%1] [%2] [%3] [%4] %5\n")
        .arg(QDateTime::currentDateTime().toString(Qt::ISODate))          // 时间
        .arg(QString::number(reinterpret_cast<quintptr>(                  // 线程 ID
                 QThread::currentThreadId())))
        .arg(levelToString(level))                                        // 级别
        .arg(module)                                                      // 模块
        .arg(msg);                                                        // 消息

    m_file.write(line.toUtf8());      // 统一按 UTF-8 落盘
    m_file.flush();                   // 立即刷盘：程序崩溃前日志已落盘可查
}

// ---------- 级别 → 字符串标签 ----------
QString LogManager::levelToString(LogLevel level)
{
    switch (level) {
    case LogLevel::Debug: return QStringLiteral("DEBUG");
    case LogLevel::Info:  return QStringLiteral("INFO");
    case LogLevel::Warn:  return QStringLiteral("WARN");
    case LogLevel::Error: return QStringLiteral("ERROR");
    case LogLevel::Fatal: return QStringLiteral("FATAL");
    }
    return QStringLiteral("UNKNOWN");
}

// ---------- 五个便捷包装 ----------
void LogManager::debug(const QString &module, const QString &msg) { log(LogLevel::Debug, module, msg); }
void LogManager::info (const QString &module, const QString &msg) { log(LogLevel::Info,  module, msg); }
void LogManager::warn (const QString &module, const QString &msg) { log(LogLevel::Warn,  module, msg); }
void LogManager::error(const QString &module, const QString &msg) { log(LogLevel::Error, module, msg); }
void LogManager::fatal(const QString &module, const QString &msg) { log(LogLevel::Fatal, module, msg); }

} // namespace utils
} // namespace datascope
```

**逐块讲解（阅读重点）**

1. **`enum class LogLevel`**：强类型枚举。C# 的 `enum` 能隐式转 `int`，C++ 的 `enum class` **不能**——所以 `level < m_minLevel` 能编译，是因为同一枚举类型可以直接比较；若想转 `int` 必须显式 `static_cast<int>`。好处是**类型安全**：不会拿个 `int` 误当级别传进来。
2. **`static LogManager inst;`**：函数内 static 局部变量（3.3），**全进程唯一实例**，首次调用时构造。
3. **`init` 里的 `QMutexLocker locker(&m_mutex);`**：函数开头就加锁，但只锁到"开文件"结束。与 `writeLine` 里**各自独立的锁**不嵌套——避免"锁里等锁"。而且 `init` 持锁区间很短，不卡其它调用。
4. **`m_file.flush()`**：每行都 flush 是**牺牲一点性能换可靠性**。工业现场日志不能依赖"进程退出时才落盘"——程序可能崩溃，崩之前写进缓冲的日志就丢了。教学项目选"每行刷盘"，实测发现性能不足再改成"定时批量刷盘"。
5. **线程 ID 显示**：`QThread::currentThreadId()` 返回平台句柄（void*），转成整数打印——排查"哪条日志是哪个线程写的"最有用，正是规范 §9 模板要线程 ID 的原因。
6. **`init` 失败静默**：日志系统本身失败了**不该抛异常**——因为"日志炸了不能把程序炸了"。这是日志组件和普通组件的最大区别：**日志永远不能成为崩溃源**。

### 4.2 ConfigManager —— INI 配置管理器

**头文件 `src/utils/configmanager.h`**

```cpp
/**
 * @file configmanager.h
 * @brief 全局配置管理器（P7 设计意图稿）
 *
 * 对应 C# 的 Properties.Settings.Default：
 *   C#:  Settings.Default.Channels / Settings.Default.SampleRate
 *   Qt:  ConfigManager::instance().intValue("device/channels", 8)
 *
 * 为什么包一层而不是直接裸用 QSettings：
 *   1. QSettings 读回来是 QVariant（弱类型），包一层把类型转换收口；
 *   2. key 的命名、默认值集中一处定义，全项目一致；
 *   3. 显式 IniFormat + 文件路径，绝不落注册表（见本文 3.1、错误案例 2）。
 */

#pragma once

#include <QString>
#include <QVariant>
#include <memory>

namespace datascope {
namespace utils {

class ConfigManager
{
public:
    static ConfigManager &instance();                 // Meyer's Singleton

    // 绑定 INI 文件路径并打开。可重复调用，最近一次生效。
    bool init(const QString &iniFilePath);

    // 强类型读取：key 不存在/类型不匹配时返回默认值 def
    QString stringValue(const QString &key, const QString &def = QString()) const;
    int     intValue   (const QString &key, int def = 0) const;
    double  doubleValue(const QString &key, double def = 0.0) const;
    bool    boolValue  (const QString &key, bool def = false) const;

    // 强类型写入 + 显式刷盘
    void setValue(const QString &key, const QVariant &value);
    void sync();                                      // 把内存改动写回磁盘

private:
    ConfigManager() = default;
    Q_DISABLE_COPY(ConfigManager)

    std::unique_ptr<QSettings> m_settings;   // 组合：路径在 init 时才确定，故用指针
};

} // namespace utils
} // namespace datascope
```

**实现 `src/utils/configmanager.cpp`**

```cpp
/**
 * @file configmanager.cpp
 * @brief ConfigManager 实现（P7 设计意图稿）
 */

#include "configmanager.h"

#include <QSettings>
#include <QCoreApplication>
#include <QStandardPaths>   // 部署场景取 AppConfigLocation 用

namespace datascope {
namespace utils {

ConfigManager &ConfigManager::instance()
{
    static ConfigManager inst;   // Meyer's Singleton（见 3.3）
    return inst;
}

bool ConfigManager::init(const QString &iniFilePath)
{
    // 显式 IniFormat + 文件路径：Windows 上绝不落注册表（见错误案例 2）
    m_settings.reset(new QSettings(iniFilePath, QSettings::IniFormat));

    // QSettings::status() 检查是否能正常访问：NoError 才成功
    return m_settings->status() == QSettings::NoError;
}

int ConfigManager::intValue(const QString &key, int def) const
{
    // value(key, def) 的第二个参数就是"key 不存在时返回的默认值"
    // 返回的 QVariant 再 toInt() 完成弱类型 → int 的收口
    return m_settings->value(key, def).toInt();
}

double ConfigManager::doubleValue(const QString &key, double def) const
{
    return m_settings->value(key, def).toDouble();
}

bool ConfigManager::boolValue(const QString &key, bool def) const
{
    return m_settings->value(key, def).toBool();
}

QString ConfigManager::stringValue(const QString &key, const QString &def) const
{
    return m_settings->value(key, def).toString();
}

void ConfigManager::setValue(const QString &key, const QVariant &value)
{
    m_settings->setValue(key, value);
    // 关键写操作后立即落盘，避免"改了配置，程序崩溃后没存上"
    m_settings->sync();
}

void ConfigManager::sync()
{
    m_settings->sync();
}

} // namespace utils
} // namespace datascope
```

**逐块讲解**

1. **为什么用 `std::unique_ptr<QSettings>` 而不是成员对象**：`QSettings` 构造必须给定路径/组织名，而路径到 `init()` 才知道。用 `unique_ptr` 在 `init()` 里 `reset(new QSettings(...))` 延迟构造——这对应 C# 里"字段在构造函数里才 new"的写法。`unique_ptr` 析构自动 `delete`（RAII，见对照指南第 3 节）。
2. **`QSettings::status()`**：Qt 5.3+ 提供，`NoError` 表示文件能正常读写。这是"配置文件路径错了、权限不足"的**第一个探测器**——比"读出来全是默认值"好排查得多。
3. **`value(key, def)` 双参数**：所有读接口都强制带默认值，把 3.2 讲的"空 QVariant 陷阱"在源头堵死。
4. **`setValue` 里主动 `sync()`**：`QSettings` 默认是**延迟落盘**（内存缓存，析构/定期才写回）。对"用户刚改完参数"这种关键操作，**立即 sync** 保证断电/崩溃不丢配置。普通批量写入可以攒着最后一次性 `sync()`。
5. **为什么是组合不是继承**：`ConfigManager` 内部持有 `QSettings`（composition），而不是 `class ConfigManager : public QSettings`。因为我们要暴露的是**强类型 + 命名约定**的接口，不是让调用者直接看到 QSettings 的全部能力——接口最小化，符合"实现细节关在门内"。

### 4.3 （可选进阶）把日志推送到 UI：LogManager 加一个信号

WPF 里你要实时日志面板，就 `event OnLog += ...`。Qt 里让 `LogManager` 继承 `QObject` 并声明一个信号，UI 用 `connect` 订阅。**信号槽跨线程自动排队**——采集线程 `emit`，UI 线程在事件循环里安全收到，这正是日志面板想要的行为（对应对照指南第 5 节）。

```cpp
// 设计意图：仅在需要"日志实时推送到 UI"时启用
class LogManager : public QObject
{
    Q_OBJECT                        // 声明信号必须要有 Q_OBJECT + QObject 基类
public:
    static LogManager &instance();
    // ...其余同 4.1...

signals:
    // 级别 + 模块 + 消息 三段式，对应 C# 的 EventHandler<LogMsg>
    void messageLogged(LogLevel level, const QString &module, const QString &msg);

private:
    // writeLine 里在写文件的同时 emit：
    //   emit messageLogged(level, module, msg);
};

// 主窗口订阅（UI 线程）：
// LogManager::instance().connect(
//     &LogManager::instance(), &LogManager::messageLogged,
//     this, [this](LogLevel lv, const QString &mod, const QString &msg) {
//         appendLogToView(lv, mod, msg);   // 更新日志 QTextEdit / QTableView
//     });
```

**要点**：
- 只有 **QObject 子类 + `Q_OBJECT`** 才能有信号（对照指南第 5 节）；纯工具类不需要 QObject 就别继承。
- `connect` 第 3 个参数 `this` 是 context 对象，保证 `this`（主窗口）析构时自动断连，不产生悬垂（对照指南错误案例 3）。
- 加了信号后，`LogManager` 仍是单例，但 `Q_OBJECT` 要求类有**且只有一个 QObject 身份**——Meyer's Singleton 的 `static` 局部变量与 `QObject` 不冲突（构造函数私有即可）。

## 5. 错误案例：把 C# 思维直接搬进 Qt 会踩的坑

### 错误案例 1：日志写进用户文档目录 / 污染工作目录

**C# 惯性**：`File.AppendAllText("app.log", ...)` 无所谓写哪，反正有固定目录。

**Qt 照搬**：

```cpp
// 直接拿当前工作目录写日志
QFile f(QStringLiteral("app.log"));
f.open(QIODevice::Append);
```

- **现象**：日志文件跑到"当前工作目录"（CWD）——Windows 上从资源管理器双击启动时 CWD 可能是 `C:\Windows\System32` 或 exe 目录；从命令行启动又变成另一个地方。日志"一会儿在这、一会儿在那"，还污染工程目录，`git status` 里全是 `app.log`。
- **更糟的情况**：装在 `Program Files` 下普通用户无写权限 → 打开文件失败 → **日志静默丢失**（`open()` 返回 false 没人检查）。
- **根因**：C# 有固定 AppData 约定，Qt 里"日志放哪"要**自己用 `QStandardPaths` 显式决定**。
- **正确写法**：

```cpp
// 日志目录放到用户可写的 AppData 下，或应用目录的 logs/ 子目录
const QString logDir = QStandardPaths::writableLocation(QStandardPaths::AppDataLocation)
                       + QStringLiteral("/logs");   // Windows: %APPDATA%/<org>/<app>/logs
QDir().mkpath(logDir);                              // 递归创建，不存在就建
LogManager::instance().init(logDir);
```

- **对照**：C# 里 `Environment.GetFolderPath(ApplicationData)` 做的事，Qt 里是 `QStandardPaths::writableLocation(AppDataLocation)`。**目录自己建、权限自己验、失败要能发现**——这三点是 C# 开发者最容易忽略的。

### 错误案例 2：Windows 上 QSettings 默认写注册表，"配置文件找不到"

**C# 惯性**：`Settings.Default.X = 8; Settings.Default.Save();` → 配置文件一定在 exe 旁边。

**Qt 照搬**：

```cpp
// 以为这样就是"写一个配置文件"
QSettings settings(QStringLiteral("datascope-config.ini"));
settings.setValue("device/channels", 8);
settings.sync();   // 写完了，配置文件呢？
```

- **现象**：程序"能存能读"（`value` 读得回来），但 exe 目录、工程目录里**永远没有 `datascope-config.ini`**。换台机器、重装系统，配置全部"消失"。用 `regedit` 一看，`HKEY_CURRENT_USER\Software\datascope-config.ini` 底下躺着一堆值。
- **根因**：`QSettings("文件路径")` 的单参数构造，**format 默认是 `NativeFormat`**——在 Windows 上 `NativeFormat` 就是**注册表**。字符串参数被当成"注册表路径"而不是文件路径。**它没有报错，看起来一切正常**，所以最隐蔽。
- **正确写法**：

```cpp
// 显式指定格式 + 绝对路径
const QString iniPath = QCoreApplication::applicationDirPath()
                        + QStringLiteral("/config/datascope-config.ini");
QSettings settings(iniPath, QSettings::IniFormat);   // IniFormat！绝不落注册表
```

- **补充**：开发阶段用 `applicationDirPath()`（exe 旁，好找）；正式部署改用 `QStandardPaths::AppConfigLocation`（永远可写）。**绝对路径 + IniFormat**，两个条件缺一不可。
- **对照**：C# 里"配置=文件"是默认；Qt 里"配置=注册表"才是 Windows 默认。**必须显式打破默认**。

### 错误案例 3：多线程写日志不加锁

**C# 惯性**：`lock` 或 `ConcurrentQueue` 帮我解决并发，随手写 `File.AppendAllText` 其实也线程不安全，但很少撞上。

**Qt 照搬**：

```cpp
// 两个线程都在写同一个 QFile，谁也没加锁
void workerA() { LogManager::instance().writeLine(LogLevel::Info, "A", "采样完成"); }
void workerB() { LogManager::instance().writeLine(LogLevel::Info, "B", "帧到达"); }
// writeLine 内部：m_file.write(line.toUtf8()); m_file.flush();   // 没有锁！
```

- **现象**：日志行互相穿插（"采帧到"、"样达完"）——**一行被撕成两半**；严重时 `QTextStream`/`QFile` 内部游标错乱、崩溃。
- **根因**：`QFile::write` 不是原子操作。两个线程同时调用，`m_file` 的写入位置被并发修改。C# 里你以为 `File.AppendAllText` 自带锁（其实没有），Qt 里**没有任何隐式锁**。
- **正确写法**：用 `QMutex` + `QMutexLocker` 保护整个"格式化 + 写入 + flush"区间（见 4.1 的 `writeLine`）。

```cpp
void LogManager::writeLine(LogLevel level, const QString &module, const QString &msg)
{
    QMutexLocker locker(&m_mutex);   // 这一行就是全部加锁，作用域结束自动解锁
    if (!m_ready) return;
    // 格式化 + m_file.write + m_file.flush 都在锁内，保证整行不被撕开
}
```

- **对照**：C# 的 `lock` 语句 ≈ Qt 的 `QMutexLocker`，但记住 Qt 锁**不可重入**（3.4）——别在锁内再进一个也要这把锁的函数。另外别用"每行 `open/append/close`"当无锁方案，那是用性能换安全，还不如一把锁。

### 错误案例 4（补充）：单测日志落进真实目录污染环境

**C# 惯性**：测试里直接调 `Logger.Info(...)`，跑完测试目录里全是日志文件，用 `.gitignore` 眼不见为净。

**Qt 照搬**：

```cpp
// 单元测试直接往工程目录写日志
LogManager::instance().init(QStringLiteral("./logs"));   // 每次跑测试都在工程里堆日志
```

- **现象**：跑一遍单测，`./logs` 一堆测试日志进 `git status`；CI 环境还可能因为目录权限失败。
- **根因**：测试没有隔离副作用。工业代码的日志/配置路径如果写死，单测就没法"跑一次、清干净"。
- **正确写法**：用 `QTemporaryDir`（Qt 自带临时目录类）——构造时创建唯一临时目录，**析构自动删除**。

```cpp
#include <QTemporaryDir>

void testLogManagerInit()
{
    QTemporaryDir tmpDir;                    // 自动生成唯一临时目录
    QVERIFY(tmpDir.isValid());               // 创建失败直接判失败

    const QString logDir = tmpDir.path() + QStringLiteral("/logs");
    LogManager::instance().init(logDir);     // 日志落在临时目录
    LogManager::instance().info("TEST", "write something");

    // 测试结束，tmpDir 析构 → 临时目录连同日志自动删除，环境零污染
}
```

- **顺带**：`ConfigManager` 的测试同理——把 INI 路径指到 `tmpDir.path()`，测完自动清理。这正是 3.1 强调"**路径显式传入**"的回报：路径可注入，测试才可隔离。C# 里这个手法叫依赖注入；C++/Qt 里就是"构造/init 时把路径作为参数传进来"。
