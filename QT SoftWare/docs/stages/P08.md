## 1. 学了什么

1. **值类型 vs 引用类型**：`Channel`/`DataPoint` 用 `struct`——它们是一次性采样/通道描述这类"轻量数据"，可以整体拷贝、放进容器，拷贝后各持一份互不影响（对应 C# 的 `record`/`POCO`）。`Device` 用 `class`——它"拥有并管理"一组 `Channel`，需要封装只读视图和写入入口（对应 C# 的 `class Device`）。
2. **强类型枚举 `enum class`**：`DeviceStatus` 不会隐式转整数，必须显式写 `DeviceStatus::Connected` 才能用——编译期挡住大量笔误（C# 的 `enum` 本质仍是 `int`，可随意与整数互转，容易写出脏数据）。
3. **`const QVector<Channel>&` 返回"只读引用"**：调用方拿到的是内部数组的一份只读视图而非拷贝——既避免每次读取复制整个数组（性能），又保证只读安全（对应 C# 的 `IReadOnlyList<T>`）。
4. **QVector / QString 的隐式共享（Copy-on-Write）**：拷贝一个 `Device` 非常便宜（共享底层数据、引用计数 +1），只有真正写入时才复制底层数组（detach）。单测 `device_copyIndependent` 专门验证了这一点。
5. **头文件只声明、实现单文件定义**：这样每个 include 本头的 `.cpp` 都不必重复编译实现，加快整体构建（对应 C# 把"声明与实现"分离的惯例）。
6. **纯数据层设计红线**：只依赖 QtCore（QString/QDateTime/QVector），不依赖 UI、不依赖 QtNetwork/SerialPort——任何界面或协议改动都不应波及领域层。

## 2. 为什么学

- **分层架构的基石**：领域模型是"设备是什么"的唯一定义。UI 层、协议层、服务层、采集线程都消费它——**契约先行，接口先定死，各 Agent 才能并行开发而互不踩踏**（这正是本次 M1 与 C1/W1 并行时用到的协作方式）。
- **数据与视图分离**：采集线程产出 `DataPoint`、UI 层绘制曲线，中间的传输格式必须是稳定、可测试的纯数据——这就是领域层存在的意义。
- **WPF 对照**：对应 C# 的 Models 层 / DTO / POCO。C# 有 `IReadOnlyList<T>` 表达只读集合，Qt 用"返回 const 引用"实现同样的只读语义。

## 3. Qt 原理（本阶段）

- **`QVector` 隐式共享的实现**：底层是"指针 + 引用计数 + 写时复制"。拷贝时只复制一个指针并 `ref++`，`append`/`clear` 等写操作触发 `detach()` 才深拷贝底层数组。这让"值语义"在 Qt 容器上几乎零成本。
- **QDateTime 默认构造是"无效时间"**：`isValid()` 返回 `false`。单测 `dataPoint_defaults` 专门断言了这一点——采集点若没带时间戳，`timestamp` 就是无效值，后续逻辑要能识别。
- **为什么 `Device()` 用 `= default`**：显式告诉编译器"用默认构造"，同时因为声明了其他成员函数，`= default` 保证默认构造函数仍被生成（C++ 规则：自定义构造函数后默认构造不再自动生成）。
- **`const` 成员函数**：`id() const` 表示"只读自身成员"。调用方拿到 `const Device&` 时只能调 const 方法——这是 C++ 的"接口最小化 + 只读视图"基础。

## 4. C++ 原理（本阶段重点）

| 机制 | 说明 | 与 C# 对比 |
|------|------|-----------|
| `struct` vs `class` | struct 默认 public、class 默认 private；语义上用 struct 表达"值类型/POCO"，class 表达"有封装的对象" | `record` vs `class` |
| `enum class` | 强类型枚举，不隐式转 int | `enum`（本质是 int，可互转） |
| 类内成员初始化 | `DeviceStatus m_status = DeviceStatus::Disconnected;` 构造时自动应用 | C# 属性初始化器 |
| const 引用返回 | `const QVector<Channel>& channels() const` | `IReadOnlyList<T>` |
| 隐式共享 | QVector/QString 的 CoW 机制 | C# 引用类型天然共享；值类型（struct）拷贝 |
| `= default` | 显式恢复默认构造 | 无对应（C# 有默认构造） |
| 命名空间 `datascope::domain` | 模块边界 + 防止符号冲突 | `namespace`（C# 也有） |

## 6. 为什么这样设计

1. **契约先行，Agent 并行**：`02-领域模型接口契约.md` 把 `Device`/`Channel`/`DataPoint` 的接口、语义、测试强制项全部写死。M1 照契约实现，T3 照契约验证——**这就是"接口已定→可并行"的开发模式**，也是本阶段的最大工程教训。
2. **struct 与 class 各司其职**：`Channel`/`DataPoint` 是"被传递的数据"，`Device` 是"持有集合、暴露只读视图的对象"。用类型系统本身表达"这份数据能不能被随意改"，比靠约定更可靠。
3. **只读引用返回**：`channels()` 返回 `const&`，调用方零拷贝读取，又无法篡改内部数组。把"性能"和"安全"同时写进接口签名。
4. **`= default` + 类内初始化**：新建 `Device` 就自动是"未连接、零通道"的合法状态，杜绝"忘初始化"导致的脏状态。
5. **隐式共享让"拷贝"免费**：`Device` 可拷贝且拷贝便宜，未来放列表/队列、跨线程传递都无压力——这是为 P12 采集线程的数据投递预先铺路。

## 7. 错误案例（真实踩坑）

### 错误案例 1：枚举与整数混用（C# 习惯的延续）

- **现象**：想写 `if (dev.status() == 2)` 判断"已连接"，或 `status = 1` 赋值——在 C# 里 `enum` 和 `int` 可以互转，习惯使然容易这样写。
- **根因**：C++11 之前的老式 `enum` 也允许隐式转 int；但 Qt 规范下我们用 `enum class`，**它禁止隐式转换**。
- **修复**：一律写 `DeviceStatus::Connected`；需要数值用显式 `static_cast<int>(status)`。
- **教训**：**`enum class` 是 C++ 现代编码的默认选择**——编译器替你挡住"脏数据"。

### 错误案例 2：返回 QVector 值类型（每次调用深拷贝）

- **现象**：第一次写 `QVector<Channel> channels() const`，调用方每次 `channels()` 都整数组拷贝一份，采集线程高频调用时白白浪费内存带宽。
- **根因**：返回值类型按值返回，即使 QVector 是隐式共享，这里语义上还是"产生一份新容器"。
- **修复**：返回 `const QVector<Channel>&`——只读视图 + 零拷贝。
- **教训**：**读接口用 `const&` 返回，写接口留显式入口**。这是 C++ 接口设计的基本功（对应 C# `IReadOnlyList<T>`）。

### 错误案例 3：忘记 `= default` 导致"没有默认构造"

- **现象**：`Device dev;` 编译报错"no matching constructor"。
- **根因**：一旦声明了任何构造函数，编译器就不再自动生成默认构造；`Device` 有 `setId()` 等成员（不是构造函数），但如果以后某版本加了一个带参构造，默认构造就会消失。
- **修复**：显式 `Device() = default;`。
- **教训**：**`= default` 是把"默认构造存在"写进契约**，防止未来改动时悄悄破坏调用方。

## 8. 推荐实践

- **契约先行**：先写接口契约文档（含测试强制项），再让实现 Agent 与测试 Agent 并行——接口已定，即可并行。
- **值类型用 struct、集合/状态对象用 class**：用类型系统表达"能否被随意改动"。
- **`enum class` 代替老式 `enum`**；需要数值时显式 `static_cast`。
- **读接口返回 `const&`，不给调用方篡改入口**。
- **领域层只依赖 QtCore**——UI/网络/串口一概不碰，保持可测试、可复用。
- **头文件只声明，实现集中在 .cpp**——加快构建、保护实现细节。

## 9. WPF 对照

| WPF / C# | Qt / C++ |
|----------|----------|
| `public class Device { public string Name { get; set; } }` | `class Device { ... QString name() const; void setName(...); }` |
| `record Channel(...)`（值语义） | `struct Channel { ... }` |
| `IReadOnlyList<Channel> Channels { get; }` | `const QVector<Channel>& channels() const` |
| `enum DeviceStatus { ... }`（本质 int） | `enum class DeviceStatus { ... }`（强类型） |
| 属性初始化器 `= Disconnected` | 类内成员初始化 `m_status = DeviceStatus::Disconnected` |
| ViewModel 引用 Model（DataContext 绑定） | UI 层直接消费领域对象的只读接口 |
| `ObservableCollection`（动态集合） | `QVector`（静态快照）+ 信号驱动刷新 |

## 10. 本质差异（最重要的一课）

> **C# 的"值语义"靠 `record`/`struct` 显式声明，Qt 的"值语义"是 Qt 容器的默认行为（隐式共享 + 写时复制）——拷贝一个 Device 便宜到近乎免费，但"改了副本不碰原对象"必须靠你自己理解 CoW 才能写对。而 C# 的 `enum` 能当整数用，Qt 的 `enum class` 拒绝隐式转换——类型安全上的取舍，Qt 更严格。**

- **隐式共享是双刃剑**：拷贝便宜是好消息；但"改了副本忘 detach"或"以为拷贝了其实共享"是经典误用。理解"引用计数 + 写时复制"是写 Qt 容器代码的分水岭。
- **只读视图**：C# 有 `IReadOnlyList<T>` 专门类型；Qt 用 `const 引用` 表达——靠 const 修饰符而非类型。习惯了 C# 的类型系统，要意识到 Qt 的"只读"是"指针语义 + const"组合出来的。
- **强类型枚举**：C# 的 `enum` 可以 `(DeviceStatus)1` 强转，也能隐式参与整数运算；Qt `enum class` 完全不参与——这逼你把"状态"当成真正的状态而非数字。

## 11. Debug / 排错案例

- **场景**：`QCOMPARE(dev.status(), DeviceStatus::Disconnected)` 编译报错"QCOMPARE 不支持枚举"。
- **排查**：`QCOMPARE` 对枚举类型需要两边类型完全一致且能 `operator==`。`DeviceStatus` 是 `enum class`，`QCOMPARE` 可用，但注意**别混入 `int`**——混用会因隐式转换歧义报错。
- **修复**：两遍都是 `DeviceStatus` 枚举值即可。
- **教训**：QtTest 的 `QCOMPARE` 能直接比较同类型枚举，不需要手动 `toString`（除非要自定义失败信息）。
