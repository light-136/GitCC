## 1. 学了什么

1. **QSettings 的三种存储维度**：Format（`NativeFormat`/`IniFormat`）和 Scope（`UserScope`/`SystemScope`）。**Windows 上 `NativeFormat` 默认就是注册表**（`HKEY_CURRENT_USER`），不显式指定就会把配置写进注册表。
2. **显式 `IniFormat` + 文件路径**：`new QSettings(iniPath, QSettings::IniFormat)` 让配置落到纯文本 INI 文件——可读可审计、可复制分发、可纳入版本管理。
3. **QVariant 类型擦除**：`QSettings::value(key)` 永远返回 `QVariant`——一个能在运行时持有 `int`/`double`/`QString`/`bool` 等已知类型之一的"万能盒子"，读取时必须用对应的 `toInt()`/`toString()` 拆箱。
4. **默认值机制**：`value(key, defaultValue)` 的第二个参数是"键不存在时返回的默认值"；**空 QVariant 的 `toInt()` 是 0、`toString()` 是空串**——不传默认值会"静默拿到类型默认值"，而不是报错。
5. **QSettings 的自动落盘（auto-sync）**：`setValue` 先写内存缓存，到 `sync()` / 析构时才真正写文件——类似 C# `Settings.Save()` 的延迟写盘思路；关键写入后主动 `sync()` 保证不丢。
6. **Meyer's Singleton + QMutex**：与 P6 同款——函数内 static 局部变量保证单例与线程安全初始化；`QMutexLocker` RAII 保护每次读写。
7. **懒加载**：调用方未先 `init()` 就 `setValue`，按默认目录自动创建 `QSettings`，避免空指针。
8. **INI 键的组织**：`setValue("ui/theme", "dark")` 的 `/` 表达分组，INI 里就是 `[ui]` 节下的 `theme=dark`。

## 2. 为什么学

- **设备参数不能写死在代码里**：通道数、采样率、串口/网口参数、报警阈值——写死意味着每次改参数都要重新编译发布。工业现场改个通道数就要求"重新出一版软件"，这是灾难。
- **WPF 有 `Properties.Settings` / `app.config` 兜底，Qt 只有 `QSettings`**：而且 Qt 的默认行为（Windows 注册表）与 C# 的"配置文件在 exe 旁"直觉完全不同——**这是从 C# 转 Qt 必踩的大坑**。
- 配置管理与 P6 日志一样，是**后续所有模块的地基**：P8 采集参数、P10 协议引擎、P12 线程 Worker 都要从这里读参数。

## 3. Qt 原理（本阶段）

- **为什么 `QSettings("x.ini")` 会写注册表**：单参数构造的 format 默认是 `NativeFormat`——在 Windows 上 `NativeFormat` 就是注册表，字符串参数被当作"注册表路径"而非文件路径。它**不报错、看起来一切正常**，所以最隐蔽。
- **`QVariant` 的类型推断**：`QSettings` 存字符串 `"123"` 读 `toInt()` 能自动转成 123；存 `"true"` 读 `toBool()` 是 true。测试 `typeCoercion` 专门验证了这一"尽力而为"的转换行为（C# `Convert.ToXxx` 是严格转换，Qt 是宽松转换）。
- **`sync()` 与析构落盘**：`QSettings` 把写入缓存到内存，`sync()` 强制写文件，析构时也会自动落盘。`ConfigManager` 的析构 `delete m_settings` 顺带保证"最后的写入尽量持久化"。
- **`resolveConfigDir` 的兜底链**：显式目录 → `QStandardPaths::AppDataLocation` → 当前目录 `/config`，逐级兜底，`QDir().mkpath()` 自动创建多级目录。
- **`QSettings::setDefaultFormat`**：进程级全局设置默认格式；`init()` 里先调用它再构造实例，确保后续所有未显式指定格式的构造也走 INI。
- **`QSettings` 非线程安全**：本类为单例，被 UI 线程 / 采集线程共享，必须用 `QMutex` 把每次读/写/删操作串行化（对应 C# `lock`）。

## 4. C++ 原理（本阶段重点）

| 机制 | 说明 | 与 C# 对比 |
|------|------|-----------|
| 组合优于继承 | `ConfigManager` 持有 `QSettings*`，不继承 | 用"强类型门面"包住弱类型组件 |
| 指针 + 懒加载 | `QSettings *m_settings` 在 `init()` 才 new | C# 字段在构造函数里初始化 |
| `QVariant` | 类型擦除容器，取用必须 `toXxx()` | C# `object` 装箱（但 QVariant 预登记类型） |
| 匿名命名空间 | `kConfigFileName` / 两个辅助函数私有 | `private const` / `private static` |
| RAII 锁 | `QMutexLocker` 构造加锁、析构解锁 | `lock` 语句 |
| `mutable` 成员 | `mutable QMutex m_mutex` 允许 const 方法加锁 | C# 无此概念（锁对象常是 readonly） |

## 6. 为什么这样设计

1. **组合而不是继承 QSettings**：暴露的是"强类型 + 命名约定"的门面接口，不让调用者直接看到 `QSettings` 的全部能力——接口最小化，实现细节关在门内。这是"为什么包一层"的核心理由。
2. **四个类型化读取都强制带默认值**：`intValue(key, def)` / `boolValue(key, def)` / `stringValue(key, def)` / `doubleValue(key, def)`——把"空 QVariant 陷阱"在源头堵死，把弱类型转换收口到一处。
3. **显式 `IniFormat` + 完整文件路径**：Windows 上绝不落注册表。注册表不透明、难备份、卸载残留、无法随程序分发、不能跨平台；INI 是纯文本，用户可读可改、可复制分发、可进版本库。
4. **加锁（`mutable QMutex`）**：单例被 UI 线程 / 采集线程共享，而 `QSettings` 本身非线程安全；每次读/写/删都进同一把锁，串行化避免数据竞争。`mutable` 让 `value()`/`configFilePath()` 等 const 方法也能加锁。
5. **懒加载 + 兜底目录**：未 `init()` 就 `setValue` 时按默认目录自动创建，避免空指针；目录解析逐级兜底，目录自动 `mkpath`。
6. **`init()` 可重复调用 = 模拟"程序重启"**：先 `delete` 旧 `QSettings`（析构自动落盘），再重建指向同一文件的新实例——单测 `persistence_acrossReload` 正是用它验证"磁盘上的数据能读回"。

## 7. 错误案例（真实踩坑）

### 错误案例 1：Windows 上 QSettings 默认写注册表，"配置文件找不到"

- **现象**：程序"能存能读"（`value` 读得回来），但 exe 目录、工程目录里**永远没有 `datascope-config.ini`**；换台机器、重装系统，配置全部"消失"。用 `regedit` 一看，`HKEY_CURRENT_USER\Software\...` 底下躺着一堆值。
- **根因**：`QSettings("datascope-config.ini")` 的单参数构造，format 默认是 `NativeFormat`——在 Windows 上 `NativeFormat` 就是**注册表**。字符串参数被当成"注册表路径"而不是文件路径。**它没有报错、看起来一切正常**，所以最隐蔽。
- **修复**（工程落地）：显式指定格式 + 完整文件路径，并配合 `QSettings::setDefaultFormat(QSettings::IniFormat)` 全局兜底：
  ```cpp
  QSettings::setDefaultFormat(QSettings::IniFormat);           // 全局默认走 INI
  m_settings = new QSettings(buildConfigFilePath(m_configDir), QSettings::IniFormat);
  ```
- **教训**：**绝对路径 + IniFormat，两个条件缺一不可**。C# 里"配置=文件"是默认；Qt 里"配置=注册表"才是 Windows 默认，必须显式打破默认。

### 错误案例 2：读取配置不给默认值 → 空 QVariant 静默拿到 0/空串

- **现象**：读一个不存在的 key，本意是"拿默认配置"，结果 `value("no/such").toInt()` 返回 0、`toString()` 返回空串——配置"静默丢失"，且**不报任何错误**，问题被掩盖到业务逻辑深处。
- **根因**：`QSettings::value(key)` 在键不存在时返回**空 QVariant**；空 QVariant 的 `toInt()` 是 0、`toString()` 是空串。C# 的 `Settings` 永远有 app.config 兜底值，Qt 没有——不传默认值就是"静默拿到类型默认值"。
- **修复**：类型化读取**一律强制带默认值**，把空 QVariant 陷阱堵死在门面层：
  ```cpp
  QVariant ConfigManager::value(const QString &key, const QVariant &defaultValue) const {
      if (!m_settings || !m_settings->contains(key)) return defaultValue;
      return m_settings->value(key, defaultValue);
  }
  ```
  单测 `defaultValue_WhenMissing` 专门覆盖"无默认 → 无效 QVariant"与"带默认 → 返回默认值"两种路径。
- **教训**：**Qt 配置代码的每处读取都要给默认值**，这是第一条好习惯；不存在的 key 不报错是设计使然，安全网要靠"默认值参数"自己搭。

## 8. 推荐实践

- `QSettings` 一律显式 `IniFormat` + 完整文件路径（Windows 绝不落注册表）。
- 配置读取**处处带默认值**，把"空 QVariant 静默归零"挡在门面层。
- 包一层类型化门面（`intValue`/`boolValue`/`stringValue`/`doubleValue`），把弱类型 `QVariant` 转换收口到一处。
- 关键写入后立即 `sync()` 落盘（"用户刚改完参数"这种操作不能等析构）；批量写入可攒着最后一次性 sync。
- 单例 + `QMutexLocker` 保护读写；锁区间短、不嵌套。
- 测试用 `QTemporaryDir` 隔离 INI 路径，测完自动清理，绝不碰真实 AppData。

| WPF / C# | Qt / C++ |

| `ConfigurationManager.AppSettings["key"]` | `QSettings::value("key", default)` |
| 配置文件"一定在 exe 旁"（C# 默认） | Windows 默认写**注册表**（必须显式 IniFormat 打破） |

## 10. 本质差异（最重要的一课）

> **C# 的配置是"编译期强类型 + 文件默认在 exe 旁"；Qt 的配置是"运行时字符串 key + QVariant + Windows 默认进注册表"。前两个差异靠门面封装解决，最后一个差异靠显式 `IniFormat` 打破——"默认值"这个 C# 里由 app.config 兜底的东西，在 Qt 里必须由你每一次读取时亲手给定。**

- **强类型 vs 弱类型**：C# `Settings.Default.Channels` 写错类型编译器就报错；Qt `value("channels").toInt()` 写错类型**不报错**，只是静默拿到 0/空串。所以必须靠 `ConfigManager` 把"命名 + 默认值 + 类型转换"收口成一处定义、处处安全。
- **文件 vs 注册表**：这是 Qt 在 Windows 上最反直觉的一课——`QSettings` 默认把配置写进 `HKEY_CURRENT_USER` 注册表，你却以为写进了文件。**不显式打破默认，配置就在你看不见的地方。**
- **默认值责任的转移**：C# 里"读不到配置怎么办"由框架（app.config）兜底；Qt 里 `QSettings::value(key)` 返回空 QVariant 就是"什么都没有"，**默认值责任完全落在调用方**。这正是"配置代码处处带默认值"这一铁律的来历。

## 11. Debug / 排错案例

- **场景**：`init_createsFile` 断言 `QFileInfo(path).absolutePath()` 与临时目录一致失败。
- **排查**：`configFilePath()` 返回的是 `buildConfigFilePath(m_configDir)`——若 `init()` 传了空目录，`m_configDir` 会落到默认兜底路径，与临时目录不符。
- **修复**：单测统一 `cm.init(dir.path())` 传入显式临时目录；`resolveConfigDir` 的兜底链只在"未指定"时生效。
- **教训**：配置路径是"可注入"的——路径显式传入，测试才可隔离（对应 C# 的依赖注入思想）。
- **场景**：`typeCoercion` 用字符串数字 `"123"` 写、`toInt()` 读，为什么能读出 123？
- **排查**：`QSettings` 的 INI 读写对 `QVariant` 有类型推断行为——字符串 `"123"` 转 int 是"尽力而为"的宽松转换（C# `Convert.ToInt32` 也是宽松，但 `QVariant::toInt` 对非法输入返回 0）。
- **教训**：**别把 `QVariant` 的转换当严格校验**；非法输入的处理仍要遵循规范 §8——校验 + 日志 + 默认值。
