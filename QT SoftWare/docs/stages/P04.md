## 1. 学了什么

1. **元对象系统三件套**：`QObject` 基类 + `Q_OBJECT` 宏 + **moc**（meta-object compiler）——这是 Qt 信号槽、属性系统、反射能力的来源，对应 C# 反射，但发生在**编译期**而非运行时。
2. **connect 的四要素**：sender（发出者）、signal（信号）、receiver（接收者）、slot（槽/回调）。前三个是"接线"，第四个是"接到的处理动作"。
3. **五种 connect 写法**：
   - 方式1 成员函数指针（推荐，编译期检查签名）
   - 方式2 lambda 匿名槽（就地处理，最灵活）
   - 方式3 信号 → 信号（转发/透传）
   - 方式4 连接后断开（disconnect 三种粒度）
   - 方式5 `deleteLater` 与对象生命周期
4. **AutoConnection 规则**：同线程 = 直接调用（DirectConnection，类似 C# 同步事件）；跨线程 = 排队投递（QueuedConnection，类似 WPF 跨线程 Dispatcher 排队）。
5. **`emit` 只是关键字**：`emit counterChanged(42);` 编译后等价于 `counterChanged(42);`——真正的分发由 moc 生成的元对象代码完成。
6. **事件驱动**：`QTimer` 是教科书例子——没有事件循环，`start()` 后什么也不会发生。
7. **对象树生命周期**：`new QTimer(this)` 挂 parent，父对象析构时自动 `delete` 子对象（RAII 式的集中释放）。
8. **`QSignalSpy` 信号探针**：QtTest 提供的信号监听器，像"订阅事件来断言事件是否触发"。

## 2. 为什么学

- WPF/C# 里事件订阅只有一种写法：`widget.Event += handler;`。Qt 的 `connect` 有五种主流写法，**这是从 C# 到 Qt 最大的心智跃迁点之一**，不逐一练过就会在真实工程里"只会抄一种写法"。
- 信号槽是 Qt 对象间通信的**唯一官方通道**（跨线程安全投递靠它），P6 的 `messageLogged`、P12 的线程 Worker 全部建立在它之上。
- 元对象系统是"为什么 `Q_OBJECT` 必须在类体开头、为什么 `AUTOMOC` 开着才能编译"的答案；不懂 moc，遇到 `qobject_cast`、`property()`、自动断连都会像看魔术。
- 事件驱动模型（QTimer + 事件循环）是理解 Qt 一切异步行为（定时器、网络、UI 刷新）的前提。

## 3. Qt 原理（本阶段）

- **moc 做了什么**：`Q_OBJECT` 宏在类里声明 `staticMetaObject`、`metaObject()`、`qt_metacall()` 等骨架；moc 在编译前读这些头文件，生成 `moc_*.cpp`——里面填好类名/父类指针/信号槽表/属性表的**静态 `QMetaObject`**，并实现每个信号函数的函数体（把参数打包交给 `qt_metacall`）。所以运行时 `metaObject()` 只是返回一个指向静态数据的指针，**没有运行时扫描**。
- **connect 的四种重载**（本工程用到三种 + 断开）：
  - `connect(sender, &Sender::signal, receiver, &Receiver::slot)`——成员函数指针，签名编译期检查；
  - `connect(sender, &Sender::signal, context, lambda)`——lambda 作槽，context 保证接收者析构时自动断连；
  - `connect(sender, &Sender::signal, receiver, &Receiver::signal)`——信号转发；
  - `disconnect(conn)` / `disconnect(sender, signal, receiver, nullptr)` 等粒度。
- **`QSignalSpy`**：`QSignalSpy spy(&demo, &SignalSlotDemo::counterChanged);` 记录信号发射次数与参数；`spy.count()` 是次数，`spy.at(i).at(j)` 是第 i 次第 j 个参数（QVariant）。它要求参数类型能被 `QVariant` 承接（P4 用的 `int`/`QString` 天然支持；自定义枚举见 P6 的坑）。
- **信号是 public 成员函数**：测试里可以像普通函数一样 `emit demo.counterChanged(42)` 手动触发，所有已连接槽会同步执行——这正是"信号 = 广播方法"的本质。
- **`QTimer` 依赖事件循环**：`QTest::qWait(ms)` 临时运行事件循环；QTimer(1000ms) 每秒触发一次 timeout。单测 `clock_emitsAfterEventLoop` 等待 1.2 秒验证"只 start() 不够，必须有事件循环"。

## 4. C++ 原理（本阶段重点）

| 机制 | 说明 | 与 C# 对比 |
|------|------|-----------|
| `Q_OBJECT` + moc | 编译期生成元对象（静态数据） | C# 运行时反射（`typeof`/`GetProperties`） |
| 信号槽连接 | connect 四要素，可自动断连 | `event += handler`（+ 手动 `-=`） |
| 函数指针 | `&SignalSlotDemo::counterChanged` 编译期检查 | C# `EventHandler` 委托（运行时绑定） |
| lambda 捕获 | `[this]` 捕获本对象成员 | C# lambda 捕获 `this`（GC 保证存活） |
| 对象树 | parent 析构统一 delete child | WPF 逻辑树只是层级描述，不负责内存 |
| `deleteLater()` | 投递 DeferredDelete 事件，事件循环收尾再删 | C# 无对应物（GC 决定时机） |
| `QPointer` | 弱引用，对象删除后自动置空 | C# `WeakReference` |

## 6. 为什么这样设计

1. **"纯 QObject、不依赖 UI"的演示类**：既能被主窗口当"舞台"用，又能被单测直接验证——教学点与可测性兼得。这是"业务对象与 UI 解耦"的雏形（对应 WPF 的 ViewModel 思路）。
2. **每种连接写一个独立私有函数**：`runAllDemos()` 依次调用，主窗口一个按钮就能跑完五种演示；每次运行前 `disconnect(this, nullptr, this, nullptr)` 清空旧连接，保证演示**可重复执行**（否则重复连接导致信号触发两次）。
3. **`startClock()` 用 lambda 翻译信号**：把 `QTimer::timeout`（Qt 类型）翻译成业务信号 `timeTicked`——这是"信号 → 信号/信号 → lambda"的典型工程用法，UI 只需关注业务信号。
4. **lambda 一律带 context 参数**：`connect(m_clock, &QTimer::timeout, this, [this]{...})` 的第三个参数 `this` 是 context 对象，保证接收者析构时 Qt 自动断连，避免悬垂——这是 P4 必须避开的坑（见错误案例 2）。
5. **主窗口布线集中在构造函数**：connect 的"接线"动作集中一处、一目了然，比散落在业务代码里更易读。
6. **对象树托管所有 child**：`m_demo = new SignalSlotDemo(this)`、`new QTimer(this)`、`new QLabel(tr(...), this)`——全部挂 parent，析构交给对象树，主窗口析构函数为空即可。

## 7. 错误案例（真实踩坑）

### 错误案例 1：字符串内嵌 ASCII 双引号导致编译报 "stray character"

- **现象**：编译 `signalslotdemo.cpp` 报错 `stray '\"' in program`（游离引号），定位到第 171 行附近。
- **根因**：该行本想打印 `【方式5】deleteLater：安全的"延迟删除"机制`，直接在字符串内部写成了 ASCII 双引号：
  ```cpp
  emit messageEmitted("【方式5】deleteLater：安全的"延迟删除"机制");
  //                                                ^此处双引号把字符串提前截断
  ```
  C++ 字符串字面量以 `"` 开始、以匹配的 `"` 结束；中间再出现 ASCII `"` 会把字符串切断，剩下的 `延迟删除"机制"` 成为游离字符（stray character），语法解析直接失败。
- **修复**：把内嵌引号改为中文引号「」（或转义 `\"`）：
  ```cpp
  emit messageEmitted("【方式5】deleteLater：安全的「延迟删除」机制");
  ```
- **教训**：C++ 字符串里要"显示引号"，只有两条路——转义 `\"`，或用非 ASCII 引号（「」、“”）。直接内嵌 ASCII `"` 必然切断字符串；这类报错的行号定位到"第一个导致语法漂移的引号"，往往不是最后一个。

### 错误案例 2：lambda 捕获裸 `this` 却漏传 context 对象 → 悬垂调用隐患

- **现象**：如果写成 `connect(m_demo, &SignalSlotDemo::messageEmitted, [this](const QString &t){ ... });`——**漏了第三个参数 `this`（context）**，编译能过、运行看起来也正常，但接收者析构后连接仍在，一旦信号再触发就是悬垂调用（`this` 已死），时好时坏、最难查。
- **根因**：Qt 的自动断连机制依赖"接收者是 QObject 且被 connect 登记"；漏传 context，Qt 就不知道"接收者是谁、什么时候该断开"。
- **修复**：lambda 作槽时**必须**传 context 对象：
  ```cpp
  connect(m_demo, &SignalSlotDemo::messageEmitted, this,
          [this](const QString &text) { m_logView->appendPlainText(text); });
  ```
- **教训**：`connect` 的第三个参数不是可选项——它把"接收者生命周期"交给 Qt 托管。凡 lambda 捕获了 `this`，就必须把 `this` 作为 context 传进去（对照指南错误案例 4 的完整论述）。

## 8. 推荐实践

- connect 首选**成员函数指针**写法：签名编译期检查，拼错函数名/参数类型不匹配会直接编译报错。
- lambda 作槽时**永远带上 context 对象**（第三个参数），避免悬垂。
- 需要"当场建、当场拆"的连接用 `QMetaObject::Connection` 句柄精确 `disconnect(conn)`，比"断开全部"更精细。
- 连接前先 `disconnect(this, nullptr, this, nullptr)` 清场，保证演示/重连场景可重复执行、不会重复触发。
- 定时器、异步对象用完不立即删，用 `deleteLater()`（配合对象所属线程的事件循环）。
- 测试里用 `QSignalSpy` 断言"信号确实发出、次数正确、参数正确"，比肉眼观察可靠。

## 9. WPF 对照

| WPF / C# | Qt / C++ |
|----------|----------|
| `widget.Event += handler;`（只有一种写法） | `connect` 五种写法（成员函数指针/lambda/转发/disconnect/deleteLater） |
| `event EventHandler<int> CounterChanged` | `signals: void counterChanged(int value)` |
| 反射 `typeof(...).GetMethods()` | `QObject::metaObject()`（编译期生成静态元数据） |
| `obj as T` | `qobject_cast<T*>(obj)`（仅 QObject，失败返回 nullptr） |
| 事件订阅用 `-=` 取消 | `disconnect(...)` 三种粒度 |
| `DispatcherTimer` / `System.Timers.Timer` | `QTimer` + 事件循环（没有事件循环就不触发） |
| `EventHandler<T>` 委托（运行时绑定） | 函数指针/lambda（编译期检查或运行时语法） |
| `WeakReference`（不阻 GC 回收） | `QPointer`（对象删除自动置空） |
| `using` / GC（无删除时机概念） | `delete` / `deleteLater()`（删除时机要与事件循环配合） |

## 10. 本质差异（最重要的一课）

> **C# 的反射是"运行时拿着身份证查户口本"；Qt 的元对象系统是"上户口时就印好了一本相册，运行时只是翻相册"。C# 的事件是"+= 一种写法 + GC 兜底生命周期"；Qt 的信号槽是"五种写法 + 必须自己管接收者生命周期"。**

- 元对象信息的**时机**不同：C# 反射在运行时读程序集元数据表；Qt 在编译期由 moc 生成静态 `QMetaObject`。这带来一个直接推论：**`Q_OBJECT` 漏写通常不是编译报错，而是"运行时行为诡异"**（信号槽全废、`qobject_cast` 不认你）——这是 Qt 新手最隐蔽的坑。
- **生命周期责任的归属**不同：C# 里 GC 保证 lambda 捕获的 `this` 一定活着；Qt 里只有你把 `this` 作为 context 传给 connect，Qt 才能在它析构时自动断连。**"自动断连"不是免费的，前提是你先把接收者登记进连接里。**
- 对象树的对照最值得记：WPF 的逻辑树是"层级描述"（不负责内存），QObject 对象树是"内存所有权"（parent 析构就 delete child）。这也是后续 P6 `LogManager`、P12 线程 Worker 生命周期管理的思维基础。

## 11. Debug / 排错案例

- **场景**：`runAllDemos_emitsMessages` 单测偶发 `msgSpy.count()` 偏大。
- **排查**：怀疑重复连接。`runAllDemos` 开头加了 `disconnect(this, nullptr, this, nullptr)` 清场后恢复稳定——连接若重复建立，同一信号会触发多个槽，计数翻倍。
- **教训**：**"信号触发了两次"的 90% 原因是重复 connect**。凡是"可反复执行的初始化/演示"路径，先清场再连接。
- **场景**：`clock_emitsAfterEventLoop` 若把 `QTest::qWait(1200)` 去掉，用例必然失败。
- **排查**：QTimer 没有事件循环驱动，`start()` 只是注册了定时器，回调永远不会来。
- **教训**：定时器/异步行为必须"进入事件循环"才生效；单测里用 `qWait` 显式推进事件循环。
