## 1. 学了什么

1. **RAII（资源获取即初始化）**：栈对象离开作用域自动析构——`QByteArray`、`QString` 无需手动释放，这是 C++ 替代 GC 的核心思维。
2. **const 引用入参**：`const QByteArray &data` 表示"只读、不拷贝、不修改调用方"，是 C++ 传参首选。
3. **非 const 引用出参**：`quint16 &out` 让函数把结果写回，配合返回值报告成功与否（TryParse 风格）。
4. **匿名命名空间**：`.cpp` 内 `namespace { ... }` 定义文件私有常量，对应 C# 的 `private const`。
5. **静态库 target**：`datascope_utils` 一个库被主程序和测试共用（对应 WPF 的类库项目）。
6. **Qt Test 数据驱动测试**：`_data()` 函数提供多组输入，`QFETCH/QCOMPARE` 消费，一次逻辑测多组。
7. **边界测试**：空数组、单字节、越界、非法输入都覆盖。

## 2. 为什么学

- P2 是 C++ 心智转型的关键阶段：**不解决"内存谁负责"的思维，后面所有 Qt 代码都会在生命周期上栽跟头**。
- 工具库是"低风险高复用的载体"，最适合把 C++ 特性练熟，不夹杂业务复杂度。
- 静态库 + 测试分离是工程基线，P10 协议引擎会复用同一套测试基建。

## 3. Qt 原理（本阶段）

- **QtTest**：`QTEST_MAIN(Class)` 自动生成 main；测试类继承 `QObject`，槽函数即用例；`QCOMPARE/QVERIFY` 失败时打印文件行号。
- **数据驱动**：`QTest::addColumn<T>("列名")` 定义表结构，`QTest::newRow("行名") << 值` 填行，测试函数用 `QFETCH(T, 变量)` 取出——对应 NUnit `TestCase`。
- **AUTOMOC 对测试文件同样生效**：`tst_byteutils.cpp` 里的 `Q_OBJECT` 由 moc 处理，末尾 `#include "tst_byteutils.moc"` 引入生成的元对象代码（Qt 约定写法）。

## 4. C++ 原理（本阶段重点）

| 机制 | 说明 | 与 C# 对比 |
|------|------|-----------|
| 栈对象 | `QByteArray result;` 离开作用域自动析构 | C# 只有引用类型，无栈自动释放概念 |
| const 引用 | `const T &x` 只读不拷贝 | C# 的 `in` 参数（较新）或普通传引用 |
| 值语义 vs 引用语义 | `QByteArray` 赋值是浅拷贝 + 写时复制 | C# 字符串/类默认引用共享 |
| 匿名命名空间 | `.cpp` 内部符号私有 | `private` 静态成员 |
| 静态库 | 编译期打包，链接时合并 | 类库 DLL 项目（动态加载） |

## 6. 为什么这样设计

1. **工具类用静态方法**：无状态纯函数，最简单可靠，对应 C# `static class`。
2. **库与主程序分离**：主程序（GUI）与测试（控制台）各自链接，编译隔离、依赖清晰。
3. **读取用"返回值报告 + 出参带结果"**：比抛异常更适合解析类场景（性能 + 语义清晰），对应 C# `int.TryParse`。
4. **大小端统一大端**：工业协议/TCP 字节流惯例，P10 帧解析直接复用。
5. **测试独立 target**：开发 Agent 写代码、测试独立验证，符合多 Agent 计划的"测试轨独立"原则。

## 7. 错误案例（真实踩坑）

### 错误案例 1：hex 解析"0x 前缀"被误解析

- **现象**：`fromHexString("0xAA,bb,0c")` 第二个字节期望 `0xBB`，实际 `0x0A`。
- **根因**：宽容解析把前缀 `0x` 里的 `'0'` 当作字节高 4 位、`'x'` 跳过、`'A'` 作低 4 位 → 拼出 `0x0A`。
- **正确写法**：遇到 `x/X` 且已捕获一个为 0 的高半字节时，撤销该 `'0'`（视为 `0x` 前缀）。
- **为什么单测能抓住**：`fromHexString_tolerant` 用例专门构造了"小写 + 0x 前缀 + 逗号"混合输入——**测试要覆盖真实场景的脏输入**。

### 错误案例 2：ctest 报 0xc0000135（找不到 DLL）

- **现象**：主程序正常，`tst_byteutils` 运行即退出，退出码 `0xc0000135 = STATUS_DLL_NOT_FOUND`。
- **根因**：windeployqt 只部署了主程序 `DataScope.exe` 的依赖；测试程序链接的 `Qt5Test.dll`/`Qt5Core.dll` 未部署到测试 exe 目录。
- **正确写法**：把 windeployqt 封装成 CMake 函数 `ds_deploy_qt(TARGET)`，主程序与**所有**测试 target 都调用。
- **教训**：任何新增可执行 target 都必须部署 Qt 运行库，这是 Qt 工程的"常识性坑"。

## 8. 推荐实践

- 传参默认 `const T &`；需要输出用引用出参；能返回值就返回值（配合 move）。
- 头文件尽量只放声明；实现细节（匿名命名空间常量）放 `.cpp`。
- 测试数据驱动：边界 + 脏输入 + 正常值三类都覆盖。
- 库边界：公共工具先独立成库，避免所有代码都塞进主程序。

| WPF / C# | Qt / C++ |

| GC 自动回收 | RAII 栈对象自动析构 |

## 10. 本质差异（最重要的一课）

> **C# 的 GC 让"内存"隐形；C++ 的 RAII 让"资源生命周期"显式化。**

- C# 写 `var list = new List<int>();` 不用关心何时回收——GC 决定。
- C++ 写 `QByteArray result;` 必须清楚它属于哪个作用域——离开作用域立即析构。
- 因此 C++ 工程里"对象归属"（谁拥有、谁销毁、什么时候销毁）是设计核心，这就是后续 P4 对象树、P6 日志管理器、P12 线程 Worker 生命周期管理的思维基础。

## 11. Debug / 排错案例

- **场景**：`fromHexString_tolerant` 单测失败，`QCOMPARE` 定位到第 82 行（第二个字节）。
- **排查**：断点 + 单步看状态机 → 发现 `'0'` 进入高半字节 → 设计"撤销 0x 前缀"修复。
- **教训**：`QCOMPARE` 的失败信息直接给出行号与期望/实际值，是定位测试失败的利器；写完解析类逻辑先跑脏输入用例。
