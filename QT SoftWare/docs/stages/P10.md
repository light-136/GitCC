## 1. 学了什么

1. **帧格式契约**：`SOF(0xAA55,2B) + FUNC(1B) + CMD(1B) + LEN(2B 大端) + DATA(LEN) + CRC16(2B 低字节在前)`——字节序是协议的灵魂，收发两端必须完全一致。
2. **CRC16-MODBUS 反射算法**：查表法（256 项查找表懒初始化），初值 0xFFFF、异或出参 0xFFFF、反射输入输出。用标准向量 `"123456789"` 验证得 `0x4B37`。
3. **组帧器 FrameBuilder**：把结构化参数（func/cmd/payload）按字节序拼成 QByteArray——`build(func, cmd, payload)` 返回完整帧或空（载荷超限时）。
4. **流式解析器 FrameParser**：三态状态机（扫描帧头 → 读头字段 → 收数据校验），支持**粘包**（一次 feed 多帧逐帧产出）与**半包**（数据分多次到达也能正确拼接），这是 TCP 字节流通信的必修课。
5. **防攻击边界设计**：`kMaxPayloadLen=1024` 防御 LEN=0xFFFF 超大值；垃圾无帧头时清空缓冲、仅保留孤立 `0xAA`；校验失败整帧丢弃不产出错误帧。
6. **CRC 覆盖范围**：FUNC 起经 CMD、LEN 到 DATA 末尾（含 LEN 字段本身）——契约明确、两端一致。

## 2. 为什么学

- **通信是采集系统的命脉**：不管串口还是 TCP，设备上报的数据必须先"组帧→发送→接收→解析→校验"这一套链路。帧引擎是整个系统的**咽喉**，必须先于模拟设备/TCP 客户端稳定。
- **协议解析是 C# 转 Qt 的高频场景**：C# 有 `BinaryReader` 手动抠字节，Qt 没有现成的帧解析——必须自己实现"流式字节 → 结构化帧"的状态机。
- **粘包/半包是网络编程第一课**：TCP 是字节流，一次 `read` 可能只收到半帧、也可能一次收到好几帧。不会处理粘包/半包的程序，在真实网络环境必然数据错乱。

## 3. Qt 原理（本阶段）

- **QByteArray 当字节缓冲区**：`feed(chunk)` 把收到的字节 `append` 进内部缓冲，`nextFrame()` 从缓冲头部消费——对应 C# 的 `List<byte>` + 游标。
- **QByteArray 构造陷阱**：`QByteArray(int, char)` 是"填充 n 个 char"的构造；`QByteArray::append(int, char)` 在 5.12 存在性不确定，C1 统一用确定存在的 `QByteArray(int, char)` 构造规避。
- **大端/小端手工拼装**：Qt 没有直接"两字节大端"便利函数，用 `quint16` 位运算 `(data[i] << 8) | data[i+1]` 手动拼/拆（对应 C# `BinaryWriter.Write(BitConverter...)`）。

## 4. C++ 原理（本阶段重点）

| 机制 | 说明 | 与 C# 对比 |
|------|------|-----------|
| `constexpr` | 编译期常量（kSof/kHeaderLen/kMaxPayloadLen） | C# `const`（仅基本类型） |
| 查表法 CRC | 静态 `quint16` 表 + 懒初始化（函数内 static） | `static readonly ushort[]` |
| 状态机枚举 | `enum class ParserState { SearchSof, ReadHeader, ReadData }` | `enum` + switch |
| 位运算 | `>>`/`<<` 拼装大端、`& 0xFF` 取低字节 | `BitConverter` 系列 |
| `quint8/quint16` | 无符号定宽整数（Qt 别名） | `byte/ushort` |
| 引用传参 | `feed(const QByteArray &chunk)` 避免拷贝 | `byte[]`（引用类型） |

## 6. 为什么这样设计

1. **协议层独立成库**：串口（P9）、TCP 客户端（P11）、模拟设备（Simulator）都消费同一套帧引擎——**一个协议实现，三个消费者**，避免三处各写一遍字节拼接逻辑。
2. **组帧器与解析器分离**：`FrameBuilder` 只管"结构 → 字节"，`FrameParser` 只管"字节流 → 结构"。对称而独立，各自可测。
3. **解析器不抛异常（TryParse 风格）**：校验失败返回 false / 不产出帧，绝不抛异常中断事件循环——工业现场宁可丢一帧，不能让程序崩。
4. **防攻击是设计的一部分**：`kMaxPayloadLen` 上限、垃圾重同步、缓冲裁剪——设备在恶劣电磁环境可能吐任意字节，解析器必须"死不了、不膨胀、能重同步"。
5. **帧结构字段默认值**：`func=0/cmd=0/payload空/isValid=false`，构造即合法状态，杜绝脏数据。

## 7. 错误案例（真实踩坑）

### 错误案例 1：CRC 覆盖范围两端不一致

- **现象**：组帧器算的 CRC 与解析器校验的 CRC 对不上，数据总是解析失败。
- **根因**：组帧与解析对"CRC 覆盖哪几字节"的区间理解不一致（一个含 LEN、一个不含）。
- **修复**：以契约为准，统一为 `FUNC + CMD + LEN + DATA` 共 `4+LEN` 字节；组帧器 `frame.mid(2)`、解析器 `mid(2, kHeaderLen+len-2)` 完全对称。
- **教训**：**协议实现里"两端必须完全一致"的地方，最好用同一个常量/表达式**，两端不一致是通信类 bug 的最高发来源。

### 错误案例 2：半包/粘包处理不当

- **现象**：只按"读一次解析一次"处理，帧被拆成两半时解析失败、两帧粘在一起时只解析出半帧。
- **根因**：不理解 TCP 是字节流，`readyRead` 到的数据量完全随机。
- **修复**：状态机 + 内部缓冲——`feed()` 只管把字节攒进来，`nextFrame()` 每次只尝试"缓冲里够不够一帧"，够才消费产出，循环取到取不出为止。
- **教训**：**解析器必须无状态（或者说状态只在内部缓冲）**，调用方不感知数据切分。

## 8. 推荐实践

- 协议实现**契约先行**：字节序、CRC 覆盖范围、字段含义写死成文档，收发的 Agent 各守一端。
- CRC 用标准向量验证（`"123456789"` → 已知值），不靠"自己算自己查"自我循环验证。
- 解析器设计成**流式状态机**，天然支持粘包/半包；单测用"分 3 段喂入""一次喂两帧"强制覆盖。
- 定上限（`kMaxPayloadLen`）、丢坏帧、能重同步——解析器永远不崩、不膨胀。
- 收发相关代码里，字节序拼装与拆解**必须对称书写**，最好紧挨着放便于审查。

## 9. WPF 对照

| WPF / C# | Qt / C++ |
|----------|----------|
| `BinaryWriter.Write` 手动拼字节 | `FrameBuilder` 位运算拼大端 |
| `BinaryReader.ReadXxx` 手动抠字节 | `FrameParser` 状态机 + 位运算 |
| `byte[]` / `List<byte>` 缓冲 | `QByteArray` |
| `const byte SOF = 0xAA` | `constexpr quint16 kSof = 0xAA55` |
| `static readonly ushort[] CRCTable` | 函数内 static 查找表（懒初始化） |
| `MemoryStream` + 游标 | 状态机 + `bufferedBytes` |
| 异常处理（try/catch 解析） | TryParse 风格：失败不产出、不抛异常 |

## 10. 本质差异（最重要的一课）

> **C# 把"字节 ↔ 结构"的转换交给 `BinaryReader/BinaryWriter` 顺手做完；Qt 没有帧解析基础设施——你必须亲手实现"流式状态机 + 字节序 + 校验"。而这一课的本质不是 Qt 缺功能，而是"通信可靠性"必须由你自己设计：防攻击上限、坏帧丢弃、粘包半包处理，这些 C# 同样要写，只是 Qt 连"帮你开头"的工具都没有，一切从零起步。**

- **状态机是解析器的灵魂**：`扫描帧头 → 读头 → 收数据 → 校验`，每一步都有"字节不够"的等待态——这就是网络编程里"流式"的完整含义。
- **字节序不写进文档就会踩坑**：大端 LEN、低字节在前的 CRC——每个字段都要写清楚，不然两端各写各的，联调时哭。
- **校验是最后防线**：CRC 覆盖范围、初值、出参、反射位序，任何一项错，整帧失效——用标准向量一次性锁定。

## 11. Debug / 排错案例

- **场景**：`tst_protocol` 里"SOF 错位"用例——前加 `"XYZ"` 垃圾字节，解析器必须丢弃垃圾、重同步到 `0xAA 0x55`。
- **排查**：状态机在"扫描帧头"态逐字节找 `0xAA`；找到后只认下一个字节是 `0x55` 才算 SOF，否则继续扫描。
- **修复**：垃圾全部消费掉（`bufferedBytes` 归零或只留孤立的 `0xAA`），随后合法帧正常产出。
- **教训**：**协议健壮性测试要主动"喂垃圾"**——真实设备在恶劣环境下发的就是任意字节。
