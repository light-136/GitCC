## 1. 学了什么

1. **QTcpSocket 事件驱动模型**：连接（connected）、可读（readyRead）、错误（error）、断开（disconnected）全是信号——对应 C# 的 `ConnectAsync`/`ReceiveAsync` 回调，Qt 没有同步阻塞的网络 API 调用方式（有 waitFor* 但绝不用于生产）。
2. **`QOverload<QAbstractSocket::SocketError>::of(&QAbstractSocket::error)`**：Qt 5.15 才有 `errorOccurred` 信号，5.12 只有 `error(...)`。它和"错误码查询方法 error()"同名重载，必须用 QOverload 精确指定"带 SocketError 参数"的那一个信号——Qt 重载信号的标准姿势。
3. **半包/粘包处理**：接收侧不能假定"一次 readyRead = 一帧"。FrameParser 用三态状态机（扫描帧头→读头→收数据校验）逐字节消费缓冲，`feed()` 喂字节、`nextFrame()` 逐帧取出——天然支持半包（不够一帧先缓存）和粘包（一帧+下帧前一半）。
4. **每客户端独立解析器**：simulator 里每个连接一个独立 FrameParser，多客户端字节流不会互相污染（对应 C# 每个连接独立接收缓冲）。
5. **模拟设备价值**：无真实硬件时用 QTcpServer 发真实格式的帧，让主程序联调链路；这是嵌入式上位机开发的标配手段。

## 2. 为什么学

- 采集链路是工业数据系统的命脉，TCP 是最通用的采集通道。
- 理解"事件驱动的字节流 → 有状态的帧解析"是协议层的核心思维，串口（P9）走同一套 FrameParser。

## 3. Qt 原理（本阶段）

- **readyRead 语义**：表示"有数据可读"，不保证一次读完整帧；正确姿势是 `readAll()` 读走全部就绪字节再喂解析器。
- **信号是连接建立时的静态绑定**：构造函数里连接好业务信号（connected/error/frameReceived），业务层不感知底层 socket 细节。

## 4. C++ 原理（本阶段重点）

| 机制 | 说明 | 与 C# 对比 |
|------|------|-----------|
| `QByteArray` | 字节容器（隐式共享） | `byte[]` |
| `memcpy` 位模式转换 | float ↔ 32 位整数互转（跨端序安全） | `BitConverter` |
| lambda 捕获 `[&, client]` | 连接作用域外的指针到 lambda | 闭包（delegate） |

## 5. 踩坑与修复（本阶段最有价值）

1. **`Qt::hex`/`Qt::dec` 不存在**：QDebug 的流操作符是 `hex`/`dec`（无 Qt:: 前缀）。修复：去掉前缀。
2. **`waitForNewConnection` 随机竞态失败**：它是同步阻塞 API，等待 `newConnection` 信号；而该信号可能已被前面 `QSignalSpy::wait()` 的事件循环"消费"（Qt 信号一次性，发出时无接收者即丢弃）。修复：改用**事件驱动**——`connect(newConnection, lambda)` + `QTRY_VERIFY_WITH_TIMEOUT`，与 tst_dataservice 全绿模式一致。
3. **"连接失败"测试的端口陷阱**：相邻端口法（probe+1）实测撞上系统活跃监听端口 → 连接"成功" → error 永不触发。且 Windows 对"刚释放的 LISTEN 端口"有约 2s 的拒绝延迟。修复：回归"验证空闲"法（listen 成功=此刻空闲 → 释放 → 立即连接），等待放宽到 5s。
4. **QSignalSpy 处理自定义类型 ProtocolFrame**：必须在 initTestCase 里 `qRegisterMetaType`，且 moc 规范化名可能记成 裸名/相对名/全限定名 三种，全部登记为别名。
