## 1. QObject：一切 Qt 对象的"地基类"

> 可类比程度：★★★☆☆　（能力上像 `object` + `DependencyObject` 的混合体，机制完全不同）

### 一句话类比

C# 里所有类都继承自 `object`，`DependencyObject` 再给 WPF 控件加上属性/绑定能力；Qt 的 `QObject` 把这两样**焊成一根**——它是所有 Qt 对象的基类，自带信号槽、属性系统、元对象信息、线程亲和性、父子树，**一个都不能拆**。

### 代码对比

```csharp
// C#：object 提供 ToString/Equals/GetHashCode；DependencyObject 提供属性系统
public class MainWindow : Window   // Window ← DependencyObject ← DispatcherObject ← object
{
    // 依赖属性要写一长串注册代码
    public static readonly DependencyProperty TitleProperty =
        DependencyProperty.Register(nameof(Title), typeof(string), typeof(MainWindow));
}
```

```cpp
// Qt：一个 Q_OBJECT 宏，以上能力全部打包
class MainWindow : public QMainWindow   // QMainWindow ← QWidget ← QObject
{
    Q_OBJECT                             // 元对象系统入口：信号槽 + 属性 + 反射
public:
    explicit MainWindow(QWidget *parent = nullptr);
    ~MainWindow() override;
    Q_DISABLE_COPY(MainWindow)
};
```

### 机制讲解

- **C# 是"三件套"分层**：`object`（所有类型的根）→ `DispatcherObject`（线程亲和）→ `DependencyObject`（依赖属性）。需要什么能力就继承到哪一层，各层职责单一。
- **Qt 是"一体机"**：`QObject` 把六种能力打包在同一个类里：
  1. **信号槽** —— 对象间通信（上一篇第 5 节）；
  2. **属性系统** —— `property()` / `setProperty()`，由元对象驱动；
  3. **元对象信息** —— `metaObject()` 拿到类名、父类、信号槽表（本篇第 6 节）；
  4. **对象树** —— parent/child 所有权（本篇第 2、3 节）；
  5. **线程亲和性** —— 每个 QObject 属于创建它的线程，跨线程操作要过事件循环；
  6. **定时器** —— `startTimer()` / `killTimer()` 是 QObject 的成员（`QTimer` 只是封装）。

  C# 里"普通类也可以有 event、可以不继承任何东西"；Qt 里**只有 QObject 子类才能发信号、连信号槽、做反射**。这是架构分水岭：不是"能用就行"，而是"想用这些能力，就必须继承 QObject"。

### 为什么不能简单照搬

1. **C# 所有类型都继承 object；Qt 只有"需要能力的类"才继承 QObject**。`QString`、`QVector`、`QByteArray` 这些值类型**不是** QObject，它们没有信号槽、不挂对象树。把"值类型"误当成"QObject"去 `connect`，编译都过不了。
2. **QObject 禁止拷贝**（`Q_DISABLE_COPY` 的由来）：C# 里 `var w = new Window(); var w2 = w;` 是引用共享，随便写。Qt 里 QObject 有身份（是某个对象树的节点、连着一堆信号槽），复制没有意义，所以 `Q_DISABLE_COPY` 从**编译期**拒绝拷贝。这是"语义上不能照搬"的硬例子——C# 靠约定，Qt 靠编译器。
3. **线程亲和性不是可选项**：C# 里线程间共享对象只要加锁；Qt 里 QObject 默认"属于创建它的线程"，在别的线程直接调它的方法（非线程安全的那些）是未定义行为。信号槽跨线程自动排队，但这是**唯一的合规通道**（规范第 7 节）。

### 在 DataScope 里的落地

- `mainwindow.h` 第 23 行 `class MainWindow : public QMainWindow`：继承链 `QMainWindow ← QWidget ← QObject`。所以 MainWindow **自动获得**全部六种能力——不需要额外注册任何东西。
- 第 25 行 `Q_OBJECT` 宏：没有它，上面那些能力一个都启用不了。注意它**必须写在类体开头**，且要求该类编译时经过 moc（CMake 的 `AUTOMOC` 已默认开启）。
- 第 34 行 `Q_DISABLE_COPY(MainWindow)`：编译器层面禁止拷贝，正是"QObject 有身份不可复制"的工程落地。

## 2. Object Tree（对象树）：谁生谁、谁养谁

> 可类比程度：★☆☆☆☆　（WPF 的逻辑树/可视树只是"层级描述"，**不负责内存**；QObject 树**就是所有权**）

### 一句话类比

WPF 的逻辑树是"家谱图"（画给你看的）；QObject 的对象树是"领养登记簿"（**法律文书**）——父对象在登记簿上签了字，就**欠它一个 delete**。

### 代码对比

```csharp
// WPF：Button 放进 Grid，只是可视化/逻辑上的"包含"
grid.Children.Add(btn);
// 内存上？GC 管。把 grid 关了，btn 的生死与 grid 毫无关系。
```

```cpp
// Qt：给 new 出来的控件指定 parent，parent 析构时自动 delete 它
auto *btn = new QPushButton(QStringLiteral("连接"), this);
// this（MainWindow）析构时，btn 被 Qt 自动释放——你不需要写 delete btn;
```

### 机制讲解

对象树是 QObject 内部维护的一组指针关系：

- 构造函数传 `parent` 参数，或调用 `setParent(parent)`，就把自己挂到父对象的 `children()` 列表里；
- **父对象析构时，遍历 children 列表，逐个 `delete`**。这一条是对象树全部价值的核心；
- 子对象也可以有自己的子对象，形成一棵树。整个树以"根"（比如 MainWindow）为唯一入口，**删除根 = 连根拔起整棵树**。

所以"挂 parent"的本质是**登记所有权**：你在告诉 Qt"这个 child 归我管，我死的时候替我清掉"。它解决的是"**谁负责 delete**"的问题——把 N 个 `delete` 从散落各处的代码里收拢到一个析构函数里。

### 为什么不能简单照搬

1. **WPF 的树是"视图描述"，Qt 的树是"内存所有权"**。在 WPF 里你把 `Button` 从 `Grid` 里 `Remove`，不会释放按钮（GC 才管）；在 Qt 里把一个 widget `setParent(nullptr)` 只是解除所有权，**内存照样归你管**——除非你转手把它交给另一个 parent 或智能指针。
2. **树是"单向引用"**：parent 持有 child 指针，child **不持有** parent 指针（只有 `parent()` 查询函数）。所以没有环，不需要引用计数——这也是为什么它比 `shared_ptr` 简单。
3. **对象树只管"堆上"对象**：把**栈对象**交给 parent 是灾难（见第 5 节和错误案例 2）。对象树默认你 `new` 过，它不检查、也检查不了。
4. **对象树不解决"悬垂指针"**：parent 析构时把 child `delete` 了，但**其他还指向这个 child 的裸指针不会自动变空**——GC 不会发生这种事，Qt 也不会。要补这个洞，用 `QPointer`（第 7 节）。

### 在 DataScope 里的落地

- `mainwindow.h` 第 30 行注释原文："析构：Qt 对象树自动清理子对象，一般无需手动 delete"。这是 Qt 的**默认心智**：UI 控件挂 parent，析构交给对象树。
- `mainwindow.h` 第 29 行 `explicit MainWindow(QWidget *parent = nullptr);`：主窗口自己也接受一个 parent。`main.cpp` 里 `MainWindow window;` 是**栈对象、无 parent**——它是整棵 UI 树的根，`main` 返回时栈析构，连带拔掉树下所有子控件。
- P2 总结里那句话正是为这节做的伏笔："'对象归属'是设计核心，这就是后续 P4 对象树、P6 日志管理器、P12 线程 Worker 生命周期管理的思维基础。"

## 3. 重点辨析：QObject Parent/Child 不是 C++ 内存管理本身

> 可类比程度：★★☆☆☆　（表面像"自动释放"，实际是**所有权协议**，不是语言语法）

### 一句话类比

RAII 是"编译器替你锁门"（**语法保证**）；对象树是"管家拿着一张钥匙清单，你走后替你锁这一排门"（**协议保证**）。前者是法律，后者是雇了个管家。

### 代码对比

```cpp
// 语言层：RAII —— 作用域结束必然析构，编译器保证，无法违抗
{
    QTimer timer;              // 栈对象
    timer.start(1000);
}                              // 到这里必然析构，没有人能阻止

// 库层：对象树 —— parent 析构时统一 delete，Qt 替你执行
auto *child = new QPushButton(parent);   // 你签了字：这个 child 归 parent 管
// ... 你不再写 delete child; 
// parent 析构时，Qt 遍历 children 列表，替你执行 delete child;
```

### 机制讲解

这是全篇**最重要的一节**，值得放慢读。C# 开发者看到"挂 parent 就自动释放"，很容易得出一个错误等式：

> "对象树 = C++ 的内存管理 = GC 的替代品。"

拆开看，两者根本不在一个层面：

- **RAII 是 C++ 语言语法**：栈对象离开作用域，编译器生成的析构调用**必然执行**，这是语言标准保证的，没有任何代码路径能绕过。上一篇第 1 节的 `QByteArray data;` 就是 RAII。
- **对象树是 Qt 库层的"所有权协议"**：父对象在自己的析构函数里写了 `for (child : children) delete child;`。它本质仍然是**裸指针 `delete`**，只是把"散落在各处的 delete"集中到了一处。它不产生新的语言机制，只是一条**约定**——"child 的生命周期由 parent 拥有"。

这个区别带来三个直接推论：

1. **对象树只对"堆上、遵守约定"的对象有效**。你把栈对象交给 parent，parent 析构时照样 `delete` 它——`delete` 栈对象是未定义行为，程序直接崩（错误案例 2）。RAII 永远不会犯这个错（编译器不允许你 `delete` 栈对象），**但对象树协议允许你"误签"，因为没有任何编译期检查**。
2. **对象树没有解决"悬垂指针"**。GC 世界里对象被回收前会先确认"没有引用指向它"；对象树世界里 parent 只管 `delete`，**不管外面还有谁指着**。你手上有 `child` 的裸指针，parent 一析构，这个指针就成了悬垂指针（错误案例 3）。
3. **对象树不等于"智能指针"**。`unique_ptr`/`shared_ptr` 是 C++ 标准库的**语言层所有权工具**，靠析构/引用计数保证；对象树是 Qt 的**应用层所有权工具**。规范第 6 节明确要求分流：UI 控件 → 挂 parent；线程对象 → `moveToThread` + `deleteLater()`；非 QObject 资源 → 智能指针。**两套体系别混用**——同一个对象不能既挂 parent 又被 `unique_ptr` 管着，否则析构两次。

一句话总结这一节：**对象树是"便利的集中 delete"，不是 RAII 的替代品，也不是 GC 的替代品。它只是把"谁负责 delete"这个问题，从"你自己满世界找 delete"简化成"parent 替你统一 delete"。**

### 为什么不能简单照搬

1. 把"挂 parent"当作"GC 托管"是最危险的心智：你会继续到处 `new`，以为都"自动管理"了，但**漏挂 parent 的对象就是孤儿**（错误案例 1）。
2. 把"对象树"当成"可以安全持有指针"的依据：对象树的析构**不通知**外部指针持有者，你的裸指针该悬垂还是悬垂。
3. 把"对象树"和"智能指针"混用：同一个对象被两套体系同时拥有 → 双重析构崩溃。**必须二选一**。

### 在 DataScope 里的落地

- `mainwindow.h` 第 30 行"一般无需手动 delete"是**对象树协议**在工作：UI 控件挂 parent，生命周期随树走。
- 规范第 6 节的分流原则，本质就是回答"这个对象归谁管"：UI → 树；线程 Worker → 树 + `deleteLater`；非 QObject（`QByteArray`、`QString`、标准容器等）→ RAII 值语义 + 智能指针。三类对象，三套规则，**互不混用**。

## 4. delete 与 deleteLater()：什么时候不能"马上删"

> 可类比程度：★★☆☆☆　（C# 没有对应物；GC 不会让你面对"删除时机"问题）

### 一句话类比

`delete` 是"当场拆台"；`deleteLater()` 是"等我这班戏唱完再拆"——因为台子底下还站着人（事件循环）等着踩上去。

### 代码对比

```csharp
// C#：没有"手动删除"这个动作，GC 决定时机，你无从也无需干预
// （IDisposable 是例外，但那是资源，不是对象本身）
```

```cpp
// Qt：两种删除方式
delete obj;             // 立即析构：此刻就释放内存
obj->deleteLater();     // 排队删除：向事件循环投递 DeferredDelete 事件，
                        // 等当前事件处理完、控制权回到事件循环后再真正析构
```

### 机制讲解

为什么会有 `deleteLater()`？因为 Qt 的一切都由**事件循环**驱动（上一篇第 6 节）。事件循环在做的事是"取事件 → 分发事件 → 处理完了 → 取下一个"。危险场景长这样：

1. 事件循环正在执行**槽函数 A**；
2. 槽函数 A 里 `delete` 了对象 X；
3. 槽函数 A 返回，事件循环去取**下一个事件**——而这个事件恰好是发给 X 的（比如排队的 `queued` 信号、`timerEvent`、`update()` 绘制事件）；
4. 事件循环访问 X → **访问已释放的内存** → 崩溃（或未定义行为）。

`deleteLater()` 正是为这个场景设计的：它把"删除"本身变成**一个事件**（`QEvent::DeferredDelete`）投递到 X **所属线程**的事件循环里。事件循环只在**处理完当前事件、回到取事件的主循环**时才处理这个 DeferredDelete——也就是"该轮该处理的都处理完了"才真正析构 X。这样就保证了"**删除动作不会发生在一个事件的处理中途**"。

两个关键点：

- **"所属线程"**：`deleteLater()` 是线程安全的，它把删除请求投递到对象所属线程的事件循环。这就是规范第 6 节"线程对象 → `moveToThread` + `deleteLater()`"的原因——**跨线程不能直接 `delete`**，但 `deleteLater()` 可以把删除安全地"托运"回对象自己的线程。
- **什么时候用 deleteLater**：
  1. 在槽函数里要删除**自己**（`this->deleteLater()`）或**发送信号的 sender**；
  2. 删除一个**可能还有事件排队**的对象（定时器、网络请求、跨线程信号）；
  3. **跨线程**删除对象；
  4. 规范要求：线程 Worker（`QThread` 的对象）一律 `deleteLater()`，禁止直接 `delete`。

### 为什么不能简单照搬

1. **GC 时代你不用想"删除时机"**，所以 C# 开发者很容易写出"在信号槽里直接 `delete sender`"的代码——这在单线程同对象队列下可能碰巧没事，一旦对象属于别的线程或还有排队事件，就是随机崩溃。
2. `deleteLater()` **不是慢速 delete，也不是异步 delete 的万能版**：它仍然要求**事件循环在跑**。如果你在一个没有事件循环的线程（比如纯计算线程）里 `deleteLater()`，这个删除**永远不会执行**——对象泄漏。规则：**对象属于哪个线程，哪个线程要有事件循环，`deleteLater` 才生效**。
3. **`deleteLater()` 之后不要再立即用这个指针**：它只是"排队"，还没真删，指针仍然"看起来有效"，容易误用。用 `QPointer` 记住它，等事件循环处理完再判空。

### 在 DataScope 里的落地

- 规范第 6 节：**线程 Worker → `moveToThread` + `deleteLater()`**，这是 DataScope 的强制约定。
- `QNetworkReply` 等异步对象用完后的标准收尾就是 `reply->deleteLater()`（上一篇第 6 节的代码块里已经出现过）——因为 reply 的内部事件（`finished` 信号的处理、底层 socket 事件）还没排完，不能当场 `delete`。

## 5. 栈上 vs 堆上：QObject 的两栖生活

> 可类比程度：★★★☆☆　（C# 的 `new` 永远在托管堆；C++ 要主动选择"放哪"）

### 一句话类比

C# 里"对象"只住一种房子（托管堆）；C++ 的 QObject 有两种住法——**栈上"帐篷"**（作用域一结束自动收，不能挂树）和**堆上"房子"**（要登记 owner，可以挂树）。**帐篷不能登记进管家的领养簿**。

### 代码对比

```csharp
// C#：new 出来的引用类型永远在托管堆，GC 管
var window = new MainWindow();   // 栈上只有一个引用，对象本体在堆上
```

```cpp
// Qt：两种选择
MainWindow window;                     // ① 栈对象：main 返回时自动析构（RAII），无 parent
auto *panel = new QPanel(this);        // ② 堆对象：必须挂 parent（或交给智能指针），
                                       //    否则没人 delete（孤儿）
```

### 机制讲解

**栈上 QObject**：

- 生命周期 = 作用域。离开 `{}` 自动析构（RAII，上一篇第 1 节）。
- **不能有 parent**。为什么？父对象析构时会 `delete child`，而 `delete` 是"释放堆内存"的动作——对一个栈对象执行 `delete` 是双重析构，未定义行为，直接崩溃（错误案例 2）。
- 什么时候用：生命周期**恰好嵌在**某个作用域内，且不需要跨函数存活。典型：`main()` 里的 `MainWindow window;`。

**堆上 QObject（必须 `new`）**：

- 生命周期不跟作用域走，必须有一个明确的 owner（parent 或智能指针），否则成孤儿。
- 什么时候**必须** `new`：
  1. **要挂对象树**——child 必须在堆上（栈对象挂树 = 双重析构）；
  2. **生命周期要跨越创建它的函数**——比如主窗口的子控件要跟主窗口一样长命，而主窗口在 `main()` 里、子控件在别的函数里创建；
  3. **要 `moveToThread` 到其他线程**——QObject 线程亲和性要求对象在堆上、无 parent，才能整体迁去目标线程；
  4. **数量动态变化**——运行时按需创建、删除（如动态图表、动态面板）。

判别标准一句话：**"它该由谁、在什么时候销毁？"能靠作用域回答 → 栈；需要跨作用域存活 → 堆，并明确登记 owner。**

### 为什么不能简单照搬

1. C# 里"窗口"永远是引用类型，你从不考虑"窗口放栈上还是堆上"；C++ 里这是**每次创建对象都要回答的问题**。答错了：栈对象挂树 → 崩；堆对象不登记 → 泄漏。
2. **"临时用一下的 QObject"别 `new`**：比如一个只在函数里用的 `QMessageBox`，用栈对象 + `exec()` 就好，别 `new` 完忘了删。
3. `new` 完之后**立即决定归属**：要么 `new QPushButton(this)` 一步到位挂 parent，要么交给智能指针。别写"先 `new` 出来再说"，那必然产生孤儿窗口期。

### 在 DataScope 里的落地

- `main.cpp` 第 37 行前的 `MainWindow window;`：**栈对象、根节点**。它不挂 parent（没有比它更大的树），靠 RAII 在 `main` 返回时析构——析构函数里 Qt 自动清理整棵 UI 子树（第 30 行注释的含义）。
- 今后在 `mainwindow.cpp` 里创建子控件，统一 `new Qxxx(this)`（堆 + 挂 parent），这是 UI 代码的**默认动作**。

## 6. Meta Object System 与 MOC：C# 反射的"编译期版"

> 可类比程度：★★★☆☆　（能力对等：都能在运行时查类信息、读写属性、做类型转换；但 C# 靠运行时元数据，Qt 靠编译期生成）

### 一句话类比

C# 的反射是"运行时拿着身份证查户口本"；Qt 的元对象系统是"**上户口的时候就印好了一本相册**，运行时只是翻相册"——信息在**编译期**就做好了。

### 代码对比

```csharp
// C#：运行时反射 —— 程序集里带着元数据表，typeof() 在运行时查询
var t = typeof(MainWindow);
var props = t.GetProperties();              // 运行时扫描
var title = (string)t.GetProperty("Title")?.GetValue(win);
```

```cpp
// Qt：编译期 moc 生成元数据 —— QMetaObject 是静态数据结构
const QMetaObject *mo = win->metaObject();      // 返回静态 QMetaObject
QString cls = mo->className();                  // "MainWindow"
QVariant title = win->property("windowTitle");  // 读属性（走元对象）
MainWindow *mw = qobject_cast<MainWindow*>(obj); // 类型转换，等价 obj as MainWindow
```

### 机制讲解

**C# 反射**：编译器把类型信息（类名、成员、属性、接口）写进程序集的元数据表（metadata）。运行时通过 `Type` 对象查询——这是一张**在内存里被反复读取的表**。

**Qt 元对象系统（Meta Object System）**：三件套——`QObject` 基类 + `Q_OBJECT` 宏 + **moc**（meta-object compiler）。

- `Q_OBJECT` 宏展开后，在类里声明了几个"骨架"成员：`static const QMetaObject staticMetaObject;`、虚函数 `metaObject()`、`qt_metacall()`、`qt_metacast()` 等；
- **moc 在编译前**读取带 `Q_OBJECT` 的头文件，生成 `moc_*.cpp`。里面实现了这些骨架：一个填好类名、父类指针、信号槽表、属性表的**静态 `QMetaObject` 实例**；信号函数的**函数体**（把参数打包传给 `qt_metacall`）；`qt_metacall()` 的**按索引分发**逻辑。
- 所以运行时 `metaObject()` 只是返回一个**指向静态数据**的指针——没有运行时扫描、没有加载时解析，全部信息在**编译期**已经固化。

由此衍生三个常用能力：

- **`property()` / `setProperty()`**：按名字在 `QMetaObject` 的属性表里查索引，再通过 `qt_metacall` 读写——类似 C# 反射读写属性。额外好处：`setProperty("任意新名字", value)` 还能**动态添加运行时属性**（不在类里声明的也存得进去），这是 C# 反射做不到的。
- **`qobject_cast<T*>(obj)`**：基于元对象链的运行时类型检查，等价 C# 的 `obj as T`。实现是沿着 `metaObject()` 的父类链比对类型，**失败返回 `nullptr`**，绝不抛异常、绝不产生未定义行为（对比 C++ 原生 `static_cast` 的不安全）。
- **信号槽连接能自动断连**：`connect` 时接收者（receiver）的元对象记录了连接；接收者析构时，Qt 通过元对象机制**自动从所有 sender 上断开**——这就是上一篇第 5 节"接收者死了连接就没了"的实现基础。

### 为什么不能简单照搬

1. **`Q_OBJECT` 必须先写**：漏了 `Q_OBJECT`，moc 不会生成元对象，`metaObject()` 只能拿到父类的信息、信号槽全废、`qobject_cast` 不认你。而且漏写通常不是编译报错，是"运行时行为诡异"——这是 Qt 新手最隐蔽的坑。
2. **moc 是"编译期"，不是"运行时"**：你不能在运行时往元对象里"加一个类"（C# 反射也不能加类，但能动态加载程序集；Qt 用插件机制 `QPluginLoader` 对应）。别指望像 `Assembly.LoadFrom` 那样动态引入类型。
3. **`qobject_cast` 只对 QObject 有效**：对非 QObject 类型（`QString`、结构体）用不了。C# 的 `as` 对所有引用类型都行。
4. **`property()` 返回 `QVariant`**：读取要 `.toInt()`、`.toString()` 等显式转换，不像 C# 反射 `GetValue` 后直接拿到强类型对象。

### 在 DataScope 里的落地

- `mainwindow.h` 第 25 行 `Q_OBJECT` 就是元对象系统的入口；文件头注释（第 19-22 行）原话："Q_OBJECT 宏是 Qt 元对象系统的入口：启用信号槽、属性系统、元对象信息（对应 C# 反射能力）；编译时由 AUTOMOC 调用 moc 生成 *_moc.cpp 元对象代码。"
- `mainwindow.h` 第 29 行 `explicit MainWindow(QWidget *parent = nullptr);` 里的 `explicit` 防隐式转换，和元对象无关但和"对象身份"有关——禁止 `QWidget` 偷偷变成 `MainWindow`，保持类型边界的严谨。
- P2 测试文件 `tst_byteutils.cpp` 里 `Q_OBJECT` 一样由 moc 处理、末尾 `#include "tst_byteutils.moc"`——这就是"元对象代码也是普通源码"的直观证据。

## 7. 与 C# 的全面对照表

把本篇的关键机制对齐成一张表。**每一行都标了"能不能照搬"**。

| C# / WPF | Qt / C++ | 类比程度 | 一句话差异 |
|----------|----------|----------|-----------|
| GC 托管堆（自动回收、时机不确定） | 对象树 + RAII（所有权明确、时机确定） | ★★☆☆☆ | GC 让内存隐形；Qt 要求你回答"谁拥有" |
| 所有类型继承 `object` | 需要能力的类才继承 `QObject` | ★★☆☆☆ | `QString`/`QVector` 不是 QObject，无信号槽 |
| `object` + `DependencyObject` 分层 | `QObject` 一体机（六能力打包） | ★★★☆☆ | Qt 不能只取其中一部分能力 |
| 依赖属性（DependencyProperty） | 元对象属性（`property`/`setProperty`） | ★★★☆☆ | WPF 为 XAML 绑定服务；Qt 由 moc 驱动、可动态加属性 |
| 反射（`typeof`/`GetProperties`） | 元对象系统（`metaObject`/`qt_metacall`） | ★★★☆☆ | C# 运行时查元数据；Qt 编译期 moc 生成静态元数据 |
| `obj as T`（引用类型转换） | `qobject_cast<T*>(obj)`（仅 QObject） | ★★★★☆ | 都失败返回 null；Qt 只对 QObject 有效 |
| 逻辑树 / 可视树（层级描述） | QObject 对象树（**所有权**） | ★☆☆☆☆ | WPF 的树不负责内存；Qt 的树就是内存所有权 |
| GC 保证"引用安全"（无悬垂） | 裸指针随时可悬垂；`QPointer` 补洞 | ★★☆☆☆ | GC 消除悬垂；Qt 要主动用 `QPointer` 防悬垂 |
| `WeakReference`（不阻回收） | `QPointer` / `QWeakPointer`（不增计数、自动置空） | ★★★☆☆ | QPointer 只针对 QObject；C# WeakReference 是通用弱引用 |
| 手动释放（`IDisposable`/`using`） | `delete` / `deleteLater()` | ★★★☆☆ | C# 用 `using` 确定性释放；Qt 有事件循环，删除时机要配合队列 |
| DispatcherObject（线程亲和） | QObject 线程亲和性 + 信号槽跨线程排队 | ★★★☆☆ | 两者都"对象属于创建它的线程"；Qt 靠事件循环跨线程投递 |

**重点对照两行（GC vs 对象树 / WeakReference vs QPointer）**：

- **GC 托管 vs 对象树**：GC 是"对象不可达才回收"（先保证没有引用，再回收）；对象树是"parent 析构就删 child"（**不管外面还有没有引用**）。所以对象树省不了"悬垂"的心——它是所有权工具，不是安全回收工具。
- **WeakReference vs QPointer**：`QPointer<QWidget> p = widget;` 会跟踪这个 widget，它被 delete 后 `p` 自动变 `nullptr`，用前 `if (p)` 判空即可。实现原理：QObject 析构时通知内部守卫结构，置空所有观察它的 QPointer。**它不增加引用计数、不阻止删除，只是"看着它死并通知你"**——对应 C# 里 `WeakReference` 的"不阻止 GC 回收"。

## 8. 错误案例：把 C# 思维直接搬进 Qt

这六起事故是本篇内容的"反面教材合集"。请反复对照前七节理解根因。

### 错误案例 1：`new` 完不挂 parent 也不 delete → 内存泄漏

**C# 惯性**：`new` 完交给 GC，放心。

```cpp
// Qt 照搬
auto *timer = new QTimer;      // 无 parent！无智能指针！没人 delete！
timer->start(1000);
```

- **现象**：程序运行越久内存越涨；窗口关了，`timer` 的析构从没被调用。
- **根因**：C# 有 GC 兜底；C++ 裸 `new` 必须有 owner。这个 `QTimer` 无父无主，成了"孤儿对象"——既不在对象树上，也没人智能指针管它，谁都不负责回收（第 3 节：对象树是"集中 delete"的协议，**不挂树就没人替你 delete**）。
- **正确写法**：挂 parent（进对象树）或直接栈对象：

```cpp
auto *timer = new QTimer(this);   // 挂 this 的对象树，随 this 析构
// 或者作用域内够用就上栈：
QTimer timer;
timer.start(1000);
```

- **对照**：第 2 节对象树、第 5 节栈/堆选择。

### 错误案例 2：栈对象传给 parent → 双重析构崩溃

**C# 惯性**：对象在哪儿、谁引用它都无所谓，GC 都管。

```cpp
// Qt 照搬
void MainWindow::buildUi() {
    QPushButton btn(this);        // 栈对象 + 挂 parent —— 大错！
    // btn 在函数返回时析构一次；
    // 等 this（MainWindow）析构时，对象树再 delete &btn —— 第二次析构！
}
```

- **现象**：编译能过、运行也不一定马上崩——但**在 MainWindow 析构的那一刻**（程序退出时）崩溃，或者更早，取决于 `btn` 离开作用域后 `this` 是否还用它的指针。未定义行为，时好时坏，最难查。
- **根因**：对象树约定"child 由 parent delete"（第 2 节），但 `delete` 只对堆对象合法。`btn` 是栈对象，作用域结束**已经析构了一次**；MainWindow 析构时又 `delete &btn`，**同一块内存析构两次** → 崩溃。
- **正确写法**：挂 parent 就 `new`（堆）；不想 `new` 就上栈且**不要**挂 parent：

```cpp
// 方案 A：堆 + 挂树（UI 控件默认做法）
auto *btn = new QPushButton(QStringLiteral("连接"), this);

// 方案 B：栈 + 不挂 parent（仅作用域内使用）
QPushButton btn(QStringLiteral("连接"));
// 用完即走，离开作用域自动析构
```

- **对照**：第 5 节"栈上 QObject 不能有 parent"。

### 错误案例 3：`delete` 后继续用指针（悬垂指针）→ 崩溃

**C# 惯性**：引用永远是安全的，对象不会被"提前删掉"。

```cpp
// Qt 照搬
auto *panel = new QPanel(this);
// ... 某处因为需求直接删了它：
delete panel;
// ... 别处还在用：
panel->setVisible(true);   // 悬垂指针！访问已释放内存 → 崩溃
```

- **现象**：`setVisible` 崩溃，或"碰巧"不崩但产生脏数据；有时删除后隔了很久才在**完全不相关的地方**炸——典型的悬垂指针"延迟引爆"。
- **根因**：`delete` 只释放内存，**不会**把外部所有指向它的指针置空。之后任何 `panel->` 都是访问已释放内存（第 3 节：对象树不解决悬垂）。
- **正确写法**：明确所有权，删除后立刻放弃所有裸指针；需要在别处"随时可能被删的对象"用 `QPointer`：

```cpp
QPointer<QPanel> panel = new QPanel(this);   // QPointer 跟踪它
// ... 某处 delete 了 panel：
delete panel;
// ... 别处用之前先判空：
if (panel) panel->setVisible(true);          // panel 已是 nullptr，安全跳过
```

- **对照**：第 7 节 `WeakReference` vs `QPointer`。

### 错误案例 4：在 lambda/信号槽里捕获裸 `this` 而对象已删除 → 悬垂调用

**C# 惯性**：lambda 捕获 `this`，GC 保证它一定活着。

```cpp
// Qt 照搬（危险）
connect(device, &Device::dataArrived, [this](const QByteArray &f) {
    appendToView(f);        // 捕获了裸 this！
});
```

- **现象**：`this`（接收者）析构后，`device` 还活着，又发来一次数据 → lambda 执行时 `this` 已死 → 悬垂调用，崩溃。**时好时坏**，最难查的那一类。
- **根因**：这条 `connect` **漏了第 3 个参数（context 对象）**。没有 context，Qt 就无法在 `this` 析构时自动断开这个连接；lambda 捕获了裸 `this`，却没人保证 `this` 活着（第 3、6 节：自动断连依赖"接收者是 QObject 且被 connect 登记"）。
- **正确写法**：**必须传 context 对象**，让 Qt 在 `this` 析构时自动断连：

```cpp
connect(device, &Device::dataArrived, this,
        [this](const QByteArray &f) { appendToView(f); });
// 第 3 个参数 this 就是 context：this 析构，Qt 自动断开这条连接
```

- **补充**：如果接收者**不是** QObject（比如一个普通 C++ 类），就改用 `QPointer` 捕获 + 判空（见错误案例 3），或 `std::weak_ptr`。
- **对照**：上一篇第 5 节"生命周期差异"；规范第 5 节"lambda 捕获 this 时注意 receiver 生命周期"。

### 错误案例 5：跨线程直接 `delete` 被信号槽引用的对象

**C# 惯性**：跨线程对象只要不加锁就是安全的（其实也不安全，但至少不会"delete"）。

```cpp
// 工作线程里：直接 delete 一个属于 UI 线程的对象
// （错误示范：worker 线程某处）
delete uiObject;        // uiObject 属于主线程！跨线程 delete = 未定义行为
```

- **现象**：崩溃、死锁、或随机内存损坏——取决于删除那一刻主线程是否正在用这个对象。
- **根因**：QObject 有**线程亲和性**（第 1 节）：对象属于创建它的线程。`delete` 是同步的，工作线程直接 `delete` 一个 UI 线程的对象，等于在别人家在别人正用着的时候把房子拆了——而且 Qt 内部可能在它的线程里还排着这个对象的事件。
- **正确写法**：用 `deleteLater()`，把删除**投递回对象所属线程**的事件循环，让它在自己线程的安全时机执行：

```cpp
// 工作线程里（安全）：把删除请求"托运"回 uiObject 所属线程
uiObject->deleteLater();   // 线程安全；对象所属线程的事件循环处理完当前事件后真正删除
```

- **注意**：前提是 `uiObject` 所属线程**有事件循环在跑**，否则 `deleteLater` 永不生效（第 4 节）。
- **对照**：第 4 节"事件循环场景要 deleteLater"；规范第 6 节"线程 Worker → moveToThread + deleteLater"。

### 错误案例 6：该用 `deleteLater` 的场景硬用 `delete`（正确做法示范）

**C# 惯性**：没有"事件循环"概念，不知道"删除时机"会被排队事件拖住。

```cpp
// 错误：在槽函数里直接删 sender / 自己
connect(net, &Net::finished, this, [&net] {
    delete &net;     // 危险！net 可能还有排队事件；若 net 属于别的线程更是直接 UB
});

// 正确：交给事件循环，处理完当前事件再删
connect(net, &Net::finished, this, [&net] {
    net.deleteLater();   // 投递 DeferredDelete；事件循环收尾时真正析构
});

// 线程 Worker 的标准收尾：对象在自己的线程里自我清理
worker->deleteLater();   // 等价于 worker->moveToThread(...) 后，用完在正确线程 deleteLater
```

- **根因回顾**：`delete` 是"当场拆"，但如果对象还有事件排队、或属于别的线程，"当场"就是错误时机（第 4 节）。
- **判据**：只要删除动作发生在**槽函数/回调内部**、或**对象可能仍有排队事件**、或**跨线程**，就一律 `deleteLater()`。

## 9. 对照速查表（对象模型与内存管理篇）

| 概念 | 类比程度 | 一句话差异 |
|------|----------|-----------|
| QObject 基类 | ★★★☆☆ | `object`+`DependencyObject` 一体机，能力全打包不可拆 |
| Object Tree | ★☆☆☆☆ | WPF 树是层级描述；QObject 树是**内存所有权** |
| 对象树 vs RAII | ★★☆☆☆ | RAII 是语法保证；对象树是"集中 delete"的协议 |
| `delete` vs `deleteLater` | ★★☆☆☆ | 当场拆台 vs 投递 DeferredDelete、事件循环收尾再拆 |
| 栈上 / 堆上 QObject | ★★★☆☆ | 栈上不能挂 parent；跨作用域存活必须 new 并登记 owner |
| 元对象系统 / MOC | ★★★☆☆ | C# 运行时反射 vs Qt 编译期 moc 生成静态元数据 |
| `qobject_cast` | ★★★★☆ | `obj as T` 的 Qt 版，仅对 QObject 有效 |
| `WeakReference` vs `QPointer` | ★★★☆☆ | 都不阻回收/删除；QPointer 只针对 QObject、自动置空 |

## 10. 练习题（请你亲自做）

> 这四题都要**动手编译运行**验证，不是背概念。验证完在代码旁写一行中文注释记录你的观察。

1. **对象树释放验证**：写一个小类 `class Child : public QObject { ~Child() { qDebug() << "child gone"; } }`（记得加 `Q_OBJECT`）。在 `MainWindow` 构造函数里 `new Child(this)`，运行程序后关闭窗口，观察析构日志是否在窗口关闭时打印。再把 `new Child(this)` 改成 `new Child`（不挂 parent），关窗后看日志——**这一次析构日志不会出现**（泄漏）。
2. **双重析构验证**：写一个 `buildUi()` 函数，里面写 `QPushButton btn(this);`（栈对象挂 parent）。编译运行，关闭主窗口，观察崩溃。然后把代码改成 `new QPushButton(this)`，崩溃消失。记录现象差异。
3. **deleteLater 实验**：给一个 `QTimer` 连一个槽，槽里对 timer 调用 `deleteLater()`，再连一个定时事件观察事件循环继续正常跑；对比改成槽里 `delete timer`（把 timer 放堆上）后是否出现随机崩溃。理解"为什么不能在事件处理中途当场拆台"。
4. **qobject_cast 实验**：在 `mainwindow.cpp` 里写 `auto *w = qobject_cast<MainWindow*>(qApp->activeWindow());` 打印结果，再试试对 `QPushButton` 强转成 `MainWindow*`——观察返回 `nullptr` 而不是崩溃，理解元对象类型检查（对比 C# `as`）。
5. **QPointer 实验**：`QPointer<QWidget> p = new QPushButton(this);` 之后 `delete p`，再 `if (p) p->show();`，确认 `p` 已自动变 `nullptr`。把它和"裸指针 delete 后继续用"（错误案例 3）的行为对比，写一句总结。
