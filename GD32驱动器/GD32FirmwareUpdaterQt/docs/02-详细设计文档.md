## 二、协议层设计（Protocol）

### 2.1 协议帧结构

```
| 字节0 | 字节1 | 字节2-3 | 字节4-5 | 字节6~N | (N+1)-(N+2) |
|  SOF  |  FUNC |  CMD    | DATALEN |  DATA   |    CRC      |
| 0x01  | 0x06  | 大端2B  | 小端2B  |  变长    | 小端2B      |
```

### 2.2 CrcCalculator

- **算法**：CRC16/Modbus，多项式 0xA001（反向），初值 0xFFFF
- **API**：
  - `quint16 calculate(const QByteArray &data)` — 整段校验
  - `quint16 calculate(data, offset, length)` — 范围校验
  - `QByteArray toLittleEndianBytes(quint16 crc)` — 小端字节输出
- **验证**：标准校验向量 `"123456789"` → `0x4B37`（tst_crc 已通过）

### 2.3 ProtocolFrame（值类型，不含 QObject）

| 成员 | 类型 | 说明 |
|------|------|------|
| sof / func | quint8 | 固定 0x01 / 0x06 |
| cmd | quint16 | 指令码 |
| data | QByteArray | 有效数据 |
| crc | quint16 | 校验值 |

| 方法 | 说明 |
|------|------|
| `serialize()` | 组帧：SOF→FUNC→CMD(大端)→DATALEN(小端)→DATA→CRC(小端) |
| `deserialize()` | 拆帧：校验长度、帧头、CRC |

### 2.4 FrameBuilder（指令帧工厂）

| 方法 | CMD | DATA |
|------|-----|------|
| buildUpgradeRequest(type) | 0x0010 | [type, 0x00] |
| buildUpgradeStart(fileSize) | 0x0011 | [size 小端4B] |
| buildUpgradeData(offset, data) | 0x0012 | [offset 小端4B + data] |
| buildJumpApp() | 0x0013 | [0x01] |
| buildVersionRequest() | 0x0014 | [0x01] |

## 三、服务层设计（Services）

### 3.1 SerialPortService（串口通讯）

**职责**：封装 QSerialPort，提供单请求-单响应通讯模式。

**核心机制**：
```
调用方 sendRequest(frame, expectedCmd, timeout)
        │
        ▼
   清空接收缓冲 → 登记期望CMD → 启动超时定时器 → write()
        │
        ▼   (事件驱动)
  readyRead信号 → 追加缓冲 → tryParseFrame()
        │
        ▼
   找SOF → 读DATALEN → 凑完整帧 → deserialize校验
        │
        ├─ 成功且CMD匹配 → 停定时器 → emit requestCompleted(frame)
        ├─ 成功但CMD不匹配 → emit requestFailed(MISMATCH)
        └─ 失败(CRC/帧头) → 丢弃该帧
        │
   timeout信号 → emit requestFailed(TIMEOUT)
```

**关键设计点**：
1. **粘包/分包处理**：字节流无帧边界，用 `SOF定位 + DATALEN定长 + 缓冲消费` 实现可靠拆帧
2. **单请求单响应**：同一时刻只允许一个待响应请求，避免回复错配
3. **超时定时器**：`QTimer::singleShot` 自动放弃等待，防止死等
4. **失败原因码**：`ERR_NOT_OPEN / ERR_TIMEOUT / ERR_MISMATCH`

### 3.2 FirmwareUpgradeService（升级引擎·状态机）

**状态枚举**：
```
Idle → Requesting → Erasing → Transferring → Finishing → Completed / Failed
```

**四步流程与回复推进**：

| 状态 | 发送指令 | 等待回复判定 | 下一步 |
|------|----------|-------------|--------|
| Requesting | 0x0010 | DATA[0]=0x00（Boot就绪） | → Erasing |
| Erasing | 0x0011 | DATA[0]=0x00（擦除完成） | → Transferring |
| Transferring | 0x0012（每帧≤128B） | DATA[0]=0x00（本帧完成） | 循环 / 全部发完→Finishing |
| Finishing | 0x0013 | DATA[0]=0x00（跳转成功） | → Completed |

**健壮性设计**：
- **重试**：Requesting/Transferring 阶段超时或失败最多重试 3 次（`MAX_RETRY`）
- **跳转等待**：设备返回"App跳转Boot中"（0x01）时，`QTimer::singleShot(2000)` 延迟 2 秒重发请求
- **超时分级**：普通 5s（`RESPONSE_TIMEOUT`），Flash 擦除 30s（`ERASE_TIMEOUT`）
- **取消**：`cancel()` 置取消标志并立即结束
- **进度映射**：请求 0% → 擦除 5% → 传输 10%~95% 线性映射 → 完成 100%

**版本查询**：独立于升级流程的一次性请求，用 `QSharedPointer<QMetaObject::Connection>` 管理连接生命周期（Qt 5.12 无 connectOnce）。

### 3.3 FirmwareParser（固件解析）

校验链：存在性 → `.bin` 扩展名 → 非空 → ≤2MB → 读入 QByteArray。

## 六、线程模型

**设计决策**：本项目**全程主线程 + 事件驱动**，不引入工作线程。

| 环节 | 处理方式 | 原因 |
|------|----------|------|
| 串口收发 | QSerialPort 内部线程读取 → readyRead 信号在主线程槽处理 | 天然非阻塞 |
| 升级流程 | 状态机：每次"发请求→等信号"都立即返回，不阻塞 UI | 避免界面卡死 |
| 大文件分包 | 每帧 sendRequest 后立即返回，靠回复信号推进 | 无需 QtConcurrent |

> **知识点**：C# 用 `await` 让逻辑顺序化；Qt 用"信号推进状态机"达到同样效果，但回调式写法要求状态显式化（本项目的 `UpgradeState` 枚举就是显式状态）。

## 七、异常与边界处理

| 场景 | 处理 |
|------|------|
| 串口打开失败 | `open()` 返回 false，日志输出错误信息 |
| 固件文件不存在/格式错/过大 | `FirmwareParser` 返回错误，界面红色日志 |
| 通讯超时 | `requestFailed(TIMEOUT)` → 升级引擎按状态重试/失败 |
| 回复 CMD 不匹配 | `requestFailed(MISMATCH)` → 按状态处理 |
| 用户取消 | `cancel()` → 立即结束并标记失败 |
| 日志无限增长 | `setMaximumBlockCount(5000)` 截断 |
